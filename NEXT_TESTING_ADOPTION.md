## First user journey, pending contract acceptance

I's v0 proposal uses `next.test.config.json`, `compatibility: 'vitest'`, and named projects with explicit environments and development/production modes. Its `browser` environment means a Node e2e driver with real browser fixtures, not browser evaluation of the spec. The architecture's earlier TypeScript configuration example is a proposal and must not be copied into a setup guide as implemented behavior.

I's follow-up proposes `next test [directory]` with `--list`, `--run`, `--project`, and repeatable file substring filters. The initial default is run once; watch is not available until J integrates it. There is no `defineConfig` export for the JSON loader, no automatic `.env.test` loading, and no `NODE_ENV=test` translation. Actual execution is now validated in the default development-profile path and explicit Node, RSC and browser development selections to the limited scope recorded below. The complete user journey remains gated; this is not a public setup guide.

The first guide should take one small App Router application through these steps:

1. Install the exact verified Next preview/version and required authoring/browser dependencies. Show browser installation separately. State supported Node and browser versions from validation evidence.
2. Select a Node unit project and run a pure function test using only APIs present in the versioned capability manifest. Show successful output and the nonzero result from an intentionally failing expectation.
3. Select an RSC project. Render a nested async Server Component with a server-only dependency and Client Component boundary through the real renderer. Explain which observations are server output and which require browser execution. Include a serialization or wrong-layer failure with its actual diagnostic.
4. Select a browser e2e project. Navigate the actual route with a fresh browser context. Use the real `instant()` to assert shell visibility and deferred-content absence, then assert completed content after release. Show exactly where the page, base URL, locator expectations, and server lifecycle come from.
5. Run the verified development and production profiles in CI. Distinguish instrumented production testing from a normal deployment artifact. Explain exit codes, artifacts, and cleanup on failure using observed behavior.

Use L's accepted fixture as the executable source for guide snippets. M owns explanatory prose and, once runnable, a separate `examples/with-next-testing` adoption example. Do not repurpose `with-vitest` into a different runtime or copy fixtures into two independently maintained implementations.
