# Next testing: stage three

Build on the accepted stage-two implementation. This stage adds production test profiles, a first registered browser-component workflow, and initial coverage, then verifies those capabilities in a clean packaged installation. Next continues to own compilation, execution and runtime; Vitest supplies the supported authoring contract.

Use fresh tasks and isolated worktrees from the same accepted source snapshot. Implementors use GPT-6 Astra with medium reasoning. The coordinator owns integration and acceptance; a fresh independent validation task owns the combined reference checks. Preserve the existing working development, mocking, snapshot and watch capabilities throughout this stage.

## Integration order

1. I3 agrees the small shared interfaces with their producers and consumers. A3 starts production test compilation; E3 and H3 agree fixture identity and hosting; B3 and K3 agree coverage ownership. Other tasks can develop their owned modules and reference cases concurrently.
2. Integrate production Node execution first, then production RSC and the browser driver. Production test entries must use an explicit test graph without contaminating the ordinary application graph. Validate each profile against normal Next behavior before broadening the public inventory.
3. Integrate development browser mounting through registered fixture IDs and compiler-produced manifests. Server rendering, client chunks and hydration must all come from Next. Use the real browser to verify the completed flow.
4. Integrate the first coverage path with worker completion and source metadata. P3 checks the packaged user journey as increments land. L3 accepts the combined milestone and records the limits that remain.

Coordinate shared native builds through A3. Serialize expensive builds and browser/compiler acceptance runs across worktrees; focused checks can proceed independently. Avoid duplicate infrastructure and repeated broad runs when a bounded correction has a clear verification path.

## Stage acceptance

- Production Node, RSC and browser-driver tests use the actual production environment and retain setup, lifecycle, diagnostics and cleanup semantics. RSC retains the route-less dynamic-subtree scope; it does not establish prerender, PPR or action-transport support. Existing unsupported production combinations stay explicit.
- Keep three distinct checks: isolated production-compiled tests; an application built with testing APIs explicitly exposed for `instant()`; and an ordinary uninstrumented application. Success in one does not certify the others.
- The initial component workflow mounts compiler-registered server fixtures in development Chromium, including async server work, a server-only dependency and an interactive client boundary. Unknown fixtures and invalid serialization fail clearly. A supplied standalone fixture does not claim the application's route/layout context.
- Initial coverage is opt-in, one-shot Node/development line coverage for imported project sources, with JSON output and a text summary. Verify exact original-source line sets, generated-code exclusion, multiple files, retries, failure and cancellation. Mocked artifacts, broader environments, branch/function parity, thresholds and unimported-file expansion require separate evidence before being advertised.
- The clean packed consumer verifies actual public types and runtime paths for the accepted additions. Documentation uses those verified commands and states the compatibility boundaries.
- Existing development setup, APIs, mocks, snapshots, watch, RSC and browser behavior remain accepted. Ordinary production output has no active test entries, fixture endpoints or harness implementation, within an explicitly recorded artifact-inspection scope.

Production component mounting, browser watch, watch snapshot updates, broad coverage-provider compatibility, precise affected-test selection, further Vitest APIs, editor integration and wider platform/browser support remain later increments. Preserve the current narrow static-mock scope rather than expanding it implicitly with production support.

## Ownership and handoff

I3 owns contracts, configuration and orchestration. A3 owns shared native/compiler entry points and templates. B3 owns execution and worker protocol; E3 owns request/RSC rendering and server fixture semantics; H3 owns browser resources and component hosting; K3 owns coverage and reporting; P3 owns exports, dependencies, examples and adoption docs; L3 owns canonical acceptance evidence. Agree changes across these boundaries before editing another owner's files.

Each handoff includes an exact patch, its required dependency patches, checks actually run and remaining limits. Native changes include immutable source/binary provenance. Reference the accepted baseline rather than reconstructing previous patch chains. The coordinator integrates reviewed increments; L3 verifies the actual combined system.
