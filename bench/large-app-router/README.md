# large-app-router

A large generated App Router application. It is the shared target for benchmarking how `next build` and `next dev` with Turbopack scale with the number of CPU cores.

Only the generator, config and scripts are committed. The application (`app/`, `components/`, `lib/`) is generated by a deterministic script, so the same arguments always produce byte-identical files.

## What gets generated

With the default size (`--routes 5000 --components 3000`), about 21k files:

- **App Router**: a root layout and 100 sections, each with its own layout, `loading.tsx`, `error.tsx` and index page. There are 5000 page routes. ~10% of them are dynamic `[slug]` segments with `generateStaticParams`, and ~15% have a nested layout.
- **Server and client components**: pages and layouts are server components. ~35% of the shared components are `'use client'` components with state, and the per-route `widget.tsx` files are client components with state and effects.
- **Shared component library**: 3000 components layered like a design system (primitives → molecules → organisms → templates). Each component imports 1–3 components from lower layers, so modules are shared heavily across routes, but every module's transitive closure stays small. Total work therefore grows linearly with the app size.
- **CSS**: a CSS Module next to every component, layout and page, plus a global stylesheet.
- **npm dependencies** (versions already in the workspace): `lodash-es`, `lucide-react`, `clsx`, `dayjs` and `zod`.
- **Dynamic imports**: `next/dynamic` in pages and `import()` in client event handlers.
- **Route handlers**: 500 `app/api/*/route.ts` with `GET`/`POST` handlers, half of them `force-dynamic`.
- **Utility modules**: 750 TypeScript modules in `lib/` that shape, validate and format data.

Derived sizes: sections = `routes / 50`, route handlers = `routes / 10`, utility modules = `components / 4`.

## Setup

From the repository root:

```bash
pnpm install
pnpm build   # builds packages/next/dist, which the scripts below use
```

### Use a release build of next-swc

Always measure with a release (optimized) native binary. Debug or dev-profile builds of next-swc scale very differently.

- `pnpm install` installs a published `@next/swc-*` binary, which is a release build. Its version may lag behind `packages/next`. To match the current canary exactly, download the matching package and point Next.js at it:

  ```bash
  VERSION=$(node -p "require('./packages/next/package.json').version")
  mkdir -p /tmp/next-swc && cd /tmp/next-swc
  npm pack @next/swc-linux-x64-gnu@$VERSION && tar xzf next-swc-linux-x64-gnu-$VERSION.tgz
  export NEXT_TEST_NATIVE_DIR=/tmp/next-swc/package
  ```

- To measure local Rust changes, build a release binary with `pnpm build-all` (or `pnpm --filter=@next/swc build-native-release`). Then unset `NEXT_TEST_NATIVE_DIR` so the locally built `packages/next-swc/native/*.node` is used.

## Generate

```bash
cd bench/large-app-router
pnpm prepare-bench                                # default size
node scripts/generate.mjs --routes 500 --components 300   # smaller, e.g. for quick checks
node scripts/generate.mjs --help
```

| Option         | Default | Description                          |
| -------------- | ------- | ------------------------------------ |
| `--routes`     | `5000`  | Number of page routes                |
| `--components` | `3000`  | Size of the shared component library |
| `--seed`       | `1`     | PRNG seed                            |

Each run deletes the previously generated files first.

## Build and dev

```bash
pnpm build-application   # next build (Turbopack)
pnpm build-nocache       # rm -rf .next && next build
pnpm dev-application     # next dev (Turbopack)
```

Type checking is disabled in `next.config.js`, because it runs `tsc` in a separate process and isn't part of what this app measures. The Turbopack persistent cache is enabled, as it is by default. Set `TURBO_CACHE=0` to disable it.

## Benchmark

`scripts/bench-build.mjs` runs N cold `next build`s, deleting `.next` before each one. It reports:

- the wall time of the whole `next build`
- the Turbopack compile time (the `run-turbopack` span from `.next/trace`)

Both are reported per run and as mean ± sample standard deviation.

```bash
pnpm bench-build --runs 3 --cpus 16
# Running 3 cold next build(s) pinned to CPUs 0,1,...,15...
#   run 1: ...s wall, turbopack compile ...s
#   ...
# next build wall time: ...s ± ...s (min ..., max ..., n=3)
# turbopack compile:    ...s ± ...s (min ..., max ...)
```

| Option              | Description                                                                       |
| ------------------- | --------------------------------------------------------------------------------- |
| `--runs <n>`        | Number of builds (default `3`)                                                    |
| `--cpus <n>`        | Pin the build to the first `n` CPUs this process may use (`taskset`, Linux)       |
| `--cpu-list <list>` | Pin the build to an explicit CPU list, e.g. `0-7` or `0,2,4,6` (`taskset`, Linux) |
| `--json <file>`     | Also write the results as JSON                                                    |
| `--verbose`         | Stream the `next build` output                                                    |

Example scaling sweep:

```bash
for c in 8 16 32; do pnpm bench-build --runs 3 --cpus $c --json results-$c.json; done
```

For stable numbers, keep the machine otherwise idle.

Mind the CPU topology (`lscpu`, `/sys/devices/system/cpu/cpu*/topology/thread_siblings_list`). `--cpus` counts logical CPUs. On machines with SMT/Hyper-Threading, the sibling threads of a core are often adjacent (CPU 0 and CPU 1 share a core). In that case `--cpus 16` is only 8 physical cores. Use `--cpu-list` to pin one thread per physical core (e.g. `--cpu-list 0,2,4,6,8,10,12,14`), and always report which CPUs were used.

## Controlling the thread count

- **CPU affinity** (recommended): `--cpus <n>`, or `taskset -c 0-15 pnpm build-application`, limits every thread of the build to those CPUs. Turbopack sizes its thread pools from `std::thread::available_parallelism()`, which respects the affinity mask. Next.js sizes its Node.js workers (page data collection, static generation) from `os.availableParallelism()`, which respects it too. This is the closest simulation of a machine with fewer cores.
- **`TURBO_TASKS_AVAILABLE_PARALLELISM=<n>`**: overrides the parallelism Turbopack detects. It controls the tokio worker thread count and the internal parallel work splitting, without restricting which CPUs the threads run on. Node.js workers still use every available core. Use it to separate "fewer threads" from "fewer cores".
- **`TOKIO_WORKER_THREADS`** has no effect: next-swc sets the tokio worker count explicitly from the value above.

For profiling, set `NEXT_TURBOPACK_TRACING=1` to write a Turbopack trace to `.next/trace-turbopack.bin`.
