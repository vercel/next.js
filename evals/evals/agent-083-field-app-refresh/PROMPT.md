Our field technicians run this dispatch console on tablets over flaky cellular connections. Two asks for this release — one launch, both land together.

**1. Offline shell.** Today, when the connection drops between sites, any navigation shows the browser's offline error page. Add a service worker so the app keeps standing: cache the app shell when the worker installs, and when a navigation fails offline, answer with the cached shell instead of the error page. The worker only handles the shell — live data keeps going to the network, and job data must never be served out of the offline cache. Platform team's hard requirements: the worker is written in TypeScript and lives in our app tree, going through the same build and type pipeline as the rest of the code, and it derives its cache name from the shell-version string in `lib/version.ts` — the same single source of truth the footer renders. When we bump the version, that one edit has to invalidate the old shell cache, which only works if exactly one copy of that string exists in the codebase. No hand-copied files in `public/`, no duplicated version constants, no extra build steps, no third-party PWA packages.

**2. The jobs list refetches on every bounce-back.** Techs live in the jobs list (`/jobs`). Going from the list into a job's detail page and straight back refetches the whole list every time — even within seconds — so the table flashes and their scroll position jumps. Keep the list per-request fresh for new visits (it must stay dynamic — no shared caching of its data), but let a tech's session reuse what it just fetched for about two minutes when they bounce back from a detail page. This is about in-app navigation while online — it is not the offline worker's job, so don't solve it there. Scope the reuse to the jobs list page only; every other page keeps today's behavior.
