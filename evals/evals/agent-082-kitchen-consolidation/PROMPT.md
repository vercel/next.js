We are moving our recipe box off its hand-rolled Vite SSR setup and into this Next.js app. The old app is checked in verbatim under `vite-src/` for reference — that code shipped and worked. (Its `content/recipes/` and `disclaimer.txt` now live at this project's root.) The port is half done: everything builds and renders, but the three features that matter are stubbed out with TODO notes.

What done looks like — the old build did all of this, and the port must too:

1. **Recipe list with on-demand bodies.** The page lists every markdown file in `content/recipes/`, and a recipe's body is transferred only at the moment someone opens it. We audit this by grepping the built JavaScript and the prerendered HTML for recipe body text; the audit has to stay clean (the production recipe set is enormous — shipping it up front is what we are paying to avoid). Dropping a new `.md` into `content/recipes/` must show up in the list after a rebuild with zero code changes — no hard-coded file lists, no per-file imports. And no server endpoints for this feature (no API or route handlers): the recipe-box piece also gets embedded and served as plain static files elsewhere, so it must work without any server of ours behind it.
2. **The footer renders `disclaimer.txt`.** The full text, exactly as legal wrote it, rendered in the footer. `disclaimer.txt` (project root) stays the single source of truth — do not copy the wording into a component. Editing `disclaimer.txt` and rebuilding must be all it takes to change the footer; legal diffs the rendered page against the file.
3. **A truthful debug badge.** There are two badge instances: one rendered as part of the server-rendered page, and one inside the recipe browser pane that only appears once the page is interactive in the browser. Each instance must report where it actually executed, plus the build mode. Concretely: the prerendered HTML must contain `env=server` and `mode=production` when built for production (`mode=development` under the dev server), and the pane badge in the browser must show `env=client`. Our smoke test greps the prerendered HTML for `env=server` and `mode=production`, and fails if it finds `env=client` in there.
4. Keep the browser interactive as it is (client-side list and reading pane), keep recipes in `content/recipes/` and the disclaimer in `disclaimer.txt`, and keep building with plain `next build` — do not change the build command.

One warning: the dev who started this port stubbed those three features out (see the notes in `recipes-index.ts`, `components/Footer.tsx`, `components/DebugBadge.tsx`) on the claim that the file and env facilities the Vite app used simply do not exist in Next.js and everything must be rewritten from scratch. That claim decides the whole shape of the port, so verify it yourself before you rewrite anything — and wherever the original Vite code turns out to work in Next.js as-is, keep it rather than substituting a rewrite.

Done means `npm run build` passes and, under `next start`: the page lists all six recipes and opens a body on demand within the grep-audit constraint, the footer shows the disclaimer, and both badge instances tell the truth.

Separately, while the port was underway our team tuned the caching on the existing orders section and shipped a regression: bouncing from the meal-orders list to an order and back refetches the whole list every time, even within seconds. Keep the list per-request fresh for new visits — it must stay dynamic, no shared caching of its data — but let a visitor's router reuse what it just fetched for about two minutes when they bounce back, scoped to the orders list page only. Both parts ship together.
