During [prerendering](/docs/app/glossary#prerendering) or Instant Navigation validation, a function used the [`use cache`](/docs/app/api-reference/directives/use-cache) directive, but its [`cacheLife`](/docs/app/api-reference/functions/cacheLife) settings excluded the cached result from required prerendered output.

This can happen in route content, [`generateMetadata()`](/docs/app/api-reference/functions/generate-metadata), or [`generateViewport()`](/docs/app/api-reference/functions/generate-viewport). A cached function can still require rendering at request time when its lifetime is too short.

With [Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents), Next.js excludes cached results whose lifetime settings do not meet the [`cacheLife` prerendering requirements](/docs/app/api-reference/functions/cacheLife#prerendering-behavior). A cache can qualify for a prerender while still being too short-lived for an [App Shell](/docs/app/glossary#app-shell).

## Ways to fix this

Choose the fix that matches where the cache is used and the freshness the data needs. These are the same fixes offered by the dev overlay, with availability determined by the context:

| Context                    | Available fixes                                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Route content              | [Cache](#increase-the-cache-lifetime), [Stream](#wrap-in-or-move-into-suspense), or [Block](#allow-blocking-route) |
| Metadata                   | [Cache](#increase-the-cache-lifetime), [Static](#use-static-metadata), or [Dynamic](#mark-the-route-as-dynamic)    |
| Viewport                   | [Cache](#increase-the-cache-lifetime), [Static](#use-static-viewport), or [Block](#allow-blocking-route)           |
| Fully static route content | [Cache](#increase-the-cache-lifetime) or [Remove](#remove-the-data-access)                                         |
| Fully static metadata      | [Cache](#increase-the-cache-lifetime) or [Static](#use-static-metadata)                                            |
| Fully static viewport      | [Cache](#increase-the-cache-lifetime) or [Static](#use-static-viewport)                                            |

A route with [`ensureStatic = 'navigation'`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#navigation) must satisfy its static requirement even inside `<Suspense>`.

## Increase the cache lifetime

Choose this fix when the data can remain cached long enough to meet the [`cacheLife` prerendering requirements](/docs/app/api-reference/functions/cacheLife#prerendering-behavior). Update the settings inside the cached function that produces the data.

### Patterns

#### Increase the relevant lifetime values

Update each setting that excludes the cached result, following the [`cacheLife` reference](/docs/app/api-reference/functions/cacheLife#prerendering-behavior). This example uses values that qualify for both prerendering and the App Shell:

```ts filename="app/data.ts"
import { cacheLife } from 'next/cache'

export async function getData() {
  'use cache'

  cacheLife({
    stale: 300,
    revalidate: 60,
    expire: 300,
  })

  const response = await fetch('https://api.example.com/data')
  return response.json()
}
```

The card shows only `expire` as an abbreviated example. Increasing `expire` alone does not fix a cache excluded by a short `stale` value or by `revalidate: 0`.

Learn more: [`cacheLife`](/docs/app/api-reference/functions/cacheLife).

### Trade-off

Longer lifetimes allow the cached data to be included in prerendered output, but may serve older data. Choose values that match the freshness your data requires.

### Gotchas

- Set `cacheLife` in the cached function, which may be a helper called by the highlighted `await`. The dev overlay points to where the route consumes the cached result.
- When both are set, `expire` must be longer than `revalidate`.
- Adding `use cache` again does not resolve this error. The function is already cached.
- Wrapping the access in `<Suspense>` or setting `instant = false` does not satisfy [`ensureStatic = 'navigation'`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#navigation). A fully static route must increase the lifetime or remove the access.

## Wrap in or move into Suspense

Choose this fix when route content should keep its short cache lifetime and can arrive after the rest of the page. Wrap the component that consumes the cached result in [`<Suspense>`](https://react.dev/reference/react/Suspense).

### Patterns

#### Keep the cached read inside the boundary

Move the `await` into a child component so the surrounding page can prerender while the child waits for the cached data. Keep the cached `getData` helper's existing short lifetime.

```tsx filename="app/page.tsx"
import { Suspense } from 'react'
import { getData } from './data'

async function DataChild() {
  const data = await getData()
  return <pre>{JSON.stringify(data)}</pre>
}

export default function Page() {
  return (
    <>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading data...</p>}>
        <DataChild />
      </Suspense>
    </>
  )
}
```

Learn more: [Wrap in or move into Suspense](/docs/messages/blocking-prerender-runtime#wrap-in-or-move-into-suspense) for more boundary patterns.

### Trade-off

The surrounding content appears immediately, while the cached content waits for request-time rendering and shows the fallback until it arrives.

### Gotchas

- Put the cached read below the boundary. Awaiting `getData()` in the parent before returning `<Suspense>` still blocks that parent.
- This fix does not satisfy `ensureStatic = 'navigation'`. The entire server-rendered route must be static.
- Metadata and viewport exports are outside the page's component tree. Use their corresponding fixes below.

## Use static metadata

Choose this fix when the metadata can use values known at build time. Replace [`generateMetadata()`](/docs/app/api-reference/functions/generate-metadata) with a static [`metadata`](/docs/app/api-reference/functions/generate-metadata#the-metadata-object) export.

### Patterns

#### Replace the cached lookup with an object

Remove the metadata function that consumes the short-lived cache and export the values directly.

```tsx filename="app/page.tsx"
export const metadata = {
  title: 'My Page',
}

export default function Page() {
  return <h1>My Page</h1>
}
```

Learn more: [Use static metadata](/docs/messages/blocking-prerender-metadata-runtime#use-static-metadata) for parameter-specific patterns.

### Trade-off

The metadata no longer reflects changes to the cached data between builds. Use this when a fixed title or description meets the route's needs.

### Gotchas

- Replace the export that consumes the short-lived cache. Adding a static object elsewhere does not remove an inherited metadata dependency.
- This fix also applies when the route must be fully static.

## Mark the route as dynamic

Choose this fix when metadata needs the short-lived cached data and the route can include intentional request-time rendering. A dynamic marker inside `<Suspense>` lets the page retain prerendered content while the metadata resolves at request time.

### Patterns

#### Add a dynamic marker to the page

Keep the cached metadata lookup and render a component that calls [`connection()`](/docs/app/api-reference/functions/connection) inside a boundary.

```tsx filename="app/page.tsx"
import { Suspense } from 'react'
import { connection } from 'next/server'
import { getData } from './data'

export async function generateMetadata() {
  const data = await getData()
  return { title: data.title }
}

async function DynamicMarker() {
  await connection()
  return null
}

export default function Page() {
  return (
    <>
      <h1>My Page</h1>
      <Suspense fallback={null}>
        <DynamicMarker />
      </Suspense>
    </>
  )
}
```

Learn more: [Mark the route as dynamic](/docs/messages/blocking-prerender-metadata-runtime#mark-the-route-as-dynamic).

### Trade-off

The metadata resolves at request time. The page can still show its prerendered content before the metadata arrives.

### Gotchas

- Wrap the marker in `<Suspense>` so it does not block the page body.
- This fix applies to metadata on routes that allow request-time rendering. It does not satisfy `ensureStatic = 'navigation'`.
- Framework-synthesized routes such as `/_not-found` may inherit root metadata without a page body where you can place a marker. Use [static metadata](#use-static-metadata) or [increase the cache lifetime](#increase-the-cache-lifetime) there.

## Use static viewport

Choose this fix when the viewport can use values known at build time. Replace [`generateViewport()`](/docs/app/api-reference/functions/generate-viewport) with a static [`viewport`](/docs/app/api-reference/functions/generate-viewport#the-viewport-object) export.

### Patterns

#### Replace the cached lookup with an object

Remove the viewport function that consumes the short-lived cache and export the values directly.

```tsx filename="app/layout.tsx"
import type { ReactNode } from 'react'

export const viewport = {
  themeColor: '#000',
}

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html>
      <body>{children}</body>
    </html>
  )
}
```

Learn more: [Use static viewport](/docs/messages/blocking-prerender-viewport-runtime#use-static-viewport).

### Trade-off

The viewport no longer reflects changes to the cached data between builds. A static theme color applies to every request.

### Gotchas

- Changing a layout's viewport affects routes that inherit it.
- This fix also applies when the route must be fully static.

## Allow blocking route

Choose this fix when the route needs the short-lived data before it can display useful content. Setting [`instant`](/docs/app/api-reference/file-conventions/route-segment-config/instant) to `false` allows the segment to wait for request-time rendering.

### Patterns

#### Opt the page out

Set the export on the page that consumes the short-lived cache.

```tsx filename="app/page.tsx"
import { getData } from './data'

export const instant = false

export default async function Page() {
  const data = await getData()
  return <pre>{JSON.stringify(data)}</pre>
}
```

Learn more: [Ensuring instant navigations](/docs/app/guides/instant-navigation).

#### Opt the layout out

Set the export on the layout when the layout itself must wait. Use the layout scope for viewport errors reported there.

```tsx filename="app/layout.tsx"
import type { ReactNode } from 'react'

export const instant = false

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html>
      <body>{children}</body>
    </html>
  )
}
```

Learn more: [Allow blocking route](/docs/messages/blocking-prerender-runtime#allow-blocking-route) for scope selection.

Use either pattern when:

- The short-lived data determines what the segment can display, so there is no meaningful content to show before it resolves.
- You are migrating the route incrementally and intend to accept blocking navigation while deciding how to cache or stream the data.

Choose [Wrap in or move into Suspense](#wrap-in-or-move-into-suspense) when useful content can appear before the cached result, or [Increase the cache lifetime](#increase-the-cache-lifetime) when the data can remain cached longer.

### Trade-off

Navigations to the segment wait for its server render. Choose this when waiting for the short-lived data is part of the intended experience.

### Gotchas

- Setting `instant` to `false` opts out only the segment that exports it. Descendant segments remain validated by their own config or the global default.
- This export does not disable prerendering. The route still prerenders if it can. It only disables instant-navigation validation for the segment.
- This fix does not satisfy `ensureStatic = 'navigation'`. Remove that requirement only if the route is allowed to render at request time.

## Remove the data access

Choose this fix when a fully static route does not need the short-lived cached value. Replace the read with data available during prerendering.

### Patterns

#### Replace the cached value with static data

Remove the call to the cached helper and render a fixed value.

```tsx filename="app/page.tsx"
export const ensureStatic = 'navigation'

export default function Page() {
  const data = 'Static data'
  return <p>{data}</p>
}
```

Learn more: [Remove the data access](/docs/messages/static-route-runtime#remove-the-data-access).

### Trade-off

The route no longer displays updates from the cached source. Every visitor receives the static replacement.

### Gotchas

- Remove every excluded cache access needed by the fully static route. Leaving another short-lived read behind a boundary still violates the requirement.
- For metadata or viewport, use the corresponding static export instead.

## Verifying the fix

After applying a fix, reload the route and navigate to it from another page. Confirm the error clears and the page immediately paints meaningful UI, with any `<Suspense>` fallbacks covering only the regions that stream in. A boundary around the whole page body can pass validation with an empty shell, which defeats the point of an instant navigation.

In [`next dev`](/docs/app/api-reference/cli/next#next-dev-options), the error overlay points at the failing component with file paths and line numbers. When working from a build instead, the default [`next build`](/docs/app/api-reference/cli/next#next-build-options) output is more abbreviated and may combine uncached and runtime causes. Check the lifetimes of cached functions consumed by the reported component. Run `next build --debug-prerender` for full user-frame stack traces and `next build --debug-build-paths /dashboard /settings` to iterate on specific routes.

## Don't want this validation?

Instant-navigation validation runs by default in [Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents) apps.

- **One segment**: add [`export const instant = false`](/docs/app/api-reference/file-conventions/route-segment-config/instant) to the page or layout file. This opts out the segment itself. Child segments are still validated during client navigations.
- **Entire app**: set [`experimental.instantInsights.validationLevel`](/docs/app/api-reference/file-conventions/route-segment-config/instant#configuring-validation-defaults) to `'manual-warning'` in `next.config`. This limits validation to segments that explicitly export `instant`.

These options do not relax `ensureStatic = 'navigation'`. A fully static route must increase the cache lifetime or replace the excluded access. To allow request-time rendering, first [remove the static requirement](/docs/messages/static-route-runtime#remove-the-static-requirement) wherever the route sets it.

See [Ensuring instant navigations](/docs/app/guides/instant-navigation) for the full model.
