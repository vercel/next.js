This error is part of the experimental [`unstable_ensureStatic`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic) API. A page or layout on this route exports `unstable_ensureStatic = 'navigation'`, requiring fully static server output.

During [prerendering](/docs/app/glossary#prerendering), Next.js encountered data in `generateMetadata()` that prevented the route from completing. In development, the error identifies the data as runtime or uncached. During a build, Next.js may report “uncached or runtime data” when it cannot distinguish the cause.

This requirement applies to every segment, including ancestors, metadata, and viewport. Wrapping server work in Suspense or setting `instant = false` does not relax it.

## Runtime data

This variant covers request-specific data from `cookies()`, `headers()`, `params`, `searchParams`, or a short-lived cache.

## Cache the metadata

Choose this fix when the data can be shared across requests. Use the [`use cache`](/docs/app/api-reference/directives/use-cache) directive and a suitable [`cacheLife`](/docs/app/api-reference/functions/cacheLife) profile.

### Patterns

Cache the asynchronous function that reads the data:

```jsx filename="app/page.jsx"
import { cacheLife } from 'next/cache'

export async function generateMetadata() {
  'use cache'
  cacheLife('hours')
  const response = await fetch('https://api.example.com/content')
  const data = await response.json()
  return { title: data.title }
}

export default function Page() {
  return <h1>My page</h1>
}
```

### Trade-off

Visitors share the cached result until it is revalidated. Choose a lifetime that matches how stale this content may be.

### Gotchas

- Caching does not make request-specific cookies, headers, or search parameters static. Moving their reads outside a cached function still requires per-request server work.
- Remove [`connection()`](/docs/app/api-reference/functions/connection) if it was only forcing an otherwise cacheable operation to run per request. If per-request work is required, [remove the static requirement](#dont-want-this-validation) instead.

### Short-lived caches

An existing cache can also cause this error. For fully static navigation, its `expire` must be at least 300 seconds, `stale` at least 30 seconds, and `revalidate` greater than zero. Increase the lifetime only if serving shared, older content is acceptable. Otherwise, allow request-time rendering.

## Use static metadata

Choose this fix when the metadata does not need request-specific or uncached data.

### Patterns

Keep `generateMetadata()` and replace the dynamic data access with values that can be prerendered:

```jsx filename="app/dashboard/layout.jsx"
export function generateMetadata() {
  return { title: 'My page' }
}

export default function Layout({ children }) {
  return <section>{children}</section>
}
```

### Trade-off

The returned metadata is determined during prerendering rather than per request.

### Gotchas

- If every value is fixed, a static [`metadata`](/docs/app/api-reference/functions/generate-metadata#metadata-object) export is equivalent and may be simpler.
- This fixes the metadata only. Page content and other segments must also satisfy the fully static requirement.

## Provide static parameters

Choose this fix when the route reads dynamic [`params`](/docs/app/api-reference/file-conventions/page#params-optional).

### Patterns

Return at least one complete parameter set from [`generateStaticParams()`](/docs/app/api-reference/functions/generate-static-params). For example, a page at `app/blog/[slug]/page.jsx` can export:

```jsx filename="app/blog/[slug]/page.jsx"
export function generateStaticParams() {
  return [{ slug: 'hello' }]
}

export default async function Page({ params }) {
  const { slug } = await params
  return <h1>{slug}</h1>
}
```

### Trade-off

The returned paths are prerendered at build time. Other parameter values wait for a blocking prerender before Next.js serves their static output.

### Gotchas

- Include every dynamic parameter, including parameters that are unused or only read by Client Components. An empty array does not satisfy this requirement.
- This fixes parameter access only. It does not make cookies, headers, or server-side search parameters static.

## Other options

### Extend the cache lifetime

Choose this fix when the value already uses [`use cache`](/docs/app/api-reference/directives/use-cache), but its lifetime excludes it from prerendering. Short-lived caches can surface as runtime data in this error.

#### Patterns

Use a longer [`cacheLife`](/docs/app/api-reference/functions/cacheLife) profile in the existing cached function:

```jsx filename="app/data.js"
import { cacheLife } from 'next/cache'

export async function getContent() {
  'use cache'
  cacheLife('hours')
  const response = await fetch('https://api.example.com/content')
  return response.json()
}
```

#### Trade-off

Visitors share cached content for longer. If the data must stay fresher than these limits allow, [remove the fully static requirement](#dont-want-this-validation) instead.

#### Gotchas

- For fully static navigation, `expire` must be at least 300 seconds, `stale` at least 30 seconds, and `revalidate` greater than zero. Check nested cached functions too.
- Extending a cache lifetime does not make cookies, headers, or server-side search parameters static.

## Verifying the fix

After applying a fix, reload the route in [`next dev`](/docs/app/api-reference/cli/next#next-dev-options) and confirm that this error no longer appears in the dev overlay. Then run [`next build`](/docs/app/api-reference/cli/next#next-build-options) and confirm that the route completes prerendering.

The default build output is abbreviated. Run `next build --debug-prerender` for full user-frame stack traces and `next build --debug-build-paths /dashboard /settings` to iterate on specific routes.

## Why `instant = false` does not clear this error

The route explicitly requires fully static server output. This is separate from instant-navigation validation. Changing `instant` or `experimental.instantInsights.validationLevel` cannot remove that requirement. If the route needs per-request server work, [remove this validation](#dont-want-this-validation).

## Don't want this validation?

`unstable_ensureStatic = 'navigation'` is an explicit opt-in. It was likely added because this route must avoid per-request server work, so keep it when fully static output is part of the route's contract.

If request-time server data is intentional and you do not need that guarantee, remove the export from each page or layout on the route that sets it. The route then follows the ordinary [Cache Components](/docs/app/getting-started/caching) rendering rules. Removing the export allows per-request server work; it does not disable the separate instant-navigation validation.
