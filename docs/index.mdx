Everything should pass through your backend.

Bad:

   ↓

   ↓

Your secret API keys remain on your server.

10. GPU / Cloud Processing

There are actually two different approaches.

Approach A — API-first

You don't operate GPUs initially.

YOUR SERVER
     ↓
AI API
     ↓
Provider's GPU
     ↓
Generated result

This is the easiest way to launch.

Approach B — Your own GPUs

Later:

YOUR SERVER
     ↓
GPU QUEUE
     ↓
NVIDIA GPU
     ↓
AI MODEL
     ↓
Generated result

You might eventually use:

NVIDIA L40S
NVIDIA A100
NVIDIA H100
NVIDIA H200

depending on workload and model requirements.

11. Why you need a queue

This is critical.

Imagine 1,000 users click:

Generate Video

at the same time.

Don't do:

1,000 requests
      ↓
1,000 GPU jobs

Instead:

1,000 requests
      ↓
      QUEUE
      ↓
Job 1
Job 2
Job 3
Job 4
...
Job 1000

Use something like:

Redis
+
BullMQ

Your workers then process jobs according to capacity.

17. Prompt compiler

This is another important component.

User selects:

Camera = Sony A1
Lens = 85mm
Movement = Dolly In
Lighting = Golden Hour
Film = 35mm
Ratio = 9:16

Your backend creates:

{
  subject: "...",
  environment: "...",
  camera: {
    body: "Sony A1",
    lens: "85mm",
    movement: "dolly_in"
  },
  lighting: "golden_hour",
  visual_style: "35mm_film",
  aspect_ratio: "9:16"
}

Then your prompt engine turns that into the model-specific request.

This lets you support different AI models without changing your entire UI.

23. Most important part: AI provider abstraction

Don't write your application like this:

if video:
   call provider X

Instead:

AIProvider
   │
   ├── ImageProvider
   ├── VideoProvider
   ├── EditProvider
   └── UpscaleProvider

Then:

VideoProvider
   │
   ├── Provider A
   ├── Provider B
   ├── Provider C
   └── Provider D

This means if one AI company changes its API or pricing, you can replace it without rebuilding your whole application.
