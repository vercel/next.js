Handle expected errors as return values and unexpected errors with error boundaries. Show expected errors where the user can resolve them, and use the closest error boundary for uncaught exceptions.

## Handling expected errors

Expected errors can occur during normal application operation, such as validation errors or failed requests. Return expected errors as values so the interface can display them without activating an error boundary.

### Server Components

In a Server Component, check a failed request and render an error message where the data would appear:

```tsx filename="app/page.tsx" switcher
export default async function Page() {
  const res = await fetch('https://api.vercel.app/posts/1')

  if (!res.ok) {
    return <p>Failed to load this post.</p>
  }

  const post = await res.json()
  return <h1>{post.title}</h1>
}
```

```jsx filename="app/page.js" switcher
export default async function Page() {
  const res = await fetch('https://api.vercel.app/posts/1')

  if (!res.ok) {
    return <p>Failed to load this post.</p>
  }

  const post = await res.json()
  return <h1>{post.title}</h1>
}
```

This keeps the rest of the page available. If rendering cannot continue after an unexpected failure, throw an error instead. The nearest error boundary will render its fallback.

## Handling uncaught exceptions

Uncaught exceptions are unexpected errors that indicate bugs or issues that should not occur during the normal flow of your application. Throw these errors so the nearest error boundary can render a fallback.

### Route-segment error boundaries

Next.js uses error boundaries to handle uncaught exceptions. Error boundaries catch errors in their child components and display a fallback UI instead of the component tree that crashed.

Create an error boundary by adding an [`error.js`](/docs/app/api-reference/file-conventions/error) file inside a route segment and exporting a React component:

```tsx filename="app/dashboard/error.tsx" switcher
'use client' // Error boundaries must be Client Components

import { useEffect } from 'react'

export default function ErrorPage({
  error,
  retry,
}: {
  error: Error & { digest?: string }
  retry: () => void
}) {
  useEffect(() => {
    // Log the error to an error reporting service
    console.error(error)
  }, [error])

  return (
    <div>
      <h2>Something went wrong!</h2>
      <button
        onClick={
          // Attempt to recover by re-fetching and re-rendering the segment
          () => retry()
        }
      >
        Try again
      </button>
    </div>
  )
}
```

```jsx filename="app/dashboard/error.js" switcher
'use client' // Error boundaries must be Client Components

import { useEffect } from 'react'

export default function ErrorPage({ error, retry }) {
  useEffect(() => {
    // Log the error to an error reporting service
    console.error(error)
  }, [error])

    <div>
      <h2>Something went wrong!</h2>
      <button
        onClick={
          // Attempt to recover by re-fetching and re-rendering the segment
          () => retry()
        }
      >
        Try again

  )
}
```

An uncaught exception bubbles to the nearest parent error boundary. Add `error.tsx` files at different levels in the [route hierarchy](/docs/app/getting-started/project-structure#component-hierarchy) to control how much of the interface the fallback replaces.

Server Component error messages are redacted in production to avoid exposing sensitive details. Show a user-facing message in the fallback and use `error.digest` to match the error with server-side logs.

### Component-level error boundaries

An `error.js` file replaces the route segment it covers. When one part of a page can fail independently, use [`catchError`](/docs/app/api-reference/functions/catchError) to keep the rest of the page available. Create a reusable error boundary with a user-facing title and a retry button:

```tsx filename="components/ui/error-boundary.tsx" switcher
'use client'

import { catchError, type ErrorInfo } from 'next/error'

function ErrorFallback(
  { title = 'Something went wrong' }: { title?: string },
  { retry }: ErrorInfo
) {
  return (
    <div>
      <p>{title}</p>
      <button onClick={() => retry()}>Try again</button>
    </div>
  )
}

export default catchError(ErrorFallback)
```

```jsx filename="components/ui/error-boundary.js" switcher
'use client'

import { catchError } from 'next/error'

function ErrorFallback({ title = 'Something went wrong' }, { retry }) {
  return (
    <div>
      <p>{title}</p>
      <button onClick={() => retry()}>Try again</button>
    </div>
  )
}

export default catchError(ErrorFallback)
```

Wrap the smallest Server Component subtree that can fail. Pair the error boundary with [`<Suspense>`](https://react.dev/reference/react/Suspense) when the subtree also suspends while loading:

```tsx filename="app/posts/[id]/page.tsx" switcher
import { Suspense } from 'react'
import ErrorBoundary from '@/components/ui/error-boundary'
import { Replies, RepliesSkeleton } from './replies'

export default function Page() {
  return (
    <ErrorBoundary title="Replies didn't load">
      <Suspense fallback={<RepliesSkeleton />}>
        <Replies />
      </Suspense>
    </ErrorBoundary>
  )
}
```

```jsx filename="app/posts/[id]/page.js" switcher
import { Suspense } from 'react'
import ErrorBoundary from '@/components/ui/error-boundary'
import { Replies, RepliesSkeleton } from './replies'

export default function Page() {
  return (
    <ErrorBoundary title="Replies didn't load">
      <Suspense fallback={<RepliesSkeleton />}>
        <Replies />
      </Suspense>
    </ErrorBoundary>
  )
}
```

`<Suspense>` displays `RepliesSkeleton` while `Replies` loads. If `Replies` throws, `ErrorBoundary` replaces only the replies with its error fallback. The rest of the page stays interactive.

In production, Next.js redacts Server Component error messages to avoid exposing sensitive details. Pass a user-facing title to the error boundary instead of rendering `error.message`. The `retry()` function re-fetches and re-renders the boundary's children, including Server Components.

`catchError` handles uncaught exceptions while allowing `notFound()` and `redirect()` to continue to their Next.js handlers. See the [`catchError` API reference](/docs/app/api-reference/functions/catchError) for the difference between `retry()` and `reset()`.

## Handling errors in mutations

Show form submission errors in the form, next to a related field when applicable. For mutation failures that are not tied to a specific field, use a toast or another local notification. Return these expected errors from Server Functions so the interface can display them where the mutation was invoked.

### Displaying inline errors

Use [`useActionState`](https://react.dev/reference/react/useActionState) to display an expected [Server Function](https://react.dev/reference/rsc/server-functions) error next to the form that caused it. Return an error value from the Server Function instead of throwing it:

```ts filename="app/actions.ts" switcher
'use server'

export type FormState = {
  message: string
}

export async function createPost(
  _prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const title = formData.get('title')
  const content = formData.get('content')

  const res = await fetch('https://api.vercel.app/posts', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ title, content }),
  })

  if (!res.ok) {
    return { message: 'Failed to create post' }
  }

  return { message: '' }
}
```

```js filename="app/actions.js" switcher
'use server'

  const content = formData.get('content')
```

Pass the Server Function to `useActionState`, then use the returned state to display the message:

```tsx filename="app/ui/form.tsx" switcher
'use client'

import { useActionState } from 'react'
import { createPost, type FormState } from '@/app/actions'

const initialState: FormState = {
  message: '',
}

export function Form() {
  const [state, formAction, pending] = useActionState(createPost, initialState)

  return (
    <form action={formAction}>
      <label htmlFor="title">Title</label>
      <input type="text" id="title" name="title" required />
      <label htmlFor="content">Content</label>
      <textarea id="content" name="content" required />
      {state?.message && <p aria-live="polite">{state.message}</p>}
      <button disabled={pending}>Create Post</button>
    </form>
  )
}
```


The `aria-live` attribute announces the message to assistive technology. Keep validation errors near the related input so the user has the context needed to resolve them.

Forms invoke Server Actions inside a Transition. If `createPost` throws an unexpected error instead of returning a message, React forwards it to the nearest error boundary.

### Displaying toast notifications

Use a toast when a mutation fails but the user can continue working in the current interface. The Server Function should return a result that distinguishes success from an expected failure:

```ts filename="app/actions.ts" switcher
'use server'

type SavePostResult = { ok: true } | { ok: false; error: string }

export async function savePost(postId: string): Promise<SavePostResult> {
  const res = await fetch(`https://api.vercel.app/posts/${postId}`, {
    method: 'PATCH',
  })

  if (!res.ok) {
    return { ok: false, error: 'Failed to save post' }
  }

  return { ok: true }
}
```

```js filename="app/actions.js" switcher
'use server'

export async function savePost(postId) {
  const res = await fetch(`https://api.vercel.app/posts/${postId}`, {
    method: 'PATCH',
  })

  if (!res.ok) {
    return { ok: false, error: 'Failed to save post' }
  }

  return { ok: true }
}
```

An event handler does not start a Transition automatically. Use `useTransition` to call the Server Function, then show its returned error in a toast:

```tsx filename="app/ui/save-button.tsx" switcher
'use client'

import { useTransition } from 'react'
import { savePost } from '@/app/actions'
import { toast } from '@/app/ui/toast'

export function SaveButton({ postId }: { postId: string }) {
  const [isPending, startTransition] = useTransition()

  return (
    <button
      disabled={isPending}
      onClick={() => {
        startTransition(async () => {
          const result = await savePost(postId)
          if (!result.ok) toast.error(result.error)
        })
      }}
    >
      Save
    </button>
  )
}
```

```jsx filename="app/ui/save-button.js" switcher
'use client'

    </button>

```

The `toast` import represents your application's notification API because Next.js does not include a toast component. Use a notification implementation with an ARIA live region so assistive technology announces the error.

Place the mutating interface beneath a [component-level](#component-level-error-boundaries) or [route-segment](#route-segment-error-boundaries) error boundary. The returned result handles the expected save failure. If `savePost` throws an unexpected error, leave it uncaught. Because the Server Function runs inside a Transition, React forwards the error to the nearest boundary, which displays its fallback.

## Not found

When a route cannot continue because a resource is missing, call [`notFound`](/docs/app/api-reference/functions/not-found) and use a [`not-found.js`](/docs/app/api-reference/file-conventions/not-found) file to show a 404 UI.

```tsx filename="app/blog/[slug]/page.tsx" switcher
import { notFound } from 'next/navigation'
import { getPostBySlug } from '@/lib/posts'

export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const post = getPostBySlug(slug)

  if (!post) {
    notFound()
  }

  return <div>{post.title}</div>
}
```

```jsx filename="app/blog/[slug]/page.js" switcher
import { notFound } from 'next/navigation'
import { getPostBySlug } from '@/lib/posts'

export default async function Page({ params }) {
  const { slug } = await params
  const post = getPostBySlug(slug)

  if (!post) {
    notFound()
  }

  return <div>{post.title}</div>
}
```

```tsx filename="app/blog/[slug]/not-found.tsx" switcher
export default function NotFound() {
  return <div>404 - Page Not Found</div>
}
```

```jsx filename="app/blog/[slug]/not-found.js" switcher
export default function NotFound() {
  return <div>404 - Page Not Found</div>
}
```

> **Good to know:** The `notFound()` and `redirect()` functions stop rendering by throwing a Next.js error. Call them outside `try`/`catch` blocks when possible. If a catch block may receive these errors, call [`unstable_rethrow(error)`](/docs/app/api-reference/functions/unstable_rethrow) at the start of the catch block.

## Global errors

Use a [`global-error.js`](/docs/app/api-reference/file-conventions/error#global-error) file to handle errors in the root layout, including when using [internationalization](/docs/app/guides/internationalization). Global error UI must define its own `<html>` and `<body>` tags because it replaces the root layout or template when active.

```tsx filename="app/global-error.tsx" switcher
'use client' // Error boundaries must be Client Components

export default function GlobalError({
  error,
  retry,
}: {
  error: Error & { digest?: string }
  retry: () => void
}) {
  return (
    // global-error must include html and body tags
    <html>
      <body>
        <h2>Something went wrong!</h2>
        <button onClick={() => retry()}>Try again</button>
      </body>
    </html>
  )
}
```

```jsx filename="app/global-error.js" switcher
'use client' // Error boundaries must be Client Components

export default function GlobalError({ error, retry }) {
  return (
    // global-error must include html and body tags
    <html>
      <body>
        <h2>Something went wrong!</h2>
        <button onClick={() => retry()}>Try again</button>
      </body>
    </html>
  )
}
```
