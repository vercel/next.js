You navigate between routes with the [`<Link>` component](/docs/app/getting-started/layouts-and-pages#linking-between-pages), or with [`useRouter`](/docs/app/api-reference/functions/use-router) when the navigation happens from code. Both perform a client-side transition instead of a full page load.

This page explains how navigation works in Next.js, and what to do when a transition still feels slow.

## Navigating from code

When a navigation is the result of something other than a click on a link, such as a successful form submission or a redirect after checking a condition, use the [`useRouter`](/docs/app/api-reference/functions/use-router) hook from a Client Component:

```tsx filename="app/ui/checkout-button.tsx" switcher
'use client'

import { useRouter } from 'next/navigation'

export default function CheckoutButton() {
  const router = useRouter()

  return (
    <button type="button" onClick={() => router.push('/checkout')}>
      Checkout
    </button>
  )
}
```

```jsx filename="app/ui/checkout-button.js" switcher
'use client'

import { useRouter } from 'next/navigation'

export default function CheckoutButton() {
  const router = useRouter()

  return (
    <button type="button" onClick={() => router.push('/checkout')}>
      Checkout
    </button>
  )
}
```

`router.push` adds a history entry, `router.replace` navigates without adding one, and `router.back` returns to the previous entry.

Prefer `<Link>` when the destination is known while rendering. A link is a real anchor, so it works before JavaScript loads, it can be opened in a new tab, and it gets prefetched. `useRouter` can do none of that until the component has hydrated.

To navigate from a Server Function after a mutation, use [`redirect`](/docs/app/getting-started/mutating-data#redirect-after-a-mutation) instead.

## How navigation works

Three things work together to keep navigation fast, and the rest of this page is about them:

- [Prefetching](#prefetching) loads a route before the click
- [Streaming](#streaming) sends a dynamic route in pieces
- [Client-side transitions](#client-side-transitions) avoid a full page load

When a route is rendered ahead of the request rather than per request, there is less to wait for. [Rendering model](/docs/app/getting-started/rendering-model) covers what decides that.

### Prefetching

Prefetching is the process of loading a route in the background before the user navigates to it. This makes navigation between routes in your application feel instant, because by the time a user clicks on a link, the data to render the next route is already available client side.

Next.js automatically prefetches routes linked with the [`<Link>` component](/docs/app/api-reference/components/link) when they enter the user's viewport.

```tsx filename="app/layout.tsx" switcher
import Link from 'next/link'

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <nav>
          {/* Prefetched when the link is hovered or enters the viewport */}
          <Link href="/blog">Blog</Link>
          {/* No prefetching */}
          <a href="/contact">Contact</a>
        </nav>
        {children}
      </body>
    </html>
  )
}
```

```jsx filename="app/layout.js" switcher
import Link from 'next/link'

export default function Layout({ children }) {
  return (
    <html>
      <body>
        <nav>
          {/* Prefetched when the link is hovered or enters the viewport */}
          <Link href="/blog">Blog</Link>
          {/* No prefetching */}
          <a href="/contact">Contact</a>
        </nav>
        {children}
      </body>
    </html>
  )
}
```

How much of the route is prefetched depends on whether it's static or dynamic:

- **Static Route**: the full route is prefetched.
- **Dynamic Route**: prefetching is skipped, unless [`loading.tsx`](/docs/app/api-reference/file-conventions/loading) is present, in which case the shared layouts and the loading UI are prefetched and the rest is left for the request.

Holding back on dynamic routes keeps the server from rendering pages nobody visits. The cost is that a click may still wait on a response, which can read as the app not responding.

To improve the navigation experience to dynamic routes, you can use [streaming](#streaming).

### Streaming

Streaming allows the server to send parts of a dynamic route to the client as soon as they're ready, rather than waiting for the entire route to be rendered. This means users see something sooner, even if parts of the page are still loading. See the [Streaming guide](/docs/app/guides/streaming) for a deep dive into how streaming works in Next.js.

For a dynamic route, this is what makes a partial prefetch useful: the shared layouts and the loading skeleton can be fetched ahead of the click, and the page content streams in after it.

```tsx filename="app/dashboard/loading.tsx" switcher
export default function Loading() {
  // Add fallback UI that will be shown while the route is loading.
  return <LoadingSkeleton />
}
```

```jsx filename="app/dashboard/loading.js" switcher
export default function Loading() {
  // Add fallback UI that will be shown while the route is loading.
  return <LoadingSkeleton />
}
```

Behind the scenes, Next.js will automatically wrap the `page.tsx` contents in a `<Suspense>` boundary. The prefetched fallback UI will be shown while the route is loading, and swapped for the actual content once ready.

> **Good to know**: You can also use [`<Suspense>`](https://react.dev/reference/react/Suspense) to create loading UI for nested components.

Benefits of `loading.tsx`:

- Immediate navigation and visual feedback for the user.
- Shared layouts remain interactive and navigation is interruptible.
- Improved Core Web Vitals: [TTFB](https://web.dev/articles/ttfb), [FCP](https://web.dev/articles/fcp), and [TTI](https://web.dev/articles/tti).

To further improve the navigation experience, Next.js performs a [client-side transition](#client-side-transitions) with the `<Link>` component.

### Client-side transitions

Traditionally, navigation to a server-rendered page triggers a full page load. This clears state, resets scroll position, and blocks interactivity.

Next.js avoids this with client-side transitions using the `<Link>` component. Instead of reloading the page, it updates the content dynamically by:

- Keeping any shared layouts and UI.
- Replacing the current page with the prefetched loading state or a new page if available.

Client-side transitions make server-rendered apps _feel_ like client-rendered apps. And when paired with [prefetching](#prefetching) and [streaming](#streaming), they enable fast transitions, even for dynamic routes.

Next.js also handles [scrolling to the top of the page](/docs/app/api-reference/components/link#scroll) during client-side transitions. If content scrolls behind a sticky or fixed header after navigation, you can fix this with CSS [`scroll-padding-top`](/docs/app/api-reference/components/link#scroll-offset-with-sticky-headers).

## Keeping transitions fast

The three mechanisms above are automatic. Two things are left to you, and both are about what the user sees while a dynamic route is still on its way.

### Give dynamic routes a `loading.tsx`

A dynamic route has nothing to prefetch until it renders, so without a loading file the click waits on the server with no visible change. Adding `loading.tsx` gives the router something to show immediately, and lets the shared layouts and skeleton be prefetched:

```tsx filename="app/blog/[slug]/loading.tsx" switcher
export default function Loading() {
  return <LoadingSkeleton />
}
```

```jsx filename="app/blog/[slug]/loading.js" switcher
export default function Loading() {
  return <LoadingSkeleton />
}
```

> **Good to know**: In development mode, you can use the Next.js Devtools to identify if the route is static or dynamic. See [`devIndicators`](/docs/app/api-reference/config/next-config-js/devIndicators) for more information.

### Acknowledge the click itself

On a slow or unstable network a prefetch may not finish before the click, which affects static and dynamic routes alike. The `loading.tsx` fallback cannot appear yet either, because it has not arrived.

Something still has to respond. The [`useLinkStatus` hook](/docs/app/api-reference/functions/use-link-status) reports that a transition is in progress, so you can show feedback on the link the user actually pressed:

```tsx filename="app/ui/loading-indicator.tsx" switcher
'use client'

import { useLinkStatus } from 'next/link'

export default function LoadingIndicator() {
  const { pending } = useLinkStatus()
  return (
    <span aria-hidden className={`link-hint ${pending ? 'is-pending' : ''}`} />
  )
}
```

```jsx filename="app/ui/loading-indicator.js" switcher
'use client'

import { useLinkStatus } from 'next/link'

export default function LoadingIndicator() {
  const { pending } = useLinkStatus()
  return (
    <span aria-hidden className={`link-hint ${pending ? 'is-pending' : ''}`} />
  )
}
```

You can "debounce" the hint by adding an initial animation delay (e.g. 100ms) and starting as invisible (e.g. `opacity: 0`). This means the loading indicator will only be shown if the navigation takes longer than the specified delay. See the [`useLinkStatus` reference](/docs/app/api-reference/functions/use-link-status#gracefully-handling-fast-navigation) for a CSS example.

> **Good to know**: An **experimental** [`useOffline`](/docs/app/api-reference/config/next-config-js/useOffline) hook can keep prefetched routes navigable during connectivity drops. See the [offline support guide](/docs/app/guides/offline-support).

> **Good to know**: You can use other visual feedback patterns like a progress bar. View an example [here](https://github.com/vercel/react-transition-progress).

## Going further

- **Control what gets prefetched.** Deferring a prefetch until hover, disabling it on a long list, or triggering one yourself are all covered in the [Prefetching guide](/docs/app/guides/prefetching), along with [Partial Prefetching](/docs/app/guides/adopting-partial-prefetching).
- **Prerender the dynamic segments you know about.** Listing them with `generateStaticParams` puts the concrete pages in the shell, and any URL you did not list is served the App Shell and upgraded afterward. See [Dynamic params and the App Shell](/docs/app/getting-started/rendering-model#dynamic-params-and-the-app-shell).
- **Update the URL without navigating.** For sorting, filtering, and other state you want in the address bar, see [Shallow routing on the client](/docs/app/guides/single-page-applications#shallow-routing-on-the-client).
