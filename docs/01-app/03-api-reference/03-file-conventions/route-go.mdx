`route.go` defines a native Go Route Handler (API endpoint) in the App Router, served through the existing Next.js Node.js server by default. A production Go public server is also available through `experimental.goServer`.

```go filename="app/users/[id]/route.go" highlight={9}
package main

import (
  "fmt"
  "net/http"
)

var Methods = []string{"GET"}
func Handle(w http.ResponseWriter, r *http.Request) {
  fmt.Fprintf(w, "User %s", r.PathValue("id"))
}
```

Enable the experiment:

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: { goRoutes: true },
}

export default nextConfig
```

```js filename="next.config.js" switcher
module.exports = {
  experimental: { goRoutes: true },
}
```

Install Go 1.24 or newer on `PATH`, or set `TURBOPACK_GO` to its executable path. Go is required for `next dev` and `next build` when compiling native handlers. `next start` launches the compiled executables without invoking the compiler.

## Reference

### Handler convention

Each route directory is an executable `package main`. Define `Methods` as a slice of supported HTTP method names and `Handle` with the signature shown above. Next.js generates the `main` function. Do not define one yourself or create `zz_next_route_main.go`, which is reserved for the generated wrapper.

All sibling `.go` files except `_test.go` are compiled together with `route.go`. Their package must also be `main`. These are explicit filename inputs: platform filename suffixes and build constraints do not select sibling files. Put platform-dependent implementations in imported packages, where Go applies its normal selection rules. Shared packages can use ordinary module imports, including `internal` packages. Direct `go run` and `go test` do not inject the generated wrapper or `ParamValues` helper; use Next.js to run the route integration. Brackets and parentheses in route directory names do not need Go import paths.

Native routes support `app` and `src/app`, [route groups](/docs/app/api-reference/file-conventions/route-groups), and [dynamic segments](/docs/app/api-reference/file-conventions/dynamic-routes). A native handler cannot share its URL with another Route Handler or page.

### HTTP methods

`Handle` receives the actual request method. Use a switch on `r.Method` to implement different behavior.

| Method                         | Behavior                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Methods in `Methods`           | Invoke `Handle`.                                                                                      |
| `HEAD` when `GET` is supported | Invoke `Handle` with `r.Method == "HEAD"`. The HTTP server suppresses response body bytes.            |
| `OPTIONS`                      | Automatically return `204` and an `Allow` header. Custom OPTIONS handling is not supported initially. |
| Unsupported methods            | Return `405`.                                                                                         |

### Parameters and HTTP data

| API                                          | Behavior                                                                                     |
| -------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `r.PathValue("id")`                          | Read a decoded dynamic parameter. Catch-all segments are joined with `/`.                    |
| `ParamValues(r, "slug")`                     | Read individual decoded catch-all segments. This helper is generated into the route package. |
| `r.URL.Query()`                              | Read query parameters, including repeated values.                                            |
| `r.Header`, `r.Cookie()`                     | Read incoming headers and cookies after Next.js proxy processing.                            |
| `r.Body`                                     | Read the streamed request body.                                                              |
| `w.Header()`, `w.WriteHeader()`, `w.Write()` | Set response headers, status and body using `net/http`.                                      |
| `http.Flusher`                               | Flush streamed response bytes.                                                               |
| `r.Context().Done()`                         | Observe cancellation when the client disconnects.                                            |

Next.js selects the endpoint after its existing routing, rewrites and `proxy.ts` processing. The native executable receives only the selected request and does not run a second router. JS/TS handlers, React rendering, Pages Router pages and static assets continue to use Node.js.

### Development and errors

Turbopack tracks direct sources, sibling files, local imported packages, module metadata, and embedded assets. Edits rebuild through the Go compiler graph. Requests ensure current compilation before invoking a native process. Compiler failures produce errors instead of serving the previous successful executable; repairing the source allows later requests to recover.

A compiled executable runs as a supervised process with pooled private loopback HTTP connections. Unchanged requests reuse it. A successful rebuild starts a replacement when the route is next invoked. Previously admitted requests can complete on the old process, with a 21-second retirement limit. Route removal and server shutdown retire workers. A child crash fails its active request; later requests restart the emitted executable. A startup failure remains failed for that executable generation until its source changes or the Next.js server restarts. A handler panic aborts its HTTP connection, resulting in an error response if response headers have not already been sent.

## Go public server (production)

Set `experimental.goServer: true` to use the precompiled Go public frontend and
an independently compiled application Go plugin. This also enables `goRoutes`.

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const config: NextConfig = {
  experimental: { goServer: true },
}

export default config
```

Run `next build` with Turbopack, then `next start`. The shipped frontend owns the
public port and calls native handlers in a separately compiled Go plugin loaded
once at startup. Handlers run in the frontend process without a worker transport.
Node is not in the native request path.
The frontend executable contains no application imports; routing and plugin
registration are loaded from a build manifest. Requests for other routes,
public assets and Next.js internals are forwarded to a private Node listener.
JavaScript handlers, React rendering and Pages Router routes still run in Node.
Static route priority prevents a dynamic Go route from intercepting a more
specific JavaScript route or a public asset.

Direct Go requests **bypass JavaScript `proxy.ts`, rewrites, redirects and custom
headers**. These features apply to the Node fallback only. Node rewrites cannot
invoke a Go handler; Go routes must be addressed through their direct public URL.
The Go listener supports `basePath`, dynamic and catch-all parameters, and
`trailingSlash` normalization. It does not implement the full Next.js router yet.

This first frontend version supports production build/start only. `next dev`
reports an unsupported-mode error when `goServer` is enabled. Use `goRoutes`
without `goServer` for the existing development handler workflow. A `go.mod` at
the application root is required for composing native packages. Handler sources
remain `package main`; generated package overlays preserve local imports,
`internal` visibility and embedded assets without editing source files. Go applies
normal filename and build-tag selection to these imported handler packages.
`zz_next_route_params.go` and `nextgenerated/` are reserved for generated inputs.

Native handlers share the frontend process, runtime and heap. Plugins are trusted
application code with the frontend's privileges; they provide no process isolation.
A handler panic aborts its HTTP connection. Exiting the process or a fatal runtime
error terminates the frontend, and Node shuts down as well. Requests are not
automatically replayed. Deployment replacement starts a new generation and drains
the previous generation; live development replacement is not enabled. On normal shutdown, the public listener stops accepting requests,
drains in-flight work for up to 20 seconds, then closes the Node fallback.

Linux with glibc and macOS on x64/arm64 are supported. Linux/musl is unsupported. Windows and other platforms are not
supported by `goServer`. Public transport is HTTP/1.1; terminate TLS in front of the
server. Request bodies, streamed responses, trailers and HTTP/1.1 upgrades use a
bounded streaming path. Native requests use the strict framing/streaming path with direct in-process
handler calls. Eligible fixed-length Node responses use the readiness loop. HTTP/1.0, direct TLS/HTTP/2 and ambiguous framing are rejected.
Dot segments, backslashes, control characters and internal empty path segments
are rejected; encoded slashes remain inside one route parameter.

Forwarded identity is rebuilt from the socket peer by default. Set
`NEXT_GO_TRUSTED_PROXIES` to comma-separated trusted proxy CIDRs to accept validated
forwarded identity. The trusted adjacent proxy must overwrite client-supplied
forwarded host and protocol. Untrusted clients cannot choose a plugin, handler symbol or upstream.

The runtime enforces global socket/buffer/pool budgets, absolute five-second header
and five-minute exchange deadlines, and fifteen-second write inactivity deadlines.
This experimental implementation has focused race, fuzz and differential tests;
these are not a completed HTTP security audit.

The frontend, build configuration and content-addressed plugin are listed in `.next/server/go-server.json` and
`.next/server/go-server.json.nft.json`. Copy the complete build output, preserving
executable permissions, to relocate it to a host with the same OS and architecture.
Production startup checks library build compatibility and reads these descriptors once and does not invoke Go or inspect
application source files on each request.

### Go plugin build compatibility

The application compiler must match the precompiled frontend's **exact Go version**,
including its patch release. Official frontend artifacts use Go 1.27.2. Set
`TURBOPACK_GO` to the matching compiler if necessary. The frontend's build metadata
is checked before application compilation; relevant library build settings and
common-package compatibility are checked again before loading. Plugin linking uses
CGO and requires a native C compiler, even though application dependencies remain
pure Go. Builds use matching trimpath settings and controlled compiler flags.

A plugin is loaded once and cannot be unloaded. Handler changes require a new
frontend process; deployment replacement drains the old generation. Dynamic plugin
race-detector coverage is limited. The default Node-based `goRoutes` mode retains
its Go 1.24+ and CGO-disabled compiler contract.

## Good to know

- This experiment supports Turbopack `next dev` and self-hosted `next build` / `next start`. Webpack produces an unsupported-mode diagnostic.
- Copy the complete `.next` output for relocation on the same OS and architecture. Keep executable permissions on native files under `.next/server/app`. Each native descriptor has a `.native.json.nft.json` trace listing its executable. Static export, standalone output and deployment adapters are unsupported.
- In the default Node-based `goRoutes` mode, WebSocket upgrades and HTTP trailers are not supported initially. The production `goServer` mode supports HTTP/1.1 upgrades and trailers through its streaming path. Native handlers always execute dynamically. JS route segment config, ISR, Server Actions and React execution do not apply to Go handlers.
- Runtime file reads are not traced. Use `go:embed` for assets shipped with native handlers. Native handlers read the process environment; `next.config` environment inlining does not apply.
- Builds use the host platform. The default Node-based mode disables CGO; the public frontend compiles Go plugins with CGO enabled. Pure-Go dependencies must already be downloaded into the selected toolchain's module cache. Builds do not download dependencies or modify `go.mod` / `go.sum`.
- Go workspaces, module replacements, vendoring, source symlinks and cross-compilation inherit the compiler experiment's unsupported status.
- `experimental.goRoutes` disables Turbopack's persistent task cache for this process. Go's build cache still persists, and unchanged compiler results are memoized during the session.
- The initial convention does not add `proxy.go`, Go Pages API routes, `page.go`, or `layout.go`. Applications without native handlers do not require a Go installation.
