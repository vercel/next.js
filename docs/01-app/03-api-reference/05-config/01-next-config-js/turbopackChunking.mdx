By default, Turbopack's chunking is configured as follows:

## Size Thresholds

The following options control how aggressively Turbopack merges client-side chunks and how large
a chunk is allowed to grow. Sizes are in bytes of uncompressed, minified code, because by
default Turbopack minifies each module before chunking. Without minify-before-chunking, sizes
measure unminified code and the defaults are larger, as described below.

- **`minChunkSize`** (default `20000`): Turbopack will avoid creating more
  than one chunk smaller than this size by merging small chunks into larger ones.
  Raising this number will produce fewer, larger chunks. Meanwhile, lowering it
  will produce more chunks that are smaller.
- **`maxChunkCountPerGroup`** (default `40`): Turbopack will not emit more than
  this many chunks per chunk group (eg. a route or a dynamic import). Lowering
  this number will lead to more aggressive merging and less network requests
  per-page. Raising it will produce smaller chunks and increase the likelihood
  of cache hits when navigating.
- **`maxMergeChunkSize`** (default `80000`): Turbopack never merges a chunk
  larger than this size with other chunks. This keeps the code in large chunks
  from being duplicated across multiple large output chunks.
- **`maxChunkSize`** (default `400000`): a best-effort maximum estimated
  client JavaScript chunk size. Turbopack never merges chunks into chunks bigger
  than this, and splits chunks that are bigger on their own into smaller chunks.
  It sorts their modules by identifier and prefers splitting where paths differ
  most (e.g. between two packages), which keeps splits deterministic and helps
  avoid unrelated chunk changes. To stay under the limit, it may create chunks
  smaller than `minChunkSize` or more chunks than `maxChunkCountPerGroup`. A
  single module bigger than this size still produces a bigger chunk. It must be
  at least 3 times `minChunkSize`, and `maxMergeChunkSize` must not be bigger.
  Otherwise, Turbopack increases `maxChunkSize` or decreases
  `maxMergeChunkSize` accordingly, and shows a warning. Set it to `0` to disable
  the limit.

When merging chunks, the trade-off being made is an improvement to performance on initial page
loads at the cost of navigation performance. This is because each additional network request
being made is costly, however, smaller chunks are more likely to be re-usable across pages.

> **Good to know**: The default sizes assume the experimental
> `experimental.turbopackMinifyBeforeChunking` option, which is enabled by default starting in
> Next.js 16.5. With it, Turbopack minifies each module before chunking and measures sizes in
> bytes of minified code. If you set it to `false` (or minification is disabled), Turbopack
> measures unminified code instead, and the default thresholds and `requestCost`, including the
> server chunk thresholds below, are multiplied by 2.5. In
> particular, the default `maxChunkSize` becomes `1000000` and the default `maxServerChunkSize`
> becomes `10000000`. Values you set explicitly (including `0`) are used as-is, so you may need
> to raise them when the option is disabled.

## Server Chunks

The size thresholds above only apply to client-side JavaScript. Server-side JavaScript uses
separate thresholds:

- **`minServerChunkSize`** (default `1600`): Turbopack will avoid creating more than one Node.js
  server chunk smaller than this size by merging small chunks into larger ones, unless the
  maximum chunk size takes precedence.
- **`maxMergeServerChunkSize`** (default `40000`): Turbopack never merges a Node.js server chunk
  larger than this size with other chunks.
- **`maxServerChunkSize`** (default `4000000`): like `maxChunkSize`, but for server (Node.js and
  edge) JavaScript chunks instead of client chunks. For Node.js, it must be at least 3 times
  `minServerChunkSize`, and `maxMergeServerChunkSize` must not be bigger. Otherwise, Turbopack
  increases `maxServerChunkSize` or decreases `maxMergeServerChunkSize` accordingly, and shows a
  warning. Set it to `0` to disable the maximum size limit.

`minServerChunkSize` and `maxMergeServerChunkSize` don't apply to the Edge runtime. Edge uses a
minimum of 8 KB (20 KB without minifying before chunking) and the effective `maxServerChunkSize`
as its merge limit. If its maximum is enabled but below 3 times that minimum (24 KB or 60 KB,
respectively), it is increased with a warning.

```js filename="next.config.js"
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    turbopackChunking: {
      minServerChunkSize: 4000,
      maxMergeServerChunkSize: 80000,
    },
  },
}

module.exports = nextConfig
```

## Component Chunks

Producing component chunks is an experimental feature that aims to give you the initial
page load benefits of merged chunks without sacrificing reusability. This feature lets
the runtime dynamically choose whether to load a merged chunk as a single file, or to
load only the component chunks it doesn't already have. Additionally, chunks that were
already loaded as part of a merged chunk will not be re-downloaded.

This avoids re-downloading JavaScript the browser already has when navigating.

- **`generateComponentChunks`** (default `false`): when enabled, each merged
  production chunk also emits its constituent component chunks alongside it, so
  the browser runtime can fetch individual component chunks.
- **`minComponentChunkSize`** (default `8000`): component chunks smaller than
  this size are folded into a single component instead of being emitted on their own,
  to avoid producing many tiny chunks.

</AppOnly>

## Heuristics

These change the assumptions the chunker makes when weighing whether merging two
chunks is worth it.

- **`clusters`** (an array of arrays of `RegExp`, e.g.
  `[[/^\/dashboard/, /^\/settings/]]`): groups of routes that are commonly
  visited together, matched against the route pathname. Turbopack assumes
  navigations are likely to stay within a cluster, so chunks shared by a
  cluster's routes are merged more eagerly.
- **`firstPageLoadPriority`** (a number between `0` and `1`): how heavily to
  weight the benefit of merging chunks for a single page load. Higher values
  merge more eagerly. If you don't have a better value, your site's bounce rate
  is a good approximation.
- **`priorityRoutes`** (an array of `RegExp`): routes that are often the first
  page a visitor lands on (e.g. the homepage). Their client-side bundles are
  merged more eagerly to reduce the single-route request cost, at the cost of
  extra requests when navigating to other pages.
- **`priorityBoost`** (default `1.5`): a multiplier on the single-request
  probability of `priorityRoutes` routes. Higher values merge those routes'
  bundles more aggressively.
- **`requestCost`** (default `80000`): the estimated cost of an
  additional request, in bytes of uncompressed, minified code. Larger values
  bias toward fewer, larger chunks and fewer requests overall.
