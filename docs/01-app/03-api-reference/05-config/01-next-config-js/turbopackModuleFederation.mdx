The experimental `turbopackModuleFederation` option configures [Module Federation](https://webpack.js.org/concepts/module-federation/) as a first-class Turbopack feature. It uses the [Module Federation enhanced runtime](https://module-federation.io/guide/basic/runtime/runtime-api) by default. Install the optional peer dependency in each app that enables federation:

```bash
pnpm add @module-federation/runtime-tools@^2.9.0
```

Apps without federation do not need this package. An app with federation but no compatible installation receives a build-time error. A host-only app can omit `name` when its `package.json` has a nonempty `name`; exposed containers must specify a name explicitly. Apps sharing a page should use distinct names.

> **Good to know**:
>
> - This option is experimental and only applies when using Turbopack.
> - Federated imports and exposed modules are currently supported in client components. They are not supported in Server Components, Route Handlers, or the Edge runtime.
> - Compared to webpack Turbopack currently supports only `script` remote type and global containers. Other remote and library types are not supported.
> - Changes to a remote or exposed module are available after reloading the browser. Next.js automatically restarts the development server when the federation configuration changes.

## Consuming a remote

Configure each remote using `globalName@url` syntax:

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    turbopackModuleFederation: {
      name: 'storefront',
      remotes: {
        catalog: 'catalog@https://catalog.example.com/remoteEntry.js',
      },
    },
  },
}

export default nextConfig
```

```js filename="next.config.js" switcher
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    turbopackModuleFederation: {
      name: 'storefront',
      remotes: {
        catalog: 'catalog@https://catalog.example.com/remoteEntry.js',
      },
    },
  },
}

module.exports = nextConfig
```

Import the exposed module from a client component:

```tsx filename="app/product.tsx" switcher
'use client'

import dynamic from 'next/dynamic'

const Product = dynamic(() => import('catalog/product'), {
  ssr: false,
  loading: () => <p>Loading</p>,
})

export function ProductBoundary() {
  return <Product />
}
```

```jsx filename="app/product.js" switcher
'use client'

import dynamic from 'next/dynamic'

const Product = dynamic(() => import('catalog/product'), {
  ssr: false,
  loading: () => <p>Loading</p>,
})

export function ProductBoundary() {
  return <Product />
}
```

A remote can be an existing webpack application created with `ModuleFederationPlugin`, or another Next.js application using this option. Remote entries may load additional chunks; Turbopack resolves those chunk URLs relative to the remote entry, including when the producer is hosted on another origin.

The URL after `globalName@` is passed to the runtime loader. It can be an absolute URL, a server-relative URL such as `/remoteEntry.js`, or a `file://` URL when the execution environment supports it. Classic Web Workers are supported; webpack remotes intended for a worker must use a worker-compatible target and chunk loader (for example `target: 'webworker'` with `chunkLoading: 'import-scripts'`). Module workers are not supported yet.

You can provide an ordered list of remote entry URLs. Turbopack tries each entry in order and reports the combined failures if none loads:

```js filename="next.config.js"
module.exports = {
  experimental: {
    turbopackModuleFederation: {
      remotes: {
        catalog: [
          'catalog@https://primary.example.com/remoteEntry.js',
          'catalog@https://fallback.example.com/remoteEntry.js',
        ],
      },
    },
  },
}
```

## Exposing modules

Set a container `name`, a `filename`, and the modules to expose. The unhashed remote entry is served from `/_next/static/<filename>`. Its content-hashed lazy chunks use the isolated `/_next/static/chunks/mf/` directory.

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    turbopackModuleFederation: {
      name: 'catalog',
      filename: 'catalogRemote.js',
      exposes: {
        './product': './app/product.tsx',
      },
    },
  },
}

export default nextConfig
```

```js filename="next.config.js" switcher
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    turbopackModuleFederation: {
      name: 'catalog',
      filename: 'catalogRemote.js',
      exposes: {
        './product': './app/product.js',
      },
    },
  },
}

module.exports = nextConfig
```

The filename defaults to `<name>.js`. It must be a relative path and cannot contain `..`, a query string, or a URL. Exposed modules are loaded lazily from separate chunks.

## Sharing modules

The `shared` option uses webpack-compatible share keys and configuration:

```js filename="next.config.js"
module.exports = {
  experimental: {
    turbopackModuleFederation: {
      name: 'storefront',
      remotes: {
        catalog: 'catalog@https://catalog.example.com/remoteEntry.js',
      },
      shared: {
        react: {
          singleton: true,
          eager: true,
          requiredVersion: '^19.0.0',
        },
      },
    },
  },
}
```

Shared entries support `eager`, `import`, `packageName`, `requiredVersion`, `shareKey`, `shareScope`, `singleton`, `strictVersion`, and `version`. By default, the enhanced runtime uses `shareStrategy: 'version-first'` to initialize configured remotes in a share scope before selecting a compatible provider. Set `shareStrategy: 'loaded-first'` to favor providers that have already loaded, reducing eager network requests but making load order relevant to version selection.

When `requiredVersion` is omitted, Next.js looks for the package in the project's `optionalDependencies`, `dependencies`, `peerDependencies`, and `devDependencies`, in that order. Set `requiredVersion: false` to disable the range constraint. Set `import: false` to require another container to provide the module.

For App Router hosts, a default `react` share uses the same vendored React module as Next's renderer. Set `eager: true` for a singleton React provider that must win over a same-version remote fallback, and have the remote declare React as shared too. Otherwise a remote component using hooks may render with a second React instance and fail with an invalid hook call.

Non-eager shared dependencies are available only in the browser. A static import in a Client Component also runs when Next.js prerenders that component on the server. To import a non-eager shared dependency statically, load the component with `next/dynamic({ ssr: false })`. An eager dependency with a local fallback can be used during prerendering; server and Edge federation consumption itself is not supported.

A key ending in `/` shares package subpaths. For example, `'design-system/'` also matches `design-system/button`.

> **Sharing limitations**:
>
> - Shared version selection and range matching are provided by `@module-federation/runtime-tools`.
> - Shared namespace bindings are copied when crossing from webpack to Turbopack. Later mutations to an exported binding are not observed as a live binding.

## Migrating from webpack

Move the options passed to webpack's `ModuleFederationPlugin` into `experimental.turbopackModuleFederation`:

```js filename="next.config.js"
module.exports = {
  experimental: {
    turbopackModuleFederation: {
      name: 'storefront',
      remotes: {
        catalog: 'catalog@https://catalog.example.com/remoteEntry.js',
      },
      shared: {
        react: { singleton: true, eager: true },
      },
    },
  },
}
```

The webpack `library` and `runtime` plugin options are not supported. Turbopack emits a global container and initializes the enhanced runtime. You can configure `runtimePlugins` as an ordered array of project-relative paths or installed package specifiers, or `[specifier, JSON-serializable options]` tuples. The runtime loads the default export of each module and calls it with the provided options in the browser. Use `implementation` to resolve a compatible runtime-tools implementation from your project instead of the default optional peer; it must provide the `./runtime` and `./webpack-bundler-runtime` entrypoints. A project-relative implementation directory must also have a package.json with a non-empty `name` so Turbopack can resolve those exported entrypoints.

For example, a runtime plugin can observe requests and use the upstream loaded-first strategy:

```js filename="next.config.js"
module.exports = {
  experimental: {
    turbopackModuleFederation: {
      remotes: {
        catalog: 'catalog@https://catalog.example.com/remoteEntry.js',
      },
      shareStrategy: 'loaded-first',
      runtimePlugins: [['./federation-plugin.js', { label: 'storefront' }]],
    },
  },
}
```

```js filename="federation-plugin.js"
module.exports = ({ label }) => ({
  name: 'storefront-observer',
  beforeRequest(args) {
    console.log(label, args.id)
    return args
  },
})
```

## Dynamic remotes and runtime plugins

From a client component, use the installed peer's runtime API to access the same enhanced instance that Turbopack initialized:

```tsx filename="app/dynamic-catalog.tsx"
'use client'

import { getInstance } from '@module-federation/runtime-tools/runtime'

export async function loadCatalog(url: string) {
  const instance = getInstance()
  if (!instance) throw new Error('Federation is not initialized yet')
  instance.registerRemotes([
    {
      name: 'optionalCatalog',
      entry: url,
      entryGlobalName: 'catalog',
      type: 'var',
    },
  ])
  return instance.loadRemote('optionalCatalog/product')
}
```

When multiple federated apps share a page, use `getInstance((instance) => instance.name === 'storefront')` to select your app's instance rather than relying on the no-argument accessor. If you set `implementation: 'custom-runtime'`, import these APIs from `custom-runtime/runtime` instead of the default peer package. Dynamic registration and `loadRemote()` support script entries. Upstream `preloadRemote()` requires a manifest; it does not preload a script-only webpack v1 remote without one.

## Runtime behavior and limitations

- Federation is client-only. Importing a remote from a Server Component, Route Handler, or Edge runtime returns a runtime error explaining that the import must move to browser client code.
- In development, changes to a separately built remote become visible after rebuilding the remote and reloading the browser. Cross-bundler HMR is not propagated.
- Changes to `experimental.turbopackModuleFederation` require restarting the Next.js development server.
- Only webpack's `script` remote transport and global containers are supported. ESM, CommonJS, promise, AMD, UMD, and SystemJS remote transports are rejected.
