---
title: Invoking Entrypoints
description: Invoke JavaScript build handlers and experimental Go HTTP server entrypoints.
---

Node.js and Edge entrypoints use a `handler(..., ctx)` interface, with runtime-specific request/response types. Experimental Go entrypoints are compiled HTTP servers.

## Node.js runtime (`runtime: 'nodejs'`)

Node.js entrypoints use the following interface:

```typescript
handler(
  req: IncomingMessage,
  res: ServerResponse,
  ctx: {
    waitUntil?: (promise: Promise<void>) => void
    requestMeta?: RequestMeta
  }
): Promise<void>
```

When invoking Node.js entrypoints directly, adapters can pass helpers directly on `requestMeta` instead of relying on internals. Some of the supported fields are `hostname`,
`revalidate`, and `render404`:

```ts
await handler(req, res, {
  requestMeta: {
    // Relative path from process.cwd() to the Next.js project directory.
    relativeProjectDir: '.',
    // Optional hostname used by route handlers when constructing absolute URLs.
    hostname: '127.0.0.1',
    // Optional internal revalidate function to avoid revalidating over the network
    revalidate: async ({ urlPath, headers, opts }) => {
      // platform-specific revalidate implementation
    },
    // Optional function to render the 404 page for pages router `notFound: true`
    render404: async (req, res, parsedUrl, setHeaders) => {
      // platform-specific 404 rendering implementation
    },
  },
})
```

## Edge runtime (`runtime: 'edge'`) (deprecated)

> The Edge Runtime is [deprecated](/docs/messages/edge-runtime-deprecated). New routes should use the Node.js runtime.

Edge entrypoints use the following interface:

```typescript
handler(
  request: Request,
  ctx: {
    waitUntil?: (prom: Promise<void>) => void
    signal?: AbortSignal
    requestMeta?: RequestMeta
  }
): Promise<Response>
```

The shape is aligned around `handler(..., ctx)`, but Node.js and Edge runtimes use different request/response primitives.

For outputs with `runtime: 'edge'`, Next.js also provides `output.edgeRuntime` with the canonical metadata needed to invoke the entrypoint:

```typescript
{
  modulePath: string // Absolute path to the module registered in the edge runtime
  entryKey: string // Canonical key used by the edge entry registry
  handlerExport: string // Export name to invoke, currently 'handler'
}
```

After your edge runtime loads and evaluates the chunks for `modulePath`, use `entryKey` to read the registered entry from the global edge entry registry (`globalThis._ENTRIES`), then invoke `handlerExport` from that entry:

```ts
const entry = await globalThis._ENTRIES[output.edgeRuntime.entryKey]
const handler = entry[output.edgeRuntime.handlerExport]
await handler(request, ctx)
```

Use `edgeRuntime` instead of deriving registry keys or handler names from filenames.

## Go runtime (`runtime: 'go'`)

With experimental [`route.go`](/docs/app/api-reference/file-conventions/route-go) handlers, `output.filePath` identifies a native executable rather than a JavaScript module. Package it with the declared `assets` for the target operating system and architecture, preserving executable permissions and the asset destination paths.

Start the executable without arguments, set `PORT` to its assigned HTTP port, and use the packaged function directory as its working directory. The adapter build's executable runs independently of the self-hosted Next.js server: it requires neither a private Next.js token nor a parent-owned stdin pipe. By default, the generated server matches its emitted route pattern and derives decoded dynamic parameters from the request URL.

Platforms that preserve the public URL when rewriting to a Go function must supply the concrete routed pathname separately. Set the function's `NEXT_GO_ADAPTER_ROUTING` environment variable to JSON with `version: 1` and `pathHeader` naming a trusted request header:

```json
{ "version": 1, "pathHeader": "x-platform-route-path" }
```

The adapter must remove caller-supplied values for this header at ingress and replace them with exactly one concrete, escaped pathname after routing, including `basePath`. Send the routed pathname rather than a dynamic route template, and omit its query string and fragment. For example, a public request for `/alias?key=one` rewritten to `/users/a%2Fb` retains `/alias?key=one` as its HTTP request URL while the routing header carries `/users/a%2Fb`.

The server derives parameters from this trusted pathname and removes the routing header before calling `Handle`. `r.URL`, `r.RequestURI`, and the request query reflect the request forwarded by the platform, including any URL normalization it performs. Escaped slashes remain within their original parameter segments. Missing, repeated, or invalid routing headers return `400`; a valid pathname that does not match the emitted route returns `404`. Invalid routing configuration fails server startup. When the environment variable is unset or empty, routing headers have no special meaning and the server continues matching the request URL.

The platform routes requests to the correct Go function and runs its own rewrite and proxy integration. Node.js outputs continue to use their existing handler interface. JavaScript callbacks such as `ctx.waitUntil` cannot be passed to the Go process; the initial server contract provides no completion guarantee for post-response work.
