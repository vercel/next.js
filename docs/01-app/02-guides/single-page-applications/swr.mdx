Use [SWR](https://swr.vercel.app) with Next.js to fetch browser-driven data or seed the SWR cache from a Server Component. SWR owns client revalidation and mutations, while Next.js can cache the server-rendered view.

## Fetching data only on the client

You do not have to seed data from a Server Component. For data whose input is only known after an interaction, such as autocomplete, call `useSWR` directly from a Client Component with a key that includes the input:

```tsx filename="app/product-autocomplete.tsx" switcher
'use client'

import useSWR from 'swr'

type Product = { id: string; name: string }

async function fetcher(url: string): Promise<Product[]> {
  const response = await fetch(url)
  if (!response.ok) throw new Error('Failed to fetch products')
  return response.json()
}

export function ProductAutocomplete({ query }: { query: string }) {
  const {
    data = [],
    error,
    isLoading,
  } = useSWR<Product[]>(query ? `/api/products?q=${query}` : null, fetcher)

  if (error) return <p>Failed to load products.</p>
  if (isLoading) return <p>Loading products...</p>

  return (
    <ul>
      {data.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  )
}
```

The result is not in the server-rendered response, so the first result waits for hydration and a client request. This tradeoff suits interaction-driven data. The Route Handler can still read through a server function that uses Cache Components.

Learn more: [SWR data fetching](https://swr.vercel.app/docs/data-fetching).

## Seeding SWR from a Server Component (optional)

With SWR 2.3.0 and React 19, you can add Server Component data to an existing SWR setup without moving all data fetching to the server. This abstracts the [`use()` pattern](/docs/app/guides/single-page-applications#using-reacts-use-within-a-context-provider), so the same Client Component can read data from the client, the server, or both.

Use SWR when the Client Component needs client-side features, such as focus revalidation, interval revalidation, [`mutate`](https://swr.vercel.app/docs/mutation), or request deduplication across components. If a Client Component only needs to read server data once, pass a Promise to it and unwrap it with [`use()`](/docs/app/guides/single-page-applications#using-reacts-use-within-a-context-provider). That avoids adding a data-fetching library for data that never revalidates on the client.

To provide server data to SWR on the first render, wrap your application in `<SWRConfig>` and provide a `fallback`:

```tsx filename="app/layout.tsx" switcher
import { SWRConfig } from 'swr'
import { getUser } from './user' // some server-side function

export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <SWRConfig
      value={{
        fallback: {
          // Not awaited: only components that read this key suspend
          '/api/user': getUser(),
        },
      }}
    >
      {children}
    </SWRConfig>
  )
}
```

```js filename="app/layout.js" switcher
import { SWRConfig } from 'swr'
import { getUser } from './user' // some server-side function

export default function RootLayout({ children }) {
  return (
    <SWRConfig
      value={{
        fallback: {
          // Not awaited: only components that read this key suspend
          '/api/user': getUser(),
        },
      }}
    >
      {children}
    </SWRConfig>
  )
}
```

Because this is a Server Component, `getUser()` can read cookies, headers, or your database. Client Components below the `<SWRConfig>` read the seeded value by using the same key.

The key is the client fetch URL. Point it at a [Route Handler](/docs/app/api-reference/file-conventions/route) with a `GET` method. The browser cannot call a [Server Function](/docs/app/guides/server-actions) as a `GET` request for revalidation or polling. Have the Route Handler call the same `getUser` function that seeds the cache:

```ts filename="app/api/user/route.ts" switcher
import { getUser } from '../../user'

export async function GET() {
  return Response.json(await getUser())
}
```

```js filename="app/api/user/route.js" switcher
import { getUser } from '../../user'

export async function GET() {
  return Response.json(await getUser())
}
```

```tsx filename="app/profile.tsx" switcher
'use client'

import useSWR from 'swr'

type User = { name: string }

async function fetcher(url: string): Promise<User> {
  const response = await fetch(url)
  if (!response.ok) throw new Error('Failed to fetch user')
  return response.json()
}

export function Profile() {
  const { data, error } = useSWR<User>('/api/user', fetcher)

  if (error) return <p>Failed to load the profile.</p>
  if (!data) return <p>Loading profile...</p>

  return <p>{data.name}</p>
}
```

```jsx filename="app/profile.js" switcher
'use client'

import useSWR from 'swr'

async function fetcher(url) {
  const response = await fetch(url)
  if (!response.ok) throw new Error('Failed to fetch user')
  return response.json()
}

export function Profile() {
  const { data, error } = useSWR('/api/user', fetcher)

  if (error) return <p>Failed to load the profile.</p>
  if (!data) return <p>Loading profile...</p>

  return <p>{data.name}</p>
}
```

The `fallback` data can be prerendered in the React Server Component payload and streamed to the browser. Child components read the value with `useSWR`, while polling and revalidation continue on the client.

Because the seeded data is available on first render, [`isLoading`](https://swr.vercel.app/docs/advanced/understanding#combining-with-isloading-and-isvalidating-for-better-ux) stays `false`. A client-side revalidation surfaces as `isValidating`.

The `fallback` value seeds what the hook returns on first render, but it does not write to the SWR cache, so it acts as a display default until the first client fetch fills the entry. In SWR 2.5 beta, [`preload`](https://swr.vercel.app/docs/prefetching) with `cacheData` instead writes the server value into the cache under the key that `useSWR(key)` and `mutate(key)` use later:

```tsx filename="app/layout.tsx" switcher
import { preload, SWRConfig } from 'swr'
import { getUser } from './user'

export default function RootLayout({ children }: LayoutProps<'/'>) {
  const userData = preload('/api/user', () => getUser())

  return <SWRConfig value={{ cacheData: userData }}>{children}</SWRConfig>
}
```

```jsx filename="app/layout.js" switcher
import { preload, SWRConfig } from 'swr'
import { getUser } from './user'

export default function RootLayout({ children }) {
  const userData = preload('/api/user', () => getUser())

  return <SWRConfig value={{ cacheData: userData }}>{children}</SWRConfig>
}
```

Call `preload` before unrelated `await`s so requests begin as early as possible. When one boundary seeds multiple keys, start each preload and merge the returned cache maps into one `cacheData` object, such as `cacheData: { ...userData, ...messageData }`.

Because `cacheData` creates a cache entry, `mutate(key)`, revalidation, and deduplication operate on it like fetched data. The `fallback` option only sets the value returned on first render. Use `preload` when the seeded value is later mutated or revalidated on the client.

### Clear SWR data when identity changes

When the authenticated identity changes while SWR keys stay the same, call `unload({ revalidate: false })` from `useSWRConfig()` before navigating. The scoped `unload` clears the current provider and discards in-flight requests, preventing responses for the previous identity from refilling the cache.

An `unload` imported from `swr` targets the default cache. For partial identity changes, prefer identity-scoped keys or a narrower provider. `unload` requires SWR 2.5.0-beta.1 or later.

Learn more: [SWR with Next.js App Router](https://swr.vercel.app/docs/with-nextjs).

## Scoping server data to the components that use it

A `<SWRConfig>` can live in any Server Component, not only the root layout. Placing it on the route segment that owns the data keeps the `fallback` close to where it is read, keeps unrelated keys out of a global config, and lets each segment start its own server-side requests.

For dynamic data, define the client key and server cache tag together. SWR uses the key in the browser, while Next.js uses the tag to invalidate cached server data.

```ts filename="app/products/[id]/product-cache.ts" switcher
export const productCache = {
  key: (id: string) => `/api/products/${id}`,
  tag: (id: string) => `product:${id}`,
}
```

```js filename="app/products/[id]/product-cache.js" switcher
export const productCache = {
  key: (id) => `/api/products/${id}`,
  tag: (id) => `product:${id}`,
}
```

```tsx filename="app/products/[id]/page.tsx" switcher
import { Suspense } from 'react'
import { SWRConfig } from 'swr'
import { getProduct } from './data' // some server-side function
import { productCache } from './product-cache'
import { ProductView } from './product-view'

export default function Page({ params }: PageProps<'/products/[id]'>) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {params.then(({ id }) => (
        <ProductData id={id} />
      ))}
    </Suspense>
  )
}

function ProductData({ id }: { id: string }) {
  return (
    <SWRConfig
      value={{
        fallback: {
          // Not awaited: only components that read this key suspend
          [productCache.key(id)]: getProduct(id),
        },
      }}
    >
      <ProductView id={id} />
    </SWRConfig>
  )
}
```

```jsx filename="app/products/[id]/page.js" switcher
import { Suspense } from 'react'
import { SWRConfig } from 'swr'
```

Inside `<Suspense>`, `params.then()` resolves the `id` and passes it to `ProductData`, which seeds the `fallback` with the `getProduct(id)` promise. Only that subtree suspends while the data loads.

The Client Component reads the data with `useSWR` using the same key:

```tsx filename="app/products/[id]/product-view.tsx" switcher
'use client'

import useSWR from 'swr'
import { productCache } from './product-cache'

const fetcher = (url: string) => fetch(url).then((res) => res.json())

export function ProductView({ id }: { id: string }) {
  const { data } = useSWR(productCache.key(id), fetcher)

  return <h1>{data?.name}</h1>
}
```

```jsx filename="app/products/[id]/product-view.js" switcher
'use client'

import useSWR from 'swr'
import { productCache } from './product-cache'

const fetcher = (url) => fetch(url).then((res) => res.json())

```

> **Good to know:** The `fallback` key and the `useSWR` key must match exactly. If they drift, SWR ignores the seeded value and fetches on the client.

Learn more: [SWR arguments and keys](https://swr.vercel.app/docs/arguments).

## Caching server data with Cache Components

Server seeding and server data caching are independent. A server function can use [Cache Components](/docs/app/getting-started/caching) whether the Server Component seed, the Route Handler, or both call it. Add [`use cache`](/docs/app/api-reference/directives/use-cache), choose a [`cacheLife`](/docs/app/api-reference/functions/cacheLife) profile, and tag the data with the server identity defined beside the SWR key:

```ts filename="app/products/[id]/data.ts" switcher
import { cacheLife, cacheTag } from 'next/cache'
import { productCache } from './product-cache'

export async function getProduct(id: string) {
  'use cache'
  cacheLife('max')
  cacheTag(productCache.tag(id))

  return db.product.findUnique({ where: { id } })
}
```

```js filename="app/products/[id]/data.js" switcher
import { cacheLife, cacheTag } from 'next/cache'
import { productCache } from './product-cache'

export async function getProduct(id) {
  'use cache'
  cacheLife('max')
  cacheTag(productCache.tag(id))

  return db.product.findUnique({ where: { id } })
}
```

This example uses `cacheLife('max')` because writes invalidate the product tag. Within the profile, `stale` controls how long the Next.js client cache can reuse a prefetched view, while `revalidate` and `expire` control the server cache. Choose a shorter profile when the server value should refresh with time.

SWR owns a separate browser cache. Its revalidation options do not need to match `cacheLife`. When React Activity restores a preserved route, SWR applies options such as `revalidateOnMount` and `revalidateIfStale` as its Effects restart.

Keep the cache contract free of server-only and client-only imports so every cache boundary can reuse it instead of duplicating raw keys and tags.

Learn more: [`use cache`](/docs/app/api-reference/directives/use-cache) and [`cacheTag`](/docs/app/api-reference/functions/cacheTag).

## Coordinating the server and client caches on mutation

The examples above seed the client cache from the server. The server value provides the initial snapshot; after hydration, SWR owns the browser copy and revalidation behavior.

For reused data, keep the SWR key and server tag in the same cache contract:

```ts filename="app/activity/activity-cache.ts" switcher
export const activityCache = {
  key: '/api/activity/unread',
  tag: (userId: string) => `activity:${userId}`,
}
```

```js filename="app/activity/activity-cache.js" switcher
export const activityCache = {
  key: '/api/activity/unread',
  tag: (userId) => `activity:${userId}`,
}
```

With SWR, pass the write to [`mutate`](https://swr.vercel.app/docs/mutation) and provide `optimisticData`. SWR shows the optimistic value immediately, replaces it with the response, and rolls it back if the write fails:

```tsx filename="app/activity/mark-read.tsx" switcher
'use client'

import { useSWRConfig } from 'swr'
import { activityCache } from './activity-cache'

export function useMarkActivityRead() {
  const { mutate } = useSWRConfig()

  return () =>
    mutate(
      activityCache.key,
      async () => {
        const response = await fetch('/api/activity/read', { method: 'POST' })
        if (!response.ok) throw new Error('Failed to mark activity as read')
        return response.json()
      },
      {
        optimisticData: { count: 0 },
        revalidate: false,
        rollbackOnError: true,
      }
    )
}
```

```jsx filename="app/activity/mark-read.js" switcher
'use client'

import { useSWRConfig } from 'swr'
import { activityCache } from './activity-cache'

export function useMarkActivityRead() {
  const { mutate } = useSWRConfig()

  return () =>
    mutate(
      activityCache.key,
      async () => {
        const response = await fetch('/api/activity/read', { method: 'POST' })
        if (!response.ok) throw new Error('Failed to mark activity as read')
        return response.json()
      },
      {
        optimisticData: { count: 0 },
        revalidate: false,
        rollbackOnError: true,
      }
    )
}
```

The Route Handler writes to the database and revalidates the tagged server data with `revalidateTag`. Tag the cached server query with [`cacheTag`](/docs/app/api-reference/functions/cacheTag) so the tag matches:

```ts filename="app/api/activity/read/route.ts" switcher
import { revalidateTag } from 'next/cache'
import { markActivityRead, getCurrentUserId } from '../../../activity/data'
import { activityCache } from '../../../activity/activity-cache'

export async function POST() {
  const userId = await getCurrentUserId()
  await markActivityRead(userId)
  revalidateTag(activityCache.tag(userId), { expire: 0 })
  return Response.json({ count: 0 })
}
```

```js filename="app/api/activity/read/route.js" switcher
import { revalidateTag } from 'next/cache'
import { markActivityRead, getCurrentUserId } from '../../../activity/data'
import { activityCache } from '../../../activity/activity-cache'

export async function POST() {
  const userId = await getCurrentUserId()
  await markActivityRead(userId)
  revalidateTag(activityCache.tag(userId), { expire: 0 })
  return Response.json({ count: 0 })
}
```

The badge updates from the SWR cache, while `revalidateTag` expires the server seed without touching the current route. The screen holds steady after the write, and the next navigation seeds SWR with fresh server data. It uses `{ expire: 0 }` because the same tag feeds the server-rendered activity list, which must be correct on the next visit.

> **Good to know:** This example assumes the server seed uses [`use cache`](/docs/app/api-reference/directives/use-cache) and `cacheTag`. Omit `revalidateTag` for an uncached read because each server render already reads fresh data. To update the current route instead of waiting for the next navigation, call [`router.refresh()`](/docs/app/api-reference/functions/use-router) after the mutation. See [coordinating the server and client caches](/docs/app/guides/single-page-applications#client-side-data-fetching-libraries) for the invalidation choices.

Learn more: [SWR mutation and optimistic updates](https://swr.vercel.app/docs/mutation).
