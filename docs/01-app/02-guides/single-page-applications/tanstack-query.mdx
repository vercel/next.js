You can use [TanStack Query](https://tanstack.com/query) (formerly React Query) with Next.js on the client and the server. This guide shows the TanStack Query-specific setup for the patterns in [Single-Page Applications](/docs/app/guides/single-page-applications#client-side-data-fetching-libraries): fetching data only on the client, optionally seeding server data into the client cache, caching server data with Cache Components, and coordinating the server and client caches on mutation.

## Fetching data only on the client

You do not have to seed a query from a Server Component. For data whose input is only known after an interaction, such as autocomplete, call `useQuery` directly from a Client Component with a key that includes the input:

```tsx filename="app/product-autocomplete.tsx" switcher
'use client'

import { useQuery } from '@tanstack/react-query'

export function ProductAutocomplete({ query }: { query: string }) {
  const { data = [] } = useQuery({
    queryKey: ['product-search', query],
    queryFn: () => fetch(`/api/products?q=${query}`).then((res) => res.json()),
    enabled: query.length > 0,
  })

  return data.map((product) => <p key={product.id}>{product.name}</p>)
}
```

The result is not in the server-rendered response, so the first result waits for hydration and a client request. This is often the right tradeoff for interaction-driven data. The API route can still read through a server function that uses Cache Components.

Learn more: [TanStack Query queries](https://tanstack.com/query/latest/docs/framework/react/guides/queries).

## Seeding TanStack Query from a Server Component (optional)

When the server already knows which data the first render needs, you can seed the cache from a Server Component the same way as [SWR](/docs/app/guides/single-page-applications/swr): prefetch on the server, hand the cache to the client, and let it own revalidation from there. This avoids the initial client-side request while preserving TanStack Query's client-side features.

TanStack Query needs a one-time setup, including a `getQueryClient` (new per request on the server, a singleton in the browser), a `<QueryClientProvider>`, and a client configured to dehydrate pending queries. TanStack Query owns this integration, so follow [its Advanced SSR guide](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr) for the full setup and current APIs.

Define the client query key and server cache tag together. They identify the same data in different caches: TanStack Query uses the key in the browser, while Next.js uses the tag to invalidate cached server data.

```ts filename="app/products/[id]/product-cache.ts" switcher
import { queryOptions } from '@tanstack/react-query'
import type { Product } from './data'

export const productCache = {
  key: (id: string) => ['product', id] as const,
  tag: (id: string) => `product:${id}`,
  options: (id: string) =>
    queryOptions({
      queryKey: productCache.key(id),
      queryFn: async (): Promise<Product> => {
        const res = await fetch(`/api/products/${id}`)
        return res.json()
      },
    }),
}
```

```js filename="app/products/[id]/product-cache.js" switcher

```

The options live with the key so callers cannot accidentally use a different query identity. The query function fetches an [API route](/docs/app/api-reference/file-conventions/route) so it can run on the client to refetch.

A Server Component starts the request with `prefetchQuery` **without awaiting it**, then serializes the cache into the streamed HTML with `<HydrationBoundary>`. On the server, override `queryFn` to call the data function directly, since the API route's relative URL only resolves in the browser:

```tsx filename="app/products/[id]/page.tsx" switcher
import { Suspense } from 'react'
import { dehydrate, HydrationBoundary } from '@tanstack/react-query'
import { getQueryClient } from '@/app/get-query-client'
import { getProduct } from './data'
import { productCache } from './product-cache'
import { ProductView } from './product-view'

export default function Page({ params }: PageProps<'/products/[id]'>) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {params.then(({ id }) => (
        <ProductData id={id} />
      ))}
    </Suspense>
  )
}

function ProductData({ id }: { id: string }) {
  const queryClient = getQueryClient()

  // Not awaited, so rendering is not blocked.
  queryClient.prefetchQuery({
    ...productCache.options(id),
    queryFn: () => getProduct(id),
  })

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ProductView id={id} />
    </HydrationBoundary>
  )
}
```

## Caching server data with Cache Components

Server seeding and server data caching are independent. With [Cache Components](/docs/app/getting-started/caching), the server function can cache the data whether it is called by the Server Component seed, the API route, or both. Add [`use cache`](/docs/app/api-reference/directives/use-cache), choose a [`cacheLife`](/docs/app/api-reference/functions/cacheLife) profile, and use the server tag defined beside the query key:

```ts filename="app/products/[id]/data.ts" switcher
import { cacheLife, cacheTag } from 'next/cache'
import { productCache } from './product-cache'

export async function getProduct(id: string) {
  'use cache'
  cacheLife('max')
  cacheTag(productCache.tag(id))

  return db.product.findUnique({ where: { id } })
}
```

```js filename="app/products/[id]/data.js" switcher
import { cacheLife, cacheTag } from 'next/cache'
import { productCache } from './product-cache'

export async function getProduct(id) {
  'use cache'
  cacheLife('max')
  cacheTag(productCache.tag(id))

  return db.product.findUnique({ where: { id } })
}
```

This example uses `cacheLife('max')` because writes invalidate the product tag. Choose a shorter profile when the server value should refresh with time instead. TanStack Query's `staleTime` and refetch options are separate browser policies and do not need to match `cacheLife`.

Keep the cache contract free of server-only and client-only imports so every cache boundary can reuse it instead of duplicating raw keys and tags.

### Prerendering the hydration state

The `dehydrate()` call reads the current time (`Date.now()`), which is not allowed while prerendering, so calling it directly fails with a [current-time prerender error](/docs/messages/blocking-prerender-current-time).

Instead, cache only that timestamp and build the dehydrated state by hand. Wrap the time read in [`use cache`](/docs/app/api-reference/directives/use-cache) with the same tags as the data reads. When a mutation invalidates those tags, the data and its timestamp advance together, so `<HydrationBoundary>` overwrites the client query on the next navigation:

```tsx filename="app/lib/hydrate.ts" switcher
import 'server-only'

import { cacheLife, cacheTag } from 'next/cache'
import {
  defaultShouldDehydrateQuery,
  QueryClient,
  type DehydratedState,
  type QueryKey,
} from '@tanstack/react-query'

type HydratedQuery = {
  queryKey: QueryKey
  data: unknown
}

type HydrationOptions = {
  tags: string[]
}

async function getHydrationUpdatedAt(tags: string[]) {
  'use cache'
  cacheTag(...tags)
  cacheLife('max')
  return Date.now()
}

export async function dehydrate(
  queries: HydratedQuery[],
  options: HydrationOptions
): Promise<DehydratedState> {
  const updatedAt = await getHydrationUpdatedAt(options.tags)

  const queryClient = new QueryClient()

  for (const query of queries) {
    queryClient.setQueryData(query.queryKey, query.data, { updatedAt })
  }

  return {
    mutations: [],
    queries: queryClient
      .getQueryCache()
      .getAll()
      .filter((query) => defaultShouldDehydrateQuery(query))
      .map((query) => ({
        dehydratedAt: updatedAt,
        queryHash: query.queryHash,
        queryKey: query.queryKey,
        state: query.state,
        ...(query.meta ? { meta: query.meta } : {}),
      })),
  }
}
```

```js filename="app/lib/hydrate.js" switcher
import 'server-only'

import { cacheLife, cacheTag } from 'next/cache'
import { defaultShouldDehydrateQuery, QueryClient } from '@tanstack/react-query'

async function getHydrationUpdatedAt(tags) {
  'use cache'
  cacheTag(...tags)
  cacheLife('max')
  return Date.now()
}

export async function dehydrate(queries, options) {
  const updatedAt = await getHydrationUpdatedAt(options.tags)

  const queryClient = new QueryClient()

  for (const query of queries) {
    queryClient.setQueryData(query.queryKey, query.data, { updatedAt })
  }

  return {
    mutations: [],
    queries: queryClient
      .getQueryCache()
      .getAll()
      .filter((query) => defaultShouldDehydrateQuery(query))
      .map((query) => ({
        dehydratedAt: updatedAt,
        queryHash: query.queryHash,
        queryKey: query.queryKey,
        state: query.state,
        ...(query.meta ? { meta: query.meta } : {}),
      })),
  }
}
```

Await the helper in the segment that owns the data, passing the data and the same tags used on the underlying `getProduct` read. Hand the result to `<HydrationBoundary>`, the same `ProductData` boundary shown above:

```tsx filename="app/products/[id]/page.tsx" switcher
import { dehydrate } from '@/app/lib/hydrate'
import { getProduct } from './data'
import { productCache } from './product-cache'

async function ProductData({ id }: { id: string }) {
  const product = await getProduct(id)
  const state = await dehydrate(
    [{ queryKey: productCache.key(id), data: product }],
    { tags: [productCache.tag(id)] }
  )

  return (
    <HydrationBoundary state={state}>
      <ProductView id={id} />
    </HydrationBoundary>
  )
}
```

```jsx filename="app/products/[id]/page.js" switcher

import { getProduct } from './data'
import { productCache } from './product-cache'

async function ProductData({ id }) {

      <ProductView id={id} />
    </HydrationBoundary>

```

> **Good to know:** The timestamp must advance whenever the seeded data advances. The helper above suits tag-driven server data because both use the same tags. For time-driven server data, derive the data and hydration timestamp from the same cached snapshot instead of maintaining unrelated time windows.

Learn more: [`use cache`](/docs/app/api-reference/directives/use-cache) and [`cacheTag`](/docs/app/api-reference/functions/cacheTag).

## Coordinating the server and client caches on mutation

The examples above seed the client cache from the server. After hydration, TanStack Query owns the browser copy and its revalidation. For reused data, keep the query key and server tag in the same cache contract:

```ts filename="app/activity/activity-cache.ts" switcher
export const activityCache = {
  key: ['activity', 'unread'] as const,
  tag: (userId: string) => `activity:${userId}`,
}
```

```js filename="app/activity/activity-cache.js" switcher
export const activityCache = {
  key: ['activity', 'unread'],
  tag: (userId) => `activity:${userId}`,
}
```

On mutation, use `useMutation`'s [`onMutate`](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates) callback to update the cache immediately, restore the previous value in `onError` if the write fails, and commit the value returned by the write:

```tsx filename="app/activity/mark-read.tsx" switcher
'use client'

import { useMutation, useQueryClient } from '@tanstack/react-query'
import { activityCache } from './activity-cache'

export function useMarkActivityRead() {
  const queryClient = useQueryClient()
  const queryKey = activityCache.key

  return useMutation({
    mutationFn: async () => {
      const response = await fetch('/api/activity/read', { method: 'POST' })
      if (!response.ok) throw new Error('Failed to mark activity as read')
      return response.json()
    },
    onMutate: async () => {
      await queryClient.cancelQueries({ queryKey })
      const previous = queryClient.getQueryData(queryKey)
      queryClient.setQueryData(queryKey, { count: 0 })
      return { previous }
    },
    onError: (_error, _variables, context) => {
      queryClient.setQueryData(queryKey, context?.previous)
    },
    onSuccess: (activity) => {
      queryClient.setQueryData(queryKey, activity)
    },
  })
}
```


The API route writes to the database, then refreshes the server seed with `revalidateTag`, the same route handler shown in the [SWR guide](/docs/app/guides/single-page-applications/swr#coordinating-the-server-and-client-caches-on-mutation).

> **Good to know:** This assumes the server seed reads through [`use cache`](/docs/app/api-reference/directives/use-cache) and is tagged with `cacheTag`. If that read is uncached, drop `revalidateTag`: each refetch already returns fresh data, so the client only revalidates after the write. See [coordinating the server and client caches](/docs/app/guides/single-page-applications#client-side-data-fetching-libraries) for the invalidation choices.
