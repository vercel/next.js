With [Cache Components](/docs/app/getting-started/caching) and [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching), a [`<Link>`](/docs/app/api-reference/components/link) prefetches one reusable [App Shell](/docs/app/glossary#app-shell) per route. The App Shell contains static output, cached content that does not depend on the destination URL, and session-specific content from [`cookies()`](/docs/app/api-reference/functions/cookies) or [`headers()`](/docs/app/api-reference/functions/headers).

Content based on [`params`](/docs/app/api-reference/file-conventions/page#params-optional) or [`searchParams`](/docs/app/api-reference/file-conventions/page#searchparams-optional) varies by URL. By default, this content streams after navigation. You can prefetch it for selected links when the underlying work is cached.

See the [Prefetching guide](/docs/app/guides/prefetching) for the default prefetch behavior and scheduling.

This guide explains how to:

- Prefetch cached URL-specific content for selected links
- Include cached session-specific content in the App Shell
- Defer cached content until the user navigates

Before you begin, enable [Cache Components](/docs/app/getting-started/caching) and [`partialPrefetching`](/docs/app/api-reference/config/next-config-js/partialPrefetching):

```ts filename="next.config.ts" highlight={4,5}
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

Your route should also have meaningful [`<Suspense>`](https://react.dev/reference/react/Suspense) boundaries. See the [Instant navigation guide](/docs/app/guides/instant-navigation) for how to structure and inspect the route's App Shell.

## Prefetch URL-specific content

Set `<Link prefetch={true}>` to resolve URL data for that link before navigation. The destination must use [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching), enabled globally with `partialPrefetching` or per segment with [`prefetch = 'partial'`](/docs/app/api-reference/file-conventions/route-segment-config/prefetch#partial).

For example, the following page opts two search links into per-link prefetching:

```tsx filename="app/page.tsx"
import Link from 'next/link'

export default function Home() {
  return (
    <nav>
      <Link href="/search?q=react" prefetch={true}>
        React
      </Link>
      <Link href="/search?q=next" prefetch={true}>
        Next.js
      </Link>
    </nav>
  )
}
```

If only some links should use per-link prefetching, keep the others on the default `auto` behavior. A conditional such as `prefetch={isFeatured}` evaluates to `prefetch={false}` for other links and disables all prefetching. Use `prefetch={isFeatured ? true : 'auto'}` instead.

The destination keeps the heading in the App Shell and renders the URL-specific results inside a `<Suspense>` boundary. The `search()` function caches each query so a prefetch can include the results:

```tsx filename="app/search/page.tsx"
import { Suspense } from 'react'

export default function SearchPage({ searchParams }: PageProps<'/search'>) {
  return (
    <>
      <h1>Search</h1>
      <Suspense fallback={<ResultsSkeleton />}>
        <Results searchParams={searchParams} />
      </Suspense>
    </>
  )
}

async function Results({
  searchParams,
}: {
  searchParams: PageProps<'/search'>['searchParams']
}) {
  const { q } = await searchParams
  return <ResultList items={await search(q)} />
}

async function search(q: string) {
  'use cache'
  return db.search(q)
}
```

Keep request-specific work outside the cache boundary. If a function combines reusable and request-specific work, move the reusable lookup into a cached helper and let the rest stream from its `<Suspense>` boundary. Use [`connection()`](/docs/app/api-reference/functions/connection) only when work must wait for a real request.

Without `prefetch={true}`, navigation renders the heading and the `<ResultsSkeleton>` fallback from the App Shell. The results then stream in. With `prefetch={true}`, the router knows `q` from the link's URL and can resolve the cached `search(q)` result before the click. The heading and results render together on navigation.

The prerender advances through anything static or cached, then stops at uncached reads and falls back to the surrounding `<Suspense>` boundary. That boundary is already in place from [structuring the route for instant navigation](/docs/app/guides/instant-navigation).

Generating a per-link prefetch can require **a server invocation for each prefetchable link**. If the content is statically renderable, Next.js serves the prefetch from the static cache instead.

> **Good to know:** Prefetching is best-effort. If the user navigates before the per-link prefetch completes, the router renders the App Shell and streams the remaining content.

Content that awaits `params` or `searchParams` needs a `<Suspense>` boundary. [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params) can prerender selected param values; a per-link prefetch with `prefetch={true}` resolves cached content for other values.

## Include session-specific content in the App Shell

Session data does not vary by destination URL, so it does not require `prefetch={true}`. A route that reads `cookies()` or `headers()` gets an App Shell that includes its session-specific content. The browser caches this shell for the current session and reuses it on navigation.

For example, the following dashboard layout renders a navigation menu based on a cookie:

```tsx filename="app/dashboard/layout.tsx"
import { Suspense } from 'react'

export default function DashboardLayout({
  children,
}: LayoutProps<'/dashboard'>) {
  return (
    <div>
      <Suspense fallback={<nav>Loading...</nav>}>
        <UserNav />
      </Suspense>
      <main>{children}</main>
    </div>
  )
}
```

You can cache the lookup in two ways:

- Read the request value outside a `"use cache"` function and pass it as an argument when the result can be shared across sessions.
- Use [`"use cache: private"`](/docs/app/api-reference/directives/use-cache-private) when the result belongs to one session.

### Extract and pass

Read the cookie outside the cached function and pass its value as an argument. The argument becomes part of the cache key, so sessions with the same value can share the result.

```tsx filename="app/dashboard/user-nav.tsx"
import { cookies } from 'next/headers'

async function UserNav() {
  const team = (await cookies()).get('team')?.value
  const topics = await getTopics(team)
  return (
    <nav>
      {topics.map((topic) => (
        <a key={topic.id} href={topic.href}>
          {topic.label}
        </a>
      ))}
    </nav>
  )
}

async function getTopics(team: string | undefined) {
  'use cache'
  return db.topics.forTeam(team)
}
```

On a direct visit, `<UserNav>` shows its fallback until the lookup resolves. On navigation, the App Shell includes the resolved menu. Sessions with the same team value share the cache entry.

### `"use cache: private"`

When the lookup belongs to a single session, use [`"use cache: private"`](/docs/app/api-reference/directives/use-cache-private). It lets a cached function read cookies, headers, or other runtime data directly. The browser stores the result for the current session.

```tsx filename="app/dashboard/user-nav.tsx"
import { cookies } from 'next/headers'

async function UserNav() {
  const user = await getUser()
  return <nav>{user.name}</nav>
}

async function getUser() {
  'use cache: private'
  const session = (await cookies()).get('session')?.value
  return db.users.findBySession(session)
}
```

This pattern is also useful when a helper reads runtime data internally, such as an authentication helper that reads a cookie and checks a token's expiry. Keep the private cache scope close to that runtime data access so unrelated work does not inherit the same lifetime.

## Defer cached content until navigation

Cached content can stay reusable without being generated during a prefetch. Await [`unstable_navigation()`](/docs/app/api-reference/functions/navigation) before the work to start it when the user navigates. The prefetched UI contains the nearest `<Suspense>` fallback until the content streams in.

The following component reads the session while creating the App Shell, but waits until navigation to rank its recommendations:

```tsx filename="app/dashboard/recommendations.tsx" highlight={6}
import { cookies } from 'next/headers'
import { unstable_navigation } from 'next/cache'

async function Recommendations() {
  const session = (await cookies()).get('session')?.value
  await unstable_navigation()
  const items = await rank(session)
  return <List items={items} />
}

async function rank(session?: string) {
  'use cache: private'
  return db.recommendations.rank({ session })
}
```

The session resolves as part of the App Shell because it is read before `unstable_navigation()`. The ranking starts after navigation and calls a private cached function, so subsequent calls can reuse the result.

Place the cache boundary in a function called after `unstable_navigation()`. The stage API cannot run inside a cached scope.

For a subtree that would otherwise sit in the App Shell, but that a `<Link prefetch={true}>` should still resolve before the click, use [`unstable_prefetch()`](/docs/app/api-reference/functions/prefetch) instead.

Unlike [`connection()`](/docs/app/api-reference/functions/connection), `unstable_navigation()` does not make the subtree request-dependent. Reusable content keeps its cache lifetime while waiting for navigation. See [How `unstable_navigation()` differs from `connection()`](/docs/app/api-reference/functions/navigation#how-unstable_navigation-differs-from-connection) for the full comparison.

## Test prefetched and deferred content

The [Instant navigation guide](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests) explains how to install and configure `@next/playwright`. For a client navigation, use `instant()` to inspect the destination's prefetched UI.

Inside the callback, click the link, wait for the destination URL, and assert which content is available. After the callback releases the navigation, assert that deferred content eventually renders:

```ts filename="e2e/product-navigation.test.ts" highlight={8-15,17}
import { test, expect } from '@playwright/test'
import { instant } from '@next/playwright'

test('prefetches the product summary but not reviews', async ({ page }) => {
  await page.goto('/products')

  await instant(page, async () => {
    await page.click('a[href="/products/baseball-cap"]')
    await page.waitForURL((url) => url.pathname === '/products/baseball-cap')

    await expect(
      page.getByRole('heading', { name: 'Baseball Cap' })
    ).toBeVisible()
    await expect(page.getByTestId('product-summary')).toBeVisible()
    await expect(page.getByTestId('reviews')).toHaveCount(0)
  })

  await expect(page.getByTestId('reviews')).toBeVisible()
})
```

While the `instant()` callback is running, dynamic writes are paused. In this example, the product summary is part of the prefetched UI, while reviews wait for navigation. The final assertion confirms that the reviews render after the pause is released.

See [Prevent regressions with e2e tests](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests) for initial page-load coverage and running these tests against a production build.

## Choose which links to prefetch

Use `prefetch={true}` when:

- Part of the component tree depends on URL data: the full URL, `searchParams`, or `params` not resolved by [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params)
- That part of the tree has a known cache lifetime (it can be expressed with `"use cache"` or `"use cache: private"`)
- The traffic justifies the per-link server invocation

Keep the default `auto` behavior when a per-link prefetch would not produce more useful UI than the App Shell:

- The route has little or no URL-data dependency. The App Shell already makes the navigation instant.
- The dependent content has to be fresh on every request. The prerender stops at the same `<Suspense>` fallback, so the user sees the same UI either way.
- The route is rarely navigated to. You pay per visible link, regardless of click-through.

When many links to a route are visible at once, such as a grid of cards, each `<Link prefetch={true}>` prefetches that link's content as it enters the viewport, so the grid makes one such server request per card. Prefetch on intent instead. A [hover-triggered prefetch](/docs/app/guides/prefetching#hover-triggered-prefetch) fetches only the links the user is likely to click. The default `<Link>` (without `prefetch={true}`) prefetches only the App Shell, so it doesn't carry this cost.

|         | App Shell                                                  | Per-link prefetch with `prefetch={true}` |
| ------- | ---------------------------------------------------------- | ---------------------------------------- |
| Scope   | One per route                                              | One per visible `<Link prefetch={true}>` |
| Content | Static, cached, and session-specific UI independent of URL | App Shell plus cached URL-specific UI    |
| Cost    | Bounded by route count                                     | Bounded by visible-link count            |
| Role    | Default prefetch                                           | More rendered before click               |

[Deferring cached content until navigation](#defer-cached-content-until-navigation) provides another way to control prefetch cost. It trades work during prefetch for a temporary `<Suspense>` fallback after navigation.
