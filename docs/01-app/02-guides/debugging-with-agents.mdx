A route can return HTTP 200 and still have a navigation Insight. The dev server can explain what blocked the route; the browser can show what a reader saw when they clicked a particular link.

## Route errors and navigation Insights

With [Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents) enabled, `next dev` validates routes in the background. A finding can appear after the page is visible. You can see it in [DevTools → Insights](/docs/app/guides/devtools#issues-and-insights) or in the terminal running `next dev`.

An agent can also [call `check_route` on the running dev server](#calling-the-dev-server) without opening a browser. Pass the concrete path, including any query string that affects the page, for example `{"path":"/settings?tab=email"}`. The tool requests the page and waits for its validation result:

- `validation.status: "validated"`: Validation ran. `validation.errors` contains any findings and their source locations when available. To verify a fix, check that the same path was validated again and the original finding is gone.
- `validation.status: "not-run"`: The route was not validated. Read `validation.reason`; an empty error list or successful HTTP response alone can't confirm a fix.

With Turbopack, `compilationIssues` also reports compiler diagnostics for that route. The request doesn't use browser cookies. If a problem only occurs when signed in, reproduce it in the signed-in browser.

## Loading UI during a navigation

To see what a link prefetched, open the page containing the link. In the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools), enable **Pause on navigations** and click it. In Playwright, click the same link inside [`instant()`](/docs/app/guides/testing/playwright#testing-instant-navigations). Both let you inspect the destination while the remaining content is still loading. Checking the destination path alone can't show what was ready for that click.

## Browser errors and logs

If an interaction throws, reproduce it in the browser where it happens. The browser console shows the error; `get_errors` can read the connected browser's error state. For server output and browser logs, `get_logs` returns the path to the dev log. Both tools take an empty arguments object. The optional [`next-dev-loop` skill](/docs/app/guides/ai-agents#next-dev-loop) can help an agent inspect the running page.

## Production-only failures

If prerendering fails during `next build`, [`--debug-prerender`](/docs/app/guides/building#debug-prerender-errors) gives you a readable stack trace. On a large app, [`--debug-build-paths`](/docs/app/api-reference/cli/next#building-specific-routes) limits the build to the affected routes. Verify the fix with a normal production build. If the build succeeds but the running app fails, reproduce the problem with `next start`.

## Calling the dev server

On Next.js 16 and later, `next dev` exposes an MCP endpoint at `/_next/mcp`. Use the URL printed by the running dev server. Send `tools/list` to see what's available in the installed version, then `tools/call` to the same endpoint. No additional package is required.

<details>
<summary>Example HTTP requests on port 3000</summary>

```bash filename="Terminal"
mcp() {
  curl -sS http://localhost:3000/_next/mcp \
    -H 'Content-Type: application/json' \
    -H 'Accept: application/json, text/event-stream' \
    -d "$1"
}

mcp '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

For example, to check a route:

```bash filename="Terminal"
mcp '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"check_route","arguments":{"path":"/settings"}}}'
```

</details>

If your agent already has the [Next.js DevTools MCP connector](/docs/app/guides/mcp), it can use `nextjs_index` to find the server and `nextjs_call` to call a tool.
