Loading UI goes wrong in a small number of recognizable ways. A route-level `loading.tsx` competes with a page skeleton and a per-query spinner. One coarse boundary hides a header that could have painted immediately. Sections reveal in whatever order their data returns and shove each other around. A skeleton reserves the wrong height, so the page jumps when the real rows arrive.

This guide fixes each of those problems in one app. The sections are independent, so read it start to finish or jump to the problem you have.

## Example

As an example, we'll fix the loading UI of a team directory that lists members, searches them, paginates them, and links to each member's profile.

You can find the resources used in this example here:

- [Demo](https://loading-ui-demo.labs.vercel.dev)
- [Code](https://github.com/vercel-labs/loading-ui-demo)

> **Good to know**: The demo runs with [Cache Components](/docs/app/guides/migrating-to-cache-components) and [Partial Prefetching](/docs/app/guides/adopting-partial-prefetching) enabled, which is why the shell appears instantly on navigation. The fixes below don't depend on either.

## Getting the shell to paint

### Top-level awaits that block the shell

Awaiting anything at the top of a page component blocks the entire route. Nothing renders, including the parts that never needed data, so the user gets a blank screen for as long as the slowest await takes.

The awaits are usually `params`, `searchParams`, a query, an authorization check, or a [`notFound()`](/docs/app/api-reference/functions/not-found) decision:

```tsx filename="app/member/[id]/page.tsx"
// Blocks the shell. The back link can't paint until the member query resolves.
export default async function MemberPage({
  params,
}: PageProps<'/member/[id]'>) {
  const { id } = await params
  const member = await getMember(Number(id))
  if (!member) notFound()

  return (
    <main>
      <Link href="/">Directory</Link>
      <ProfileHeader member={member} />
    </main>
  )
}
```

Keep the page component synchronous and push each read down into the component that needs it. The page becomes a layout of static markup and boundaries, which is exactly what can be prerendered:

```tsx filename="app/member/[id]/page.tsx"
export default function MemberPage({ params }: PageProps<'/member/[id]'>) {
  return (
    <main>
      {/* Static, so it goes out with the first HTML */}
      <Link href="/">Directory</Link>

      <Suspense fallback={<ProfileHeaderSkeleton />}>
        {params.then(({ id }) => (
          <ProfileHeader id={Number(id)} />
        ))}
      </Suspense>
    </main>
  )
}
```

The `notFound()` check moves inside `ProfileHeader`, where it runs against data that component already has. A 404 decision at the page level gates every byte of the response on a query that only one section needs.

We can confirm the result with [`next build`](/docs/app/api-reference/cli/next#next-build-options). The route is now prerendered up to its boundaries:

```bash filename="Terminal"
Route (app)
┌ ◐ /
└ ◐ /member/[id]

◐  (Partial Prerender)  prerendered as static HTML with dynamic server-streamed content
```

With an `await` back at the top of the page, the same route reports no static content, because there is nothing the framework can generate ahead of the request.

> **Good to know**: With [Cache Components](/docs/app/getting-started/caching), awaiting uncached data outside a boundary is a [build-time error](/docs/messages/blocking-prerender-dynamic) rather than a silent performance cliff, because the route can no longer prerender a shell.

### Stable UI hidden behind one coarse boundary

A boundary hides everything inside it until its slowest child is ready, so anything that could have rendered immediately and ends up inside one is wasted. Headers, titles, navigation, search controls, and empty containers all belong outside.

Put the boundary around the part that's actually slow:

```tsx filename="app/page.tsx"
import { Suspense } from 'react'
import { Stats } from './stats'
import { MemberList, DirectorySkeleton } from './member-list'

export default function Page({ searchParams }: PageProps<'/'>) {
  return (
    <main>
      <header>
        <h1>Team directory</h1>
        {/* Synchronous, so it never sits behind a fallback */}
        <Stats />
      </header>

      <Suspense fallback={<DirectorySkeleton />}>
        {searchParams.then(({ q, page }) => (
          <MemberList
            query={typeof q === 'string' ? q : ''}
            pageCount={Math.max(1, Number(page) || 1)}
          />
        ))}
      </Suspense>
    </main>
  )
}
```

The header and the skeleton go out with the first HTML, and the list replaces the skeleton when its query resolves. If `<Stats />` sat inside the boundary, it would wait behind the skeleton too.

The page's largest element belongs outside for a second reason. A skeleton is not a [Largest Contentful Paint](/docs/app/guides/streaming#lcp-largest-contentful-paint) candidate, because LCP only counts images, video posters, background images, and blocks that contain text. A placeholder built from empty sized boxes never registers as one, so the LCP timestamp waits for the real content and streaming a hero image or a headline delays it by that query's full duration. Keep the largest above-the-fold element in the [static shell](/docs/app/guides/streaming#the-static-shell), and if it's an image, give it [`priority`](/docs/app/api-reference/components/image#priority) so it isn't lazy-loaded.

### Competing loading signals

One region should produce one loading signal. Apps accumulate them by adding each in isolation, and the user ends up watching a route-level `loading.tsx`, then a page-level skeleton, then a spinner inside a card, for a single page load.

[`loading.tsx`](/docs/app/api-reference/file-conventions/loading) is one boundary around the whole route, so it fits a page whose entire first render waits on data. Once any part of the page can paint sooner, `<Suspense>` around the slow part replaces it rather than joining it. A full-page skeleton also has to be maintained alongside the real page, and it drifts out of sync as the layout changes. See [When to use `loading.js` vs `<Suspense>`](/docs/app/guides/streaming#when-to-use-loadingjs-vs-suspense).

Layouts add signals the same way. A `loading.tsx` above a shared layout doesn't show on client navigations, because React re-enters the tree at that layout, so an overlay added to compensate ends up firing on the first load when the fallback already covers it. See [Ensuring instant navigations](/docs/app/guides/instant-navigation).

Nested queries are the last source. A section that already shows a skeleton doesn't need a second spinner for a query inside it, and a `<Link>` pointing at a destination that has its own shell doesn't need one either, because the click lands on that shell and the destination's skeletons are the feedback. When the destination has no shell, [`useLinkStatus`](/docs/app/api-reference/functions/use-link-status#gracefully-handling-fast-navigation) gives the link its own pending state.

### Data fetching split across client effects

Fetching in a client effect puts every request behind the JavaScript bundle. The shell paints empty, the requests start after hydration, and each component that fetches for itself adds a round trip and its own `isLoading` spinner:

```tsx filename="app/member-list.tsx"
'use client'

// The request can't start until this component has downloaded and hydrated.
export function MemberList() {
  const [members, setMembers] = useState(null)

  useEffect(() => {
    fetch('/api/members')
      .then((res) => res.json())
      .then(setMembers)
  }, [])

  if (!members) return <Spinner />
  return <List items={members} />
}
```

Nesting components like this produces a waterfall of dependent requests and scatters the loading UI across whichever components happen to fetch. Reading the data in a Server Component behind one boundary starts the query on the server before the bundle has downloaded, and puts the loading state where you chose to put it.

## Designing the fallback

### Skeletons that don't match the final geometry

A fallback that's smaller or larger than the content replacing it makes the browser reflow the page, and everything below it moves. That jump is [Cumulative Layout Shift](/docs/app/guides/streaming#cls-cumulative-layout-shift). The usual causes are a wrong row count, a wrong row height, a button or input narrower than the real one, missing icons, and a spinner standing in for a card.

Define the row box once and use it on both sides, so the two can't drift. Give the container a minimum height as well, and the full space is reserved before any data arrives:

```tsx filename="app/member-list.tsx"
const LIST_BOX = 'mt-4 min-h-[512px] divide-y divide-border'
const ROW_BOX = 'h-16'
const ROW_INNER = 'flex h-full items-center gap-3.5 px-4'

export function MemberRowsSkeleton({ rows = PAGE_SIZE }: { rows?: number }) {
  return (
    <>
      {Array.from({ length: rows }).map((_, i) => (
        <li key={i} className={ROW_BOX} aria-hidden>
          <div className={ROW_INNER}>
            <span className="skeleton size-9 rounded-full" />
            <span className="flex min-w-0 flex-1 flex-col gap-[3px]">
              <span className="skeleton h-[14px] w-[140px]" />
              <span className="skeleton h-3 w-[100px]" />
            </span>
          </div>
        </li>
      ))}
    </>
  )
}
```

Put the height on the same element in both, and give the placeholder the same DOM shape as the real row. Moving the height inward is enough to break it: with `h-16` on the row's inner `<a>` instead of its `<li>`, the real row comes out one pixel taller than its skeleton, because the `<li>` adds the list divider on top of a full-height child. One pixel per row is eight pixels of shift on a page of eight rows. Reload with the layout shift regions overlay enabled in your browser's dev tools and the list reports a shift on every load.

The placeholder is decorative, so it's `aria-hidden` and carries no text for a screen reader to announce. Keeping it in the same file as the component, built from the same box constants, is what keeps the two matched as the component changes.

Space outside the fallback shifts the page the same way, and a correct skeleton won't save a layout that leaves it unreserved. An image, video, or iframe without `width` and `height` or an `aspect-ratio` collapses until its file loads, which is why [`next/image`](/docs/app/api-reference/components/image) requires dimensions and why [`placeholder="blur"`](/docs/app/api-reference/components/image#placeholder) fills the box beforehand. A web font whose metrics differ from its fallback reflows every line of text when it swaps in, which [`next/font`](/docs/app/api-reference/components/font) handles through [`adjustFontFallback`](/docs/app/api-reference/components/font#adjustfontfallback), on by default. Anything inserted above existing content, such as a cookie banner or an alert bar, moves the whole page down after it looked settled, so reserve that space in the initial HTML or take the element out of flow.

> **Good to know**: Long lists have a related trap. [`content-visibility: auto`](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility) skips rendering rows outside the viewport, but it needs a [`contain-intrinsic-size`](https://developer.mozilla.org/en-US/docs/Web/CSS/contain-intrinsic-size) matching the real row height. Without one, the scroll height changes as rows enter the viewport, which produces CLS from the optimization rather than the problem.

### False empty states

Rendering a real state from data you don't have yet is worse than rendering a placeholder. "No members yet" while the query is in flight tells the user the team is empty, and the UI then flips to a full list a moment later. The same failure produces a default product type, a zero count, or a logged-out header that corrects itself.

The distinction is between "resolved and empty" and "not resolved yet". Decide the empty state from a value that has actually resolved. A count is cheap next to fetching rows, so it can settle the question before any row arrives:

```tsx filename="app/member-list.tsx"
export function MemberList({
  query,
  pageCount,
}: {
  query: string
  pageCount: number
}) {
  const total = countMembers(query)

  if (total === 0) {
    return <p>No members match “{query}”.</p>
  }

  return <MemberPages query={query} pageCount={pageCount} total={total} />
}
```

A Server Component that awaits its rows instead gets the same guarantee for free, because the code after the `await` only runs once the data exists. The failure is specific to the client, where the pending state and the resolved value share one variable and `undefined` gets treated as empty. Check for pending before checking the value, and let the fallback cover it rather than rendering a plausible alternative.

The resolved count is worth passing down. It tells each page's fallback how many rows that page will hold, which is what the next section needs.

### Fallbacks that never resolve

A loading state promises that content is coming, so it has to end in either content or an error. A section whose query throws leaves a skeleton pulsing forever unless something catches it.

Wrap a slow section in an [error boundary](/docs/app/getting-started/error-handling) at the same granularity as its `<Suspense>` boundary. A failure then shows an error in that section, and one failed section doesn't blank the rest of the page. See [error handling mid-stream](/docs/app/guides/streaming#error-handling-mid-stream) for how status codes behave once the stream has started.

A skeleton or spinner also reads as broken past about [10 seconds](https://www.nngroup.com/articles/response-times-3-important-limits/). For an operation you know runs long, show determinate progress such as a percent-done bar, and let the user keep working while it finishes.

## Ordering the reveal

### Popcorn loading

Popcorn loading is what happens when every section gets its own boundary. Each region appears the moment its own data arrives, in network order, and sections of unknown height push each other around as they land.

A member profile stacks two sections whose height nobody can predict. The bio might be one paragraph or three, and the activity feed might be two rows or eight, so no skeleton can reserve the right height for either. As siblings, the feed often paints high on the page and then gets shoved down when the bio above it arrives.

Nesting the feed's boundary inside the bio's fixes the order. A nested boundary can't reveal before its parent, so the sections appear top-down and a long bio grows into the space below it:

```tsx filename="app/member/[id]/page.tsx"
import { Suspense } from 'react'
import {
  BioText,
  BioTextSkeleton,
  ActivityRows,
  ActivityRowsSkeleton,
} from './profile'

export default function MemberPage({ params }: PageProps<'/member/[id]'>) {
  return (
    <main>
      <Suspense fallback={<BioTextSkeleton />}>
        {params.then(({ id }) => (
          <>
            <BioText id={Number(id)} />
            <Suspense fallback={<ActivityRowsSkeleton />}>
              <ActivityRows id={Number(id)} />
            </Suspense>
          </>
        ))}
      </Suspense>
    </main>
  )
}
```

Both queries still run in parallel. Nesting delays the reveal of a finished section, not its query.

Sibling boundaries are right when the regions are visually independent, such as dashboard cards in a grid, because each card can appear as soon as its data is ready and nothing below it has to move. One boundary around the whole stack is right when per-section reveals aren't worth the extra fallbacks.

> **Good to know**: The [profiling guide](/docs/app/guides/profiling-performance#step-2-find-content-gated-by-one-boundary) shows these sections streaming in the Performance panel, so you can confirm the queries run in parallel and spot a boundary that gates too much content.

### Stable labels that disappear and reappear

A label the app already knows doesn't belong in the fallback. When a section heading is drawn as a skeleton bar and then rendered again as real text, the same word leaves the DOM and re-enters it a frame later, and any reveal animation on that region animates a label that never changed.

Render the label as real text and let the fallback cover only what's actually unknown:

```tsx filename="app/member/[id]/page.tsx"
<SectionHeading>About</SectionHeading>

<Suspense fallback={<BioTextSkeleton />}>
  {params.then(({ id }) => (
    <BioText id={Number(id)} />
  ))}
</Suspense>
```

Where the label goes depends on whether its position is settled. "About" sits under a profile header whose skeleton is the same size as the real header, so its position is fixed from the first paint and it belongs in the shell. A heading below a variable-height section is different: its position isn't known until that section resolves, so putting it in the shell would only move it later. Render it inside the parent's boundary, still as real text, next to the fallback for its own rows:

```tsx filename="app/member/[id]/page.tsx"
<Suspense fallback={<BioTextSkeleton />}>
  {params.then(({ id }) => (
    <>
      <BioText id={Number(id)} />

      <SectionHeading>Recent activity</SectionHeading>
      <Suspense fallback={<ActivityRowsSkeleton />}>
        <ActivityRows id={Number(id)} />
      </Suspense>
    </>
  ))}
</Suspense>
```

Either way the label is never a skeleton bar. The rule is about what the fallback contains, not about how far up the tree the label goes.

This applies to container chrome as well as headings. Cards, borders, table headers, and empty list containers can all render immediately, leaving the fallback responsible for rows alone.

### Content that pops in

By default a fallback is replaced by real content in a single frame. Wrapping the streamed content in React's [`<ViewTransition>`](https://react.dev/reference/react/ViewTransition) crossfades the two instead. View transitions work in the App Router with no configuration.

Reuse one wrapper for every reveal. `enter="auto"` animates the first time content appears, and `default="none"` skips animating later updates of the same region:

```tsx filename="app/crossfade.tsx"
import { ViewTransition } from 'react'

export function Crossfade({ children }: { children: React.ReactNode }) {
  return (
    <ViewTransition enter="auto" default="none">
      {children}
    </ViewTransition>
  )
}
```

Wrap the fallback in a matching `exit="auto"` so the skeleton fades out as the content fades in:

```tsx filename="app/member/[id]/page.tsx"
<Suspense
  fallback={
    <ViewTransition exit="auto" default="none">
      <BioTextSkeleton />
    </ViewTransition>
  }
>
  {params.then(({ id }) => (
    <Crossfade>
      <BioText id={Number(id)} />
    </Crossfade>
  ))}
</Suspense>
```

Content that's already in the static shell has nothing to reveal, so don't animate it, and don't wrap a subtree that re-renders on every keystroke or the enter animation fires on every character.

A reveal runs while the page is still streaming and hydrating, when the main thread is busiest. Animate only `opacity` and `transform`, which the compositor runs on its own thread. A shimmer that animates `background-position`, or a skeleton that animates `height`, forces paint or layout on every frame and competes with hydration for the same thread. Keep the placeholder animation quiet for the same reason. A slow opacity pulse marks the region as loading without competing with content that has already arrived beside it.

> **Good to know**: Honor [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) for users who ask for less motion. See [Respecting reduced motion](/docs/app/guides/view-transitions#respecting-reduced-motion) for the CSS, and [Designing view transitions](/docs/app/guides/view-transitions) for directional navigation and shared-element morphs.

## Handling updates

### Updates that wipe the current results

The first-load fallback is for the first load. Reusing it when the user searches or filters replaces results they're reading with a skeleton, and every keystroke does it again.

Next.js wraps App Router navigations in a transition, and during a transition `<Suspense>` keeps content it has already revealed. The current rows stay on screen until the next result is ready, which leaves the pending signal to the control that started the update:

```tsx filename="app/search-shell.tsx"
'use client'

import { useTransition } from 'react'
import { useRouter, useSearchParams } from 'next/navigation'

export function SearchShell({ children }: { children: React.ReactNode }) {
  const router = useRouter()
  const searchParams = useSearchParams()
  const [isPending, startTransition] = useTransition()

  function onSearch(value: string) {
    startTransition(() => {
      router.replace(value ? `/?q=${encodeURIComponent(value)}` : '/', {
        scroll: false,
      })
    })
  }

  return (
    <div>
      <input
        type="search"
        defaultValue={searchParams.get('q') ?? ''}
        onChange={(e) => onSearch(e.target.value)}
        aria-label="Search members"
      />
      <span className="pending" data-active={isPending ? '' : undefined} />
      <div
        className="transition-opacity data-[pending]:opacity-60"
        data-pending={isPending ? '' : undefined}
      >
        {children}
      </div>
    </div>
  )
}
```

The wrapper sets `data-pending`, which dims the stale rows until the next results replace them. Changing the `key` on the `<Suspense>` boundary would remount it and bring the first-load skeleton back, so leave the key alone.

The input stays uncontrolled, which also protects [INP](/docs/app/guides/streaming#inp-interaction-to-next-paint). A controlled input that re-renders a large subtree on every keystroke delays the keypress itself, while an uncontrolled field paired with a transition keeps typing off that path.

See [Building interactive apps](/docs/app/guides/interactive-apps) for the mutation side of this, including optimistic updates and form feedback.

### Spinners that flash on fast operations

An indicator bound straight to a pending flag appears the instant the update starts, even when the response arrives a few milliseconds later. The spinner appears and disappears within a few frames, on an operation that was already fast.

Start the indicator invisible and reveal it only after a short delay, so a fast response resolves before it's ever seen:

```css filename="app/globals.css"
/* Invisible for 150ms, so a fast search resolves before it is ever seen. */
.pending {
  opacity: 0;
}

.pending[data-active] {
  animation:
    pending-in 0.2s cubic-bezier(0.23, 1, 0.32, 1) 0.15s forwards,
    spin 0.7s linear infinite;
}

@keyframes pending-in {
  to {
    opacity: 1;
  }
}

@keyframes spin {
  to {
    transform: rotate(360deg);
  }
}
```

A search that resolves in under 150ms never shows the spinner. `<Suspense>` applies a similar window of its own before showing a fallback, so a fast stream doesn't flash a skeleton either.

Once the spinner is visible, hold it. Clearing `data-active` the moment the pending flag turns false still flickers when the response is only slightly slower than the delay. And when the surrounding UI already communicates the wait, such as rows dimming during a search, an indicator can be dropped entirely.

### Pagination that remounts the list

"Load more" should add rows, not replace them. Rekeying the list, or widening one boundary so it now covers page two as well, unmounts rows the user is already looking at, resets scroll position, and animates content that never changed.

Give each page its own boundary and a stable key. Earlier pages keep their DOM nodes, and on a fresh load each page's fallback reserves exactly the rows that page will hold:

```tsx filename="app/member-list.tsx"
function MemberPages({ query, pageCount, total }: Props) {
  return (
    <ul className={LIST_BOX}>
      {Array.from({ length: pageCount }, (_, i) => i + 1).map((page) => (
        // Stable key per page, so page 1 is untouched when page 2 arrives
        <Suspense
          key={page}
          fallback={
            <MemberRowsSkeleton
              rows={Math.min(PAGE_SIZE, total - (page - 1) * PAGE_SIZE)}
            />
          }
        >
          <MemberRows query={query} page={page} />
        </Suspense>
      ))}
    </ul>
  )
}
```

Size the last page's fallback to the rows that page actually holds, not a full `PAGE_SIZE`. A partial final page whose fallback reserves eight rows for four shifts the moment it resolves.

Where the pending feedback comes from depends on where the page count lives.

With the count in the URL, pressing "Load more" is a navigation, so it runs as a transition, and the server re-renders pages 1 through N rather than only the new page. React commits nothing until the pages already on screen have re-resolved, so the new boundary's fallback never gets a window on screen. The button is the only thing that can report the wait. Keep its label centered in a fixed-width control so swapping the text can't resize it.

Accumulating the pages in client state instead keeps each resolved page as settled state that is never re-fetched. Appending one more page mounts a new boundary against a pending promise, so that boundary shows its fallback immediately, below rows that never moved:

```tsx filename="app/paginator.tsx"
'use client'

export function Paginator({ initialPage, renderPage, skeleton }: Props) {
  const [pages, setPages] = useState([initialPage])

  function loadMore() {
    // A promise, appended unresolved. Earlier pages are already settled.
    setPages((prev) => [...prev, renderPage(prev.length + 1)])
  }

  return pages.map((page, i) => (
    <Suspense key={i} fallback={skeleton}>
      <PageContent page={page} onLoadMore={loadMore} />
    </Suspense>
  ))
}
```

The trade is real in both directions. The URL version is shareable and survives a reload, and it costs a re-render of every page on screen. The client version fetches only the new page and can show its fallback, and it gives up the shareable URL, loses its pages on reload, and sits outside revalidation. Pick per feed, not per app.

A "Load more" button also shouldn't outrun the list it belongs to. Whether the button is needed depends on data, so it belongs behind its own boundary, nested in the loading hierarchy under the list rather than inside the list markup. Have it read the same query the last page's rows read, so it can never resolve first and appear above rows that haven't arrived:

```tsx filename="app/member-list.tsx"
<Suspense fallback={<LoadMoreSlot />}>
  <LoadMoreGate page={pageCount} />
</Suspense>
```

Give that boundary a fallback with the button's dimensions. Its presence is unknown until the query resolves, and an unreserved control appearing under a list pushes the page down when it arrives, then again when it turns out not to be needed.

## Verifying the sequence

Fallbacks are hard to review because a good one flashes by. The [React Developer Tools](https://react.dev/learn/react-developer-tools) let you suspend a selected `<Suspense>` boundary so its fallback stays on screen while you check its sizing, contrast, and dark mode. The Next.js DevTools freeze the initial and prefetched UI for a route, which shows exactly which parts are fallback. See [Visualize loading states with the Next.js DevTools](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools).

Then throttle the network and CPU. Fallbacks that never appear on a local machine appear on a mid-range phone, and that's the sequence most of your users get.

Tests usually cover the final loaded page and skip the frame that these problems live in. The `@next/playwright` [`instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests) helper asserts on the UI that's visible immediately, before dynamic content streams in, so a boundary that drifts to the wrong place fails the test:

```typescript filename="e2e/loading.test.ts"
import { test, expect } from '@playwright/test'
import { instant } from '@next/playwright'

test('the directory shell is instant', async ({ page }) => {
  await page.goto('/')

  await instant(page, async () => {
    // Stable UI is in the shell
    await expect(page.locator('h1')).toContainText('Team directory')
    // The fallback reserves the space the rows will occupy
    const skeleton = page.locator('ul[aria-hidden]')
    await expect(skeleton).toBeVisible()
    expect((await skeleton.boundingBox())?.height).toBeGreaterThanOrEqual(512)
  })

  await expect(page.getByRole('listitem').first()).toBeVisible()
})
```

Assert on both halves. A marker proves the right content is in the shell, and a dimension proves the fallback reserves the space, which is the part that regresses silently when a skeleton and its component drift apart.
