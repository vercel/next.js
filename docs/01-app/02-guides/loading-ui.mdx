Good loading UI preserves what the app already knows while uncertain content resolves. Poorly placed boundaries can hide stable UI, stack competing indicators, or shift sections as they stream.

Use the patterns below independently or together to keep first loads and updates stable.

## Example

We'll fix the loading UI of a team directory that lists members, searches them, paginates them, and links to each member's profile.

Explore the finished example:

- [Demo](https://loading-ui-demo.labs.vercel.dev)
- [Code](https://github.com/vercel-labs/loading-ui-demo)

> **Good to know**: The demo runs with [Cache Components](/docs/app/guides/migrating-to-cache-components) and [Partial Prefetching](/docs/app/guides/adopting-partial-prefetching) enabled, which is why the shell appears instantly on navigation. The fixes below don't depend on either.

## Getting the shell to paint

### Top-level awaits that block the shell

An await at the top of a page component delays all UI below it until the await resolves, unless a parent boundary can show a fallback. Stable UI that doesn't need the result waits too.

This often happens with `params`, `searchParams`, a query, or a [`notFound()`](/docs/app/api-reference/functions/not-found) decision:

```tsx filename="app/member/[id]/page.tsx"
// Blocks the shell. The back link can't paint until the member query resolves.
export default async function MemberPage({
  params,
}: PageProps<'/member/[id]'>) {
  const { id } = await params
  const member = await getMember(Number(id))
  if (!member) notFound()

  return (
    <main>
      <Link href="/">Directory</Link>
      <ProfileHeader member={member} />
    </main>
  )
}
```

For a read that gates only one section, keep the page component synchronous and move the read into the component that needs it. The page becomes static markup around focused boundaries that Next.js can prerender:

```tsx filename="app/member/[id]/page.tsx"
export default function MemberPage({ params }: PageProps<'/member/[id]'>) {
  return (
    <main>
      {/* Static, so it goes out with the first HTML */}
      <Link href="/">Directory</Link>

      <Suspense fallback={<ProfileHeaderSkeleton />}>
        {params.then(({ id }) => (
          <ProfileHeader id={Number(id)} />
        ))}
      </Suspense>
    </main>
  )
}
```

The `notFound()` check moves inside `ProfileHeader`, where it runs against data that component already has.

This lets the shell stream, but the streamed not-found response has a `200` status and a `noindex` tag. To return a real `404`, check the resource before streaming or in [`proxy`](/docs/app/api-reference/file-conventions/proxy). See [Status codes](/docs/app/api-reference/file-conventions/loading#status-codes).

Keep page-wide authorization checks and redirects before any protected UI streams. Move a read only when its result gates that section rather than the whole response.

We can confirm the result with [`next build`](/docs/app/api-reference/cli/next#next-build-options). The route is now prerendered up to its boundaries:

```bash filename="Terminal"
Route (app)
┌ ◐ /
└ ◐ /member/[id]

◐  (Partial Prerender)  prerendered as static HTML with dynamic server-streamed content
```

> **Good to know**: With [Cache Components](/docs/app/getting-started/caching), awaiting uncached data outside a boundary is a [build-time error](/docs/messages/blocking-prerender-dynamic) rather than a silent performance cliff, because the route can no longer prerender a shell.

### Stable UI hidden behind one coarse boundary

A boundary hides everything inside it until its slowest child is ready, so anything inside one that could have rendered immediately waits for no reason. Headers, titles, navigation, search controls, and empty containers all belong outside.

Put the boundary around the part that's actually slow:

```tsx filename="app/page.tsx"
import { Suspense } from 'react'
import { Stats } from './stats'
import { MemberList, DirectorySkeleton } from './member-list'

export default function Page({ searchParams }: PageProps<'/'>) {
  return (
    <main>
      <header>
        <h1>Team directory</h1>
        {/* Synchronous, so it never sits behind a fallback */}
        <Stats />
      </header>

      <Suspense fallback={<DirectorySkeleton />}>
        {searchParams.then(({ q, page }) => (
          <MemberList
            query={typeof q === 'string' ? q : ''}
            pageCount={Math.max(1, Number(page) || 1)}
          />
        ))}
      </Suspense>
    </main>
  )
}
```

The header and the skeleton go out with the first HTML, and the list replaces the skeleton when its query resolves. If `<Stats />` sat inside the boundary, it would wait behind the skeleton too.

Controls belong outside too. A search input that only writes the query to the URL can stay in the shell. Reading the query back makes the input request-dependent and requires a placeholder of its own. Seed the initial value with the pattern from [Preventing flash before hydration](/docs/app/guides/preventing-flash-before-hydration).

When `Stats` has to await something, even 250ms, it can't render in the shell, and it also shouldn't join the list's boundary and wait behind the slow query. Give it its own boundary with a placeholder that reserves its height:

```tsx filename="app/page.tsx"
<header>
  <h1>Team directory</h1>

  <Suspense fallback={<p className="h-5" aria-hidden />}>
    <Stats />
  </Suspense>
</header>
```

The placeholder only has to hold the space the real stats will occupy. Here, `h-5` matches the line height of the final text. The header still paints with the first HTML, and the two reads resolve on their own schedules instead of the faster one inheriting the slower one's wait.

When the likely [Largest Contentful Paint](/docs/app/guides/streaming#lcp-largest-contentful-paint) element doesn't depend on slow data, keep it in the [static shell](/docs/app/guides/streaming#the-static-shell). Empty skeleton boxes aren't LCP candidates, so streaming a prominent image or headline delays LCP until the real content arrives.

For an above-the-fold image, use [`loading="eager"`](/docs/app/api-reference/components/image#loading) or [`fetchPriority="high"`](https://developer.mozilla.org/docs/Web/API/HTMLImageElement/fetchPriority) when appropriate.

### Competing loading signals

One region should produce one loading signal. Apps accumulate them by adding each in isolation, and the user ends up watching a route-level `loading.tsx`, then a page-level skeleton, then a spinner inside a card, for a single page load.

A route-level [`loading.tsx`](/docs/app/api-reference/file-conventions/loading) wraps the page and child segments below its folder. It doesn't wrap the layout, template, or error boundary in the same segment.

Once part of the page can paint sooner, place `<Suspense>` around the slow region instead. See [When to use `loading.js` vs `<Suspense>`](/docs/app/guides/streaming#when-to-use-loadingjs-vs-suspense).

Layouts add signals the same way. A `loading.tsx` above a shared layout doesn't show on client navigations, because React re-enters the tree at that layout. An overlay added to compensate then appears on the first load when the fallback already covers it. See [Ensuring instant navigations](/docs/app/guides/instant-navigation).

A section that already shows a skeleton doesn't need a second spinner for a query inside it. A `<Link>` pointing to a destination with its own shell doesn't need one either. The destination's skeletons appear when the navigation commits. When the destination has no shell, [`useLinkStatus`](/docs/app/api-reference/functions/use-link-status#gracefully-handling-fast-navigation) gives the link its own pending state.

### Data fetching split across client effects

Fetching in a client effect puts every request behind the JavaScript bundle. The shell paints empty, the requests start after hydration, and each component that fetches for itself adds a round trip and its own `isLoading` spinner:

```tsx filename="app/member-list.tsx"
'use client'

// The request can't start until this component has downloaded and hydrated.
export function MemberList() {
  const [members, setMembers] = useState(null)

  useEffect(() => {
    fetch('/api/members')
      .then((res) => res.json())
      .then(setMembers)
  }, [])

  if (!members) return <Spinner />
  return <List items={members} />
}
```

Nesting components like this produces a waterfall of dependent requests and scatters the loading UI across whichever components happen to fetch. Reading the data in a Server Component behind one boundary starts the query on the server before the bundle has downloaded, and puts the loading state where you chose to put it.

## Designing the fallback

### Skeletons that don't match the final geometry

A fallback that's smaller or larger than the content replacing it makes the browser reflow the page, and everything below it moves. That jump is [Cumulative Layout Shift](/docs/app/guides/streaming#cls-cumulative-layout-shift).

The usual causes are a wrong row count or height, mismatched control sizes, missing icons, and a spinner standing in for a card.

Define the row box once and use it for both the fallback and the content. Shared class-name constants, a CSS module class, or one stylesheet rule all prevent the two versions from drifting.

Give the container a minimum height too, so it reserves the full space before data arrives:

```tsx filename="app/member-list.tsx"
const LIST_BOX = 'mt-4 min-h-[512px] divide-y divide-border'
const ROW_BOX = 'h-16'
const ROW_INNER = 'flex h-full items-center gap-3.5 px-4'

export function MemberListSkeleton({ rows = PAGE_SIZE }: { rows?: number }) {
  return (
    <ul className={LIST_BOX} aria-hidden>
      <MemberRowsSkeleton rows={rows} />
    </ul>
  )
}

export function MemberRowsSkeleton({ rows = PAGE_SIZE }: { rows?: number }) {
  return (
    <>
      {Array.from({ length: rows }).map((_, i) => (
        <li key={i} className={ROW_BOX}>
          <div className={ROW_INNER}>
            <span className="skeleton size-9 rounded-full" />
            <span className="flex min-w-0 flex-1 flex-col gap-[3px]">
              <span className="skeleton h-[14px] w-[140px]" />
              <span className="skeleton h-3 w-[100px]" />
            </span>
          </div>
        </li>
      ))}
    </>
  )
}
```

Put the height on the same element and give the placeholder the same DOM shape as the real row. Moving `h-16` from the `<li>` to its inner `<a>` makes the real row one pixel taller because the divider sits outside the full-height child. That becomes eight pixels of shift across eight rows.

Reload with the layout shift regions overlay enabled in your browser's DevTools to see the list move.

The placeholder is decorative, so it's `aria-hidden` and carries no text for a screen reader to announce. Keeping it in the same file as the component, built from the same box constants, is what keeps the two matched as the component changes.

Space outside the fallback can shift the page too:

- **Media**: Give images, videos, and iframes dimensions or an `aspect-ratio`. [`next/image`](/docs/app/api-reference/components/image) requires `width` and `height` unless you use a static import or [`fill`](/docs/app/api-reference/components/image#fill).
- **Fonts**: A web font with different metrics from its fallback reflows text when it loads. [`next/font`](/docs/app/api-reference/components/font) uses [`adjustFontFallback`](/docs/app/api-reference/components/font#adjustfontfallback) by default to reduce this shift.
- **Inserted content**: Reserve space in the initial HTML for a cookie banner or alert bar, or take the element out of flow so it doesn't move settled content.

### False empty states

Rendering a real state from data you don't have yet is worse than rendering a placeholder. "No members yet" while the query is in flight tells the user the team is empty, and the UI then flips to a full list a moment later. The same failure produces a default product type, a zero count, or a logged-out header that corrects itself.

The distinction is between "resolved and empty" and "not resolved yet". Decide the empty state from a value that has resolved. In this example, `countMembers()` reads a local array synchronously, so it can settle the question before the rows arrive:

```tsx filename="app/member-list.tsx"
export function MemberList({
  query,
  pageCount,
}: {
  query: string
  pageCount: number
}) {
  const total = countMembers(query)

  if (total === 0) {
    return <p>No members match “{query}”.</p>
  }

  return <MemberPages query={query} pageCount={pageCount} total={total} />
}
```

A Server Component that awaits its rows gets the same guarantee because the code after the `await` runs only when the data exists.

A common client-side version of this bug treats the pending value, such as `undefined`, as an empty result. Check for pending before checking the value, and let the fallback cover it rather than rendering a plausible alternative.

Pass the resolved count down. Each page's fallback uses it to reserve the number of rows that page will hold.

### Loading states without an error path

A loading state should end in content or an error. A query that throws should reach an error boundary at the same granularity as its `<Suspense>` boundary. A promise that never settles needs a timeout or cancellation in the data layer.

A component-level error boundary created with [`catchError`](/docs/app/api-reference/functions/catchError) lets one section show an error without blanking the rest of the page. Wrap the boundary around the same region as its loading state:

```tsx filename="app/page.tsx"
<ErrorBoundary title="Directory unavailable">
  <Suspense fallback={<DirectorySkeleton />}>
    <MemberList />
  </Suspense>
</ErrorBoundary>
```

See [error handling mid-stream](/docs/app/guides/streaming#error-handling-mid-stream) for how status codes behave after streaming starts.

For work expected to exceed about [10 seconds](https://www.nngroup.com/articles/response-times-3-important-limits/), show progress and let the user continue or interrupt it.

## Ordering the reveal

### Popcorn loading

Popcorn loading is what happens when every section gets its own boundary. Each region appears the moment its own data arrives, in network order, and sections of unknown height push each other around as they land.

A member profile stacks two sections whose height nobody can predict. The bio might be one paragraph or three, and the activity feed might be two rows or eight, so no skeleton can reserve the right height for either. As siblings, the feed often appears first, high on the page, and then moves down when the bio above it arrives.

Nesting the feed's boundary inside the bio's fixes the order. A nested boundary can't reveal before its parent, so the sections appear top-down and a long bio grows into the space below it:

```tsx filename="app/member/[id]/page.tsx"
import { Suspense } from 'react'
import {
  BioText,
  BioTextSkeleton,
  ActivityRows,
  ActivityRowsSkeleton,
} from './profile'

export default function MemberPage({ params }: PageProps<'/member/[id]'>) {
  return (
    <main>
      <Suspense fallback={<BioTextSkeleton />}>
        {params.then(({ id }) => (
          <>
            <BioText id={Number(id)} />
            <Suspense fallback={<ActivityRowsSkeleton />}>
              <ActivityRows id={Number(id)} />
            </Suspense>
          </>
        ))}
      </Suspense>
    </main>
  )
}
```

Nesting boundaries doesn't serialize the queries by itself. In this example, both async components start during the same server render, while the nested boundary controls their reveal order.

Sibling boundaries are right when the regions are visually independent, such as dashboard cards in a grid, because each card can appear as soon as its data is ready and nothing below it has to move. One boundary around the whole stack is right when per-section reveals aren't worth the extra fallbacks.

> **Good to know**: Use server logs or tracing to confirm that queries start in parallel. The Chrome Performance panel shows when each streamed section paints and helps spot a boundary that gates too much content.

### Stable labels that disappear and reappear

A label the app already knows doesn't belong in the fallback. When a section heading is drawn as a skeleton bar and then rendered again as real text, the same word leaves the DOM and re-enters it a frame later, and any reveal animation on that region animates a label that never changed.

Render the label as real text and let the fallback cover only what's actually unknown:

```tsx filename="app/member/[id]/page.tsx"
<SectionHeading>About</SectionHeading>

<Suspense fallback={<BioTextSkeleton />}>
  {params.then(({ id }) => (
    <BioText id={Number(id)} />
  ))}
</Suspense>
```

Place the label where its position becomes stable. "About" sits below a profile header whose fallback matches the final size, so the label can render in the shell.

A heading below variable-height content can't settle until that content resolves. Render it inside the parent boundary as real text, next to the fallback for its own rows:

```tsx filename="app/member/[id]/page.tsx"
<Suspense fallback={<BioTextSkeleton />}>
  {params.then(({ id }) => (
    <>
      <BioText id={Number(id)} />

      <SectionHeading>Recent activity</SectionHeading>
      <Suspense fallback={<ActivityRowsSkeleton />}>
        <ActivityRows id={Number(id)} />
      </Suspense>
    </>
  ))}
</Suspense>
```

Either way the label is never a skeleton bar. The rule is about what the fallback contains, not about how far up the tree the label goes.

This applies to container chrome as well as headings. Cards, borders, table headers, and empty list containers can all render immediately, leaving the fallback responsible for rows alone.

### Content that pops in

By default a fallback is replaced by real content in a single frame. Wrapping the streamed content in React's [`<ViewTransition>`](https://react.dev/reference/react/ViewTransition) crossfades the two instead. View transitions work in the App Router with no configuration.

Reuse one wrapper for every reveal. `enter="auto"` animates the first time content appears, and `default="none"` skips animating later updates of the same region:

```tsx filename="app/crossfade.tsx"
import { ViewTransition } from 'react'

export function Crossfade({ children }: { children: React.ReactNode }) {
  return (
    <ViewTransition enter="auto" default="none">
      {children}
    </ViewTransition>
  )
}
```

Wrap the fallback in a matching `exit="auto"` so the skeleton fades out as the content fades in:

```tsx filename="app/member/[id]/page.tsx"
<Suspense
  fallback={
    <ViewTransition exit="auto" default="none">
      <BioTextSkeleton />
    </ViewTransition>
  }
>
  {params.then(({ id }) => (
    <Crossfade>
      <BioText id={Number(id)} />
    </Crossfade>
  ))}
</Suspense>
```

Content that's already in the static shell has nothing to reveal, so don't animate it. Keep the wrapper around the region that is inserted, and use `default="none"` to prevent unrelated updates from animating it.

Reveal animations run while the page may still be streaming and hydrating. Prefer `opacity` and `transform`, which generally avoid layout and paint work.

Avoid animating layout properties such as `height`, and verify the result in the Performance panel. A slow opacity pulse can mark a region as loading without drawing attention from content that has arrived.

> **Good to know**: Honor [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) for users who ask for less motion. See [Respecting reduced motion](/docs/app/guides/view-transitions#respecting-reduced-motion) for the CSS, and [Designing view transitions](/docs/app/guides/view-transitions) for directional navigation and shared-element morphs.

## Handling updates

### Updates that wipe the current results

Reusing the first-load fallback when the user searches or filters replaces the results they are reading with a skeleton, and every keystroke does it again.

Next.js wraps App Router navigations in a transition, and during a transition `<Suspense>` keeps content it has already revealed. The current rows stay on screen until the next result is ready, which leaves the pending signal to the control that started the update:

```tsx filename="app/search-shell.tsx"
'use client'

import { useTransition } from 'react'
import { useRouter } from 'next/navigation'

export function SearchShell({ children }: { children: React.ReactNode }) {
  const router = useRouter()
  const [isPending, startTransition] = useTransition()

  function onSearch(value: string) {
    startTransition(() => {
      router.replace(value ? `/?q=${encodeURIComponent(value)}` : '/', {
        scroll: false,
      })
    })
  }

  return (
    <div>
      <input
        type="search"
        onChange={(e) => onSearch(e.target.value)}
        aria-label="Search members"
      />
      <span className="pending" data-active={isPending ? '' : undefined} />
      <div
        className="transition-opacity data-[pending]:opacity-60"
        data-pending={isPending ? '' : undefined}
      >
        {children}
      </div>
    </div>
  )
}
```

The wrapper sets `data-pending`, which dims the stale rows until the next results replace them. Changing the `key` on the `<Suspense>` boundary would remount it and bring the first-load skeleton back, so leave the key alone.

The complete demo seeds and synchronizes the uncontrolled input with the URL using the pattern from [Preventing flash before hydration](/docs/app/guides/preventing-flash-before-hydration).

The uncontrolled input avoids a synchronous state update on every keystroke. The transition lets React keep typing responsive while the navigation updates the results.

See [Building interactive apps](/docs/app/guides/interactive-apps) for the mutation side of this, including optimistic updates and form feedback.

### Spinners that flash on fast operations

An indicator bound straight to a pending flag appears the instant the update starts, even when the response arrives a few milliseconds later. The spinner appears and disappears within a few frames, on an operation that was already fast.

Start the indicator invisible and reveal it only after a short delay, so a fast response resolves before it's ever seen:

```css filename="app/globals.css"
/* Invisible for 150ms, so a fast search resolves before it is ever seen. */
.pending {
  opacity: 0;
}

.pending[data-active] {
  animation:
    pending-in 0.2s cubic-bezier(0.23, 1, 0.32, 1) 0.15s forwards,
    spin 0.7s linear infinite;
}

@keyframes pending-in {
  to {
    opacity: 1;
  }
}

@keyframes spin {
  to {
    transform: rotate(360deg);
  }
}
```

A search that resolves inside the delay never shows the spinner. The exact delay is a design choice. A range of 100ms to 200ms keeps fast responses silent without leaving a slower one unacknowledged.

A delayed pending hint is also useful with [`useLinkStatus`](/docs/app/api-reference/functions/use-link-status#gracefully-handling-fast-navigation) when a navigation may finish before the indicator becomes helpful.

If the surrounding UI already communicates the wait, such as rows dimming during a search, omit the indicator.

### Pagination that remounts the list

"Load more" should add rows, not replace them. Rekeying the list, or widening one boundary to cover page two, unmounts rows the user is reading and discards their DOM state.

Give each page its own boundary and a stable key, so the rows already on screen keep their DOM nodes when the next page arrives:

```tsx filename="app/member-list.tsx"
<ul>
  {pageNumbers.map((page) => (
    // Stable key per page, so page 1 is untouched when page 2 arrives
    <Suspense key={page} fallback={<MemberRowsSkeleton rows={rowsOn(page)} />}>
      <MemberRows page={page} />
    </Suspense>
  ))}
</ul>
```

Size each page's fallback to the rows that page will actually hold. A partial final page whose fallback reserves eight rows for four shifts the moment it resolves.

Reserve the button's slot too. Whether a "Load more" is needed at all depends on data, so an unreserved control pushes the page down when it arrives, and again when the last page turns out not to need one.

Put the pending state on the button. The rows above the button are deliberately left alone, so nothing else on screen changes to acknowledge the click. Swap the label and add an indicator beside it in a fixed-size control, so the box can't resize while it reports.

## Verifying the sequence

Fallbacks are hard to review because a good one flashes by. The [React Developer Tools](https://react.dev/learn/react-developer-tools) let you suspend a selected `<Suspense>` boundary while you check its sizing, contrast, and dark mode.

The Next.js DevTools freeze a route's initial and prefetched UI, which shows which parts are fallbacks. See [Visualize loading states with the Next.js DevTools](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools).

Then test representative network and CPU profiles. A fallback that disappears on a fast local machine may stay visible on a slower device.

Measure layout stability rather than judging it by eye. A `layout-shift` [PerformanceObserver](https://developer.mozilla.org/en-US/docs/Web/API/LayoutShift) reports each shift and the affected elements. Run this in the browser's DevTools Console:

```js filename="DevTools Console"
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.hadRecentInput) continue
    console.log(entry.value, entry.sources)
  }
}).observe({ type: 'layout-shift', buffered: true })
```

Run it across the journeys the page supports, not only the first load. The sources include the affected nodes and their previous and current rectangles, which expose a one-pixel row mismatch or a placeholder that collapses to zero height.

Tests usually cover the final loaded page and skip the frame that these problems live in. The `@next/playwright` [`instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests) helper asserts on the UI that's visible immediately, before dynamic content streams in, so a boundary that drifts to the wrong place fails the test:

```ts filename="e2e/loading.test.ts"
import { test, expect } from '@playwright/test'
import { instant } from '@next/playwright'

test('the directory shell is instant', async ({ page, baseURL }) => {
  await instant(
    page,
    async () => {
      await page.goto('/')
      // Stable UI is in the shell
      await expect(page.locator('h1')).toContainText('Team directory')
      // The fallback reserves the space the rows will occupy
      const skeleton = page.locator('ul[aria-hidden]')
      await expect(skeleton).toBeVisible()
      await expect(skeleton).toHaveCSS('min-height', '512px')
    },
    { baseURL }
  )

  await expect(page.getByRole('listitem').first()).toBeVisible()
})
```

A marker proves the right content is in the shell, and the CSS assertion proves the fallback reserves its space. That second half can regress silently when a skeleton and its component drift apart.
