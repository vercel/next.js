Before Cache Components, static and dynamic rendering were primarily a route-level choice. [Route segment configs](/docs/app/guides/caching-without-cache-components#dynamic) such as `dynamic = 'force-static'`, `dynamic = 'force-dynamic'`, and `dynamic = 'error'` controlled whether the entire route was prerendered, rendered on demand, or failed when it could not be prerendered.

[Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents) moves this boundary to the component and function level. A single route can have a static shell, cached content, and request-specific content that streams in later. In most cases, this mix provides useful UI early without requiring the entire route to be static.

However, some output must not introduce request-time server work. You may need predictable rendering performance, want to avoid request-time compute, or want to protect a route that is expected to remain fully prerendered. In these cases, [`ensureStatic`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic) makes the static requirement explicit so later changes cannot silently introduce request-time rendering.

This guide explains where static output can be produced during navigation, then applies each `ensureStatic` level to a worked example. You will also use the development overlay and build errors to find work that does not meet the selected requirement.

## Choose how much output must be static

Static output is produced without request-specific data, so Next.js can generate it before a request and use it across requests. With [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching), a default `<Link>` loads the destination's [App Shell](/docs/app/glossary#app-shell). Setting `prefetch={true}` can also load static or cached [URL-specific content](/docs/app/guides/optimizing-prefetching#resolve-url-data-at-prefetch-time). The navigation request returns the remaining server-rendered content after the user follows the link.

`ensureStatic` lets you require progressively more of this output to remain static:

- **`'shell'`** keeps the App Shell static. Request-specific content can render during a later per-link prefetch or navigation.
- **`'prefetch'`** keeps the App Shell and per-link prefetches static. Request-specific content waits for navigation.
- **`'navigation'`** requires the complete server-rendered route to be static. Because there is no later server-rendering stage, request-specific or uncached server work produces a validation error.

Each level includes the requirements before it. The following example starts with the App Shell and progressively extends the static requirement through the complete route.

For more granular control, [`prefetch()`](/docs/app/api-reference/functions/prefetch) keeps one subtree out of the App Shell, while [`navigation()`](/docs/app/api-reference/functions/navigation) keeps it out of both the App Shell and per-link prefetches. `ensureStatic` takes the opposite approach: instead of choosing the subtree to defer, you declare which route output must remain static. See [Excluding content from a prefetch](/docs/app/guides/optimizing-prefetching#exclude-content-from-a-prefetch) for the subtree-level approach.

## Example

Consider an online store with a shared layout, product pages, and editorial buying guides. The shared storefront should always have a static shell, product links should prefetch cached summaries without running live inventory queries, and buying guides should be fully prerendered.

You will add the static requirements after first establishing the routes and their data access.

Enable [Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents) and [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching):

```ts filename="next.config.ts" highlight={4,5}
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

Start with these routes:

```text filename="Folder structure"
app/
└── store/
    ├── layout.tsx
    ├── page.tsx
    ├── products/
    │   └── [slug]/
    │       └── page.tsx
    └── guides/
        └── [id]/
            └── page.tsx
```

The shared layout renders the store navigation:

```tsx filename="app/store/layout.tsx"
import Link from 'next/link'

export default function StoreLayout({ children }: LayoutProps<'/store'>) {
  return (
    <>
      <nav>
        <Link href="/store">Products</Link>
        <Link href="/store/guides">Buying guides</Link>
      </nav>
      <main>{children}</main>
    </>
  )
}
```

The catalog links to each product without opting into a per-link prefetch:

```tsx filename="app/store/page.tsx"
import Link from 'next/link'
import { getProducts } from '@/lib/store'

export default async function StorePage() {
  const products = await getProducts()

  return (
    <ul>
      {products.map((product) => (
        <li key={product.slug}>
          <Link href={`/store/products/${product.slug}`}>{product.name}</Link>
        </li>
      ))}
    </ul>
  )
}
```

Each product page renders a cached product summary and current inventory. The two parts have separate `<Suspense>` boundaries so they can become available at different times:

```tsx filename="app/store/products/[slug]/page.tsx"
import { Suspense } from 'react'
import { getInventory, getProduct } from '@/lib/store'

export default function ProductPage({
  params,
}: PageProps<'/store/products/[slug]'>) {
  return (
    <>
      <Suspense fallback={<p>Loading product...</p>}>
        <ProductDetails params={params} />
      </Suspense>
      <Suspense fallback={<p>Checking availability...</p>}>
        <Inventory params={params} />
      </Suspense>
    </>
  )
}

type Params = PageProps<'/store/products/[slug]'>['params']

async function ProductDetails({ params }: { params: Params }) {
  const { slug } = await params
  const product = await getProduct(slug)
  return <h1>{product.name}</h1>
}

async function Inventory({ params }: { params: Params }) {
  const { slug } = await params
  const inventory = await getInventory(slug)
  return <p>{inventory.count} available</p>
}
```

Product listings and details are reusable, so their data helpers use [`use cache`](/docs/app/api-reference/directives/use-cache). Inventory changes frequently and remains uncached:

```ts filename="lib/store.ts" highlight={4,9}
import { db } from '@/lib/db'

export async function getProducts() {
  'use cache'
  return db.product.findMany()
}

export async function getProduct(slug: string) {
  'use cache'
  return db.product.findUniqueOrThrow({ where: { slug } })
}

export async function getInventory(slug: string) {
  return db.inventory.findUniqueOrThrow({ where: { slug } })
}
```

Finally, each buying guide reads its content from the database:

```tsx filename="app/store/guides/[id]/page.tsx"
import { getGuide } from '@/lib/guides'

export default async function GuidePage({
  params,
}: PageProps<'/store/guides/[id]'>) {
  const { id } = await params
  const guide = await getGuide(id)
  return <article>{guide.content}</article>
}
```

The buying-guide query is initially uncached. A second helper returns the IDs that the store can prerender:

```ts filename="lib/guides.ts"
import { db } from '@/lib/db'

export async function getGuide(id: string) {
  return db.guide.findUniqueOrThrow({ where: { id } })
}

export async function getGuideIds() {
  const guides = await db.guide.findMany({ select: { id: true } })
  return guides.map((guide) => guide.id)
}
```

At this point, the app lets Next.js decide what it can prerender. Add three explicit requirements:

- Keep the shared storefront shell static.
- Prefetch cached product details while leaving live inventory for navigation.
- Prerender buying guides in full.

### Step 1: Protect the storefront shell

The store layout is shared by the catalog, product pages, and buying guides. Add `ensureStatic = 'shell'` above the existing layout so its App Shell remains static as the app changes:

```tsx filename="app/store/layout.tsx"
export const ensureStatic = 'shell'
```

A default `<Link>` into the store can load this shell from static output. If a later change adds request-specific content behind `<Suspense>`, that content waits for a per-link prefetch or navigation instead of making the shell render per request.

For one subtree, [`await prefetch()`](/docs/app/api-reference/functions/prefetch) provides similar behavior by keeping the work below it out of the App Shell. Use `ensureStatic = 'shell'` when the static requirement applies across the route instead of adding that cutoff to each subtree.

### Step 2: Prefetch product details, not live inventory

A product page already separates its cached summary from live inventory with `<Suspense>`. Add `ensureStatic = 'prefetch'` so the shell and each per-link prefetch remain static:

```tsx filename="app/store/products/[slug]/page.tsx"
export const ensureStatic = 'prefetch'
```

Update the product links with `prefetch={true}` so each link can resolve its cached, URL-specific product details:

```tsx filename="app/store/page.tsx" highlight={1}
<Link href={`/store/products/${product.slug}`} prefetch={true}>
  {product.name}
</Link>
```

When a product link becomes visible, its prefetch includes the product heading and **Checking availability...** fallback. The uncached inventory query runs after the user follows the link.

Pause the next navigation in the Next.js DevTools to inspect this result. Resume the navigation to load the current inventory.

For one subtree, [`await navigation()`](/docs/app/api-reference/functions/navigation) keeps the work below it out of both the App Shell and per-link prefetches. Use `ensureStatic = 'prefetch'` when every prefetch for the route must remain static.

### Step 3: Prerender every buying guide

Buying guides are editorial pages whose complete server output should remain static. Add `ensureStatic = 'navigation'` to the existing dynamic `[id]` route:

```tsx filename="app/store/guides/[id]/page.tsx"
export const ensureStatic = 'navigation'
```

Run `next build`. The route cannot guarantee static output because Next.js does not know which `id` values to prerender:

```text filename="Terminal"
Page "/store/guides/[id]": `ensureStatic = "navigation"` requires an exported `generateStaticParams()` function.
Learn more: https://nextjs.org/docs/messages/generate-static-params#with-ensurestatic
```

Export [`generateStaticParams()`](/docs/app/api-reference/functions/generate-static-params) and return every buying guide ID:

```tsx filename="app/store/guides/[id]/page.tsx" highlight={3,5-8}
import { getGuide, getGuideIds } from '@/lib/guides'

export const ensureStatic = 'navigation'

export async function generateStaticParams() {
  const ids = await getGuideIds()
  return ids.map((id) => ({ id }))
}

export default async function GuidePage({
  params,
}: PageProps<'/store/guides/[id]'>) {
  const { id } = await params
  const guide = await getGuide(id)
  return <article>{guide.content}</article>
}
```

The parameter error is now fixed. If the route has multiple dynamic segments, every result must include all of them.

Open one of the returned guide URLs with `next dev`. Because `getGuide()` still performs an uncached database query, the development overlay points to that query:

```text filename="Development overlay"
Next.js encountered uncached data on a route that must be fully static.
```

There are two ways to preserve the complete-route requirement:

- Remove the data access if the page does not need it.
- Cache the data if its result can be shared across requests.

Buying-guide content is shared, so cache the query:

```ts filename="lib/guides.ts" highlight={4}
import { db } from '@/lib/db'

export async function getGuide(id: string) {
  'use cache'
  return db.guide.findUniqueOrThrow({ where: { id } })
}
```

Reload the page in development. The static-route error clears. Run `next build` again to confirm that the returned guide IDs and their content are fully prerendered.

If the guide must read uncached or request-specific data, remove `ensureStatic = 'navigation'` instead. That changes the route's requirement and allows the data to render per request.
