Before Cache Components, static and dynamic rendering were a route-level choice. [Route segment configs](/docs/app/guides/caching-without-cache-components#dynamic) such as `dynamic = 'force-static'`, `dynamic = 'force-dynamic'`, and `dynamic = 'error'` controlled whether the entire route was prerendered, rendered on demand, or failed when it could not be prerendered.

[Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents) moves this boundary to the component and function level. A single route can have a static shell, cached content, and request-specific content that streams in later. Shared UI can render first without requiring the entire route to be static.

Some routes must still avoid request-time server work, to control compute costs or to stay fully prerendered as the codebase changes. [`ensureStatic`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic) makes that requirement explicit, so a later change that adds request-time rendering is reported instead of going unnoticed.

## Decide what should stay static

Static output does not depend on request-specific data. Next.js can generate it before a request and reuse it across requests. With [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching), a default `<Link>` loads the destination's [App Shell](/docs/app/glossary#app-shell). Setting `prefetch={true}` can also load static or cached [URL-specific content](/docs/app/guides/optimizing-prefetching#resolve-url-data-at-prefetch-time). The navigation request returns the remaining server-rendered content after the user follows the link. These are the route's [navigation stages](/docs/app/glossary#navigation-stages).

Each `ensureStatic` value extends the static requirement through one more stage. In the following diagram, gray marks output that must remain static, while blue marks work that can render later:

For most apps, `'prefetch'` on a shared layout is the right starting point. It keeps both the App Shell and per-link prefetches static, while request-specific content behind `<Suspense>` still renders on navigation. Use `'shell'` only when per-link prefetches should render request-specific content on the server, and `'navigation'` for routes that must be fully prerendered. A page can set a stricter level than its layout.

The following example sets `'prefetch'` on a store layout, structures its product pages for static prefetches, then requires `'navigation'` for buying guides.

## Example

An online store has product data, live inventory, and buying guides. Its shared layout, product pages, and buying guides have different static requirements.

Enable [Cache Components](/docs/app/api-reference/config/next-config-js/cacheComponents) and [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching):

```ts filename="next.config.ts" highlight={4,5}
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

### Step 1: Keep the storefront shell and prefetches static

The store layout is shared by the catalog, product pages, and buying guides. Add `ensureStatic = 'prefetch'` so its App Shell and every per-link prefetch under it stay static as the app changes:

```tsx filename="app/store/layout.tsx" highlight={5}
import Link from 'next/link'
import { Suspense } from 'react'
import { CartButton } from '@/app/ui/cart'

export const ensureStatic = 'prefetch'

export default function StoreLayout({ children }: LayoutProps<'/store'>) {
  return (
    <>
      <nav>
        <Link href="/store">Products</Link>
        <Link href="/store/guides">Buying guides</Link>
        <Suspense fallback={<CartButton count={0} />}>
          <CartButton />
        </Suspense>
      </nav>
      <main>{children}</main>
    </>
  )
}
```

A default `<Link>` into the store loads the shell from static output, and a `<Link prefetch={true}>` loads its per-link prefetch from static output too. `CartButton` reads the cart cookie, so it renders on navigation behind its `<Suspense>` boundary, and the prefetched UI shows the empty button until then. Request-specific content outside `<Suspense>` is reported by [Instant Navigation validation](/docs/messages/instant-navigation-validation).

`'shell'` would not be enough here. Product links will resolve `params` in their per-link prefetch, and under `'shell'` each of those prefetches would render on the server, with nothing in the UI to show that cost. `'prefetch'` serves them from prerendered output instead.

Awaiting [`navigation()`](/docs/app/api-reference/functions/navigation) inside `<Suspense>` defers one subtree's work until navigation. With `ensureStatic = 'prefetch'` on the layout, request-specific work inside `<Suspense>` is deferred that way across every route under it, so the subtrees need no call of their own. See [Defer work to a later stage](/docs/app/guides/optimizing-prefetching#defer-work-to-a-later-stage) for the per-subtree controls.

### Step 2: Prefetch product details, not live inventory

The layout's `'prefetch'` level already covers the product page. What the page controls is how much of it a static prefetch can include. Separate the cached product details from live inventory with `<Suspense>`, and return the products to prerender from [`generateStaticParams()`](/docs/app/api-reference/functions/generate-static-params):

```tsx filename="app/store/products/[slug]/page.tsx" highlight={5-8}
import { Suspense } from 'react'
import { Inventory, ProductDetails } from '@/app/ui/product'
import { getFeaturedProductSlugs } from '@/lib/products'

export async function generateStaticParams() {
  const slugs = await getFeaturedProductSlugs()
  return slugs.map((slug) => ({ slug }))
}

export default function ProductPage({
  params,
}: PageProps<'/store/products/[slug]'>) {
  return (
    <>
      <Suspense fallback={<p>Loading product...</p>}>
        <ProductDetails params={params} />
      </Suspense>
      <Suspense fallback={<p>Checking availability...</p>}>
        <Inventory params={params} />
      </Suspense>
    </>
  )
}
```

`ProductDetails` uses [`use cache`](/docs/app/api-reference/directives/use-cache), while `Inventory` reads uncached data.

A default `<Link>` loads only the App Shell. To include the product details in the prefetch, a link needs `prefetch={true}`. A grid of products should not request that for every card, so upgrade each link when the user shows intent:

```tsx filename="app/ui/product-link.tsx" highlight={11}
'use client'

import Link from 'next/link'
import { useState } from 'react'

export function ProductLink({
  slug,
  children,
}: {
  slug: string
  children: React.ReactNode
}) {
  const [active, setActive] = useState(false)
  return (
    <Link
      href={`/store/products/${slug}`}
      prefetch={active ? true : 'auto'}
      onMouseEnter={() => setActive(true)}
      onFocus={() => setActive(true)}
    >
      {children}
    </Link>
  )
}
```

The link starts with the default App Shell prefetch and switches to a per-link prefetch on hover or focus. See [Hover-triggered prefetch](/docs/app/guides/prefetching#hover-triggered-prefetch) for the trade-offs of extending `<Link>`.

That prefetch includes the product heading and the **Checking availability...** fallback. The uncached inventory query runs after the user follows the link.

Products returned from `generateStaticParams()` are prerendered at build time. For any other product, the first prefetch on a new deployment serves the route's fallback shell instead, because no page has been generated yet. Next.js generates it in the background, and later prefetches include the product heading. See [ISR with Cache Components](/docs/app/guides/incremental-static-regeneration-cache-components#at-runtime).

### Step 3: Prerender every buying guide

Buying guides are editorial pages whose complete server output should remain static. The page can require a stricter level than the layout's `'prefetch'`. Start with a page that displays the guide ID and reads a theme preference from `cookies()`. Add `ensureStatic = 'navigation'`:

```tsx filename="app/store/guides/[id]/page.tsx" highlight={3}
import { cookies } from 'next/headers'

export const ensureStatic = 'navigation'

export default async function GuidePage({
  params,
}: PageProps<'/store/guides/[id]'>) {
  const { id } = await params
  const theme = (await cookies()).get('theme')?.value
  return <article data-theme={theme}>Buying guide: {id}</article>
}
```

The `'navigation'` requirement is [validated during both `next dev` and `next build`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#validation). Start the development server and open a guide URL. Because Next.js does not know which `id` values to prerender, the development overlay reports that the route requires an exported `generateStaticParams()` function and links to the [`generateStaticParams` error guide](/docs/messages/generate-static-params#with-ensurestatic).

Export `generateStaticParams()` and return every buying guide ID. Unlike the product page, which lists only featured products and leaves the rest to the fallback shell, `'navigation'` has no later stage to fall back to, so the list must be complete:

```tsx filename="app/store/guides/[id]/page.tsx" highlight={4,6-9}
import { cookies } from 'next/headers'
import { getGuideIds } from '@/lib/guides'

export const ensureStatic = 'navigation'

export async function generateStaticParams() {
  const ids = await getGuideIds()
  return ids.map((id) => ({ id }))
}

export default async function GuidePage({
  params,
}: PageProps<'/store/guides/[id]'>) {
  const { id } = await params
  const theme = (await cookies()).get('theme')?.value
  return <article data-theme={theme}>Buying guide: {id}</article>
}
```

If the route has multiple dynamic segments, every result must include all of them.

```diff filename="app/store/guides/[id]/page.tsx"

  import { getGuideIds } from '@/lib/guides'

-   const theme = (await cookies()).get('theme')?.value
-   return <article data-theme={theme}>Buying guide: {id}</article>

  }
```

Reload the page to confirm that the runtime data error clears. Next, load the guide content from the database. Add a query alongside `getGuideIds()` in `lib/guides.ts`:

```ts filename="lib/guides.ts"
import { db } from '@/lib/db'

export async function getGuide(id: string) {
  return db.guide.findUniqueOrThrow({ where: { id } })
}
```

Call `getGuide()` from the page, keeping the `ensureStatic` and `generateStaticParams()` exports:

```diff filename="app/store/guides/[id]/page.tsx"
- import { getGuideIds } from '@/lib/guides'
+ import { getGuide, getGuideIds } from '@/lib/guides'

  export default async function GuidePage({ params }) {
    const { id } = await params
-   return <article>Buying guide: {id}</article>
+   const guide = await getGuide(id)
+   return <article>{guide.content}</article>
  }
```

Buying-guide content is shared, so cache the query:

```ts filename="lib/guides.ts" highlight={4}
import { db } from '@/lib/db'

export async function getGuide(id: string) {
  'use cache'
  return db.guide.findUniqueOrThrow({ where: { id } })
}
```

Reload the page in development. The static-route error clears. Run `next build` to confirm that the returned guide IDs and their content are fully prerendered.

If request-time rendering is intentional, first confirm that the route no longer needs to be fully static. Then [remove the static requirement](/docs/messages/static-route-runtime#remove-the-static-requirement) and [wrap the component that reads the data in `<Suspense>`](/docs/messages/blocking-prerender-dynamic#wrap-in-or-move-into-suspense), so the route can show a fallback while the data loads.
