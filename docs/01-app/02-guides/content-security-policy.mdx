[Content Security Policy (CSP)](https://developer.mozilla.org/docs/Web/HTTP/CSP) is important to guard your Next.js application against various security threats such as cross-site scripting (XSS), clickjacking, and other code injection attacks.

By using CSP, developers can specify which origins are permissible for content sources, scripts, stylesheets, images, fonts, objects, media (audio, video), iframes, and more.

## Nonces

A [nonce](https://developer.mozilla.org/docs/Web/HTML/Global_attributes/nonce) is a unique, random string of characters created for a one-time use. It is used in conjunction with CSP to selectively allow certain inline scripts or styles to execute, bypassing strict CSP directives.

### Why use a nonce?

CSP can block both inline and external scripts to prevent attacks. A nonce lets you safely allow specific scripts to run—only if they include the matching nonce value.

If an attacker wanted to load a script into your page, they'd need to guess the nonce value. That's why the nonce must be unpredictable and unique for every request.

### Adding a nonce with Proxy

[Proxy](/docs/app/api-reference/file-conventions/proxy) enables you to add headers and generate nonces before the page renders.

Every time a page is viewed, a fresh nonce should be generated. This means that you **must use [dynamic rendering](/docs/app/glossary#dynamic-rendering) to add nonces**.

For example:

> **Good to know**: In development, `'unsafe-eval'` is required because React uses `eval` to provide enhanced debugging information, such as reconstructing server-side error stacks in the browser. `unsafe-eval` is not required for production. Neither React nor Next.js use `eval` in production by default.

```ts filename="proxy.ts" highlight={8,9} switcher
import { NextRequest, NextResponse } from 'next/server'

export function proxy(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64')
  const isDev = process.env.NODE_ENV === 'development'
  const cspHeader = `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''};
    style-src 'self' ${isDev ? "'unsafe-inline'" : `'nonce-${nonce}'`};
    style-src-attr 'unsafe-inline';
    img-src 'self' blob: data:;
    font-src 'self';
    object-src 'none';
    base-uri 'self';
    form-action 'self';
    frame-ancestors 'none';
    upgrade-insecure-requests;
`
  // Replace newline characters and spaces
  const contentSecurityPolicyHeaderValue = cspHeader
    .replace(/\s{2,}/g, ' ')
    .trim()

  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-nonce', nonce)

  requestHeaders.set(
    'Content-Security-Policy',
    contentSecurityPolicyHeaderValue
  )

  const response = NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  })
  response.headers.set(
    'Content-Security-Policy',
    contentSecurityPolicyHeaderValue
  )

  return response
}
```

This policy uses [`'strict-dynamic'`](https://developer.mozilla.org/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src#strict-dynamic), so supporting browsers trust scripts loaded by an already-trusted script and ignore host sources such as `'self'` in `script-src`. The nonce is what makes the framework scripts trusted, which in turn allows the chunks they load.

> **Good to know**: A nonce cannot apply to `style` attributes, so `style-src-attr 'unsafe-inline'` is required for inline styles such as the ones [`next/image`](/docs/app/api-reference/components/image) sets. Adding `'unsafe-inline'` to `style-src` instead has no effect, because browsers ignore it when the directive also contains a nonce.

By default, Proxy runs on all requests. You can filter Proxy to run on specific paths using a [`matcher`](/docs/app/api-reference/file-conventions/proxy#matcher).

We recommend ignoring matching prefetches (from `next/link`) and static assets that don't need the CSP header.

```ts filename="proxy.ts" switcher
export const config = {
  matcher: [
    /*
     * Match all request paths except for the ones starting with:
     * - api (API routes)
     * - _next/static (static files)
     * - _next/image (image optimization files)
     * - favicon.ico (favicon file)
     */
    {
      source: '/((?!api|_next/static|_next/image|favicon.ico).*)',
      missing: [
        { type: 'header', key: 'next-router-prefetch' },
        { type: 'header', key: 'purpose', value: 'prefetch' },
      ],
    },
  ],
}
```

### How nonces work in Next.js

To use a nonce, your page must be **dynamically rendered**. This is because Next.js applies nonces during **server-side rendering**, based on the CSP header present in the request. Static pages are generated at build time, when no request or response headers exist—so no nonce can be injected.

Here’s how nonce support works in a dynamically rendered page:

1. **Proxy generates a nonce**: Your proxy creates a unique nonce for each request and sets it in the `Content-Security-Policy` header on both the request and the response, along with an `x-nonce` header for your own code to read.
2. **Next.js extracts the nonce**: During rendering, Next.js parses the `Content-Security-Policy` or `Content-Security-Policy-Report-Only` header and extracts the nonce using the `'nonce-{value}'` pattern. Report-only lets you trial a policy while nonces are still applied.
3. **Nonce is applied automatically**: Next.js attaches the nonce to:
   - Framework scripts (React, Next.js runtime)
   - Page-specific JavaScript bundles
   - Inline styles and scripts generated by Next.js
   - Any `<Script>` components using the `nonce` prop

Because of this automatic behavior, you don’t need to manually add a nonce to each tag.

### Forcing dynamic rendering

If you're using nonces, you may need to explicitly opt pages into dynamic rendering:

## Static vs Dynamic Rendering with CSP

Using nonces has important implications for how your Next.js application renders:

### Dynamic Rendering Requirement

A nonce comes from the incoming request, so a page that uses one must be [dynamically rendered](/docs/app/glossary#dynamic-rendering):

- Each request renders the page again with a fresh nonce
- Prerendered pages carry no nonce at all
- Pages cannot be cached by CDNs without additional configuration
- [Partial Prerendering (PPR)](/docs/app/glossary#partial-prerendering-ppr) prerenders the shell, so the shell's scripts carry no nonce

A page that renders without a nonce still builds and serves normally, and the browser blocks its scripts, so it never hydrates. After [forcing dynamic rendering](#forcing-dynamic-rendering), confirm the nonce reached the HTML:

```bash filename="Terminal"
curl -s http://localhost:3000/ | grep -c 'nonce='
```

### Performance Implications

Opting a page into dynamic rendering is what makes a nonce reachable, and that opt-in is per page. Applying it broadly is how apps lose prerendering without meaning to:

- Pages are rendered per request instead of being prerendered at build time
- Static generation and ISR no longer apply to those pages, so their responses cannot be served from a CDN cache
- Serving cost scales with traffic rather than with builds

Add the opt-in only to the pages that need a nonce, rather than to a shared layout.

### When to use nonces

Consider nonces when:

- You have strict security requirements that prohibit `'unsafe-inline'`
- Your application handles sensitive data
- You need to allow specific inline scripts while blocking others
- Compliance requirements mandate strict CSP

## Without Nonces

For applications that do not require nonces, you can set the CSP header directly in your [`next.config.js`](/docs/app/api-reference/config/next-config-js) file. `'unsafe-inline'` is needed in `script-src` because Next.js sends the data required for hydration in inline `<script>` tags:

```js filename="next.config.js"
const isDev = process.env.NODE_ENV === 'development'

const cspHeader = `
    default-src 'self';
    script-src 'self' 'unsafe-inline'${isDev ? " 'unsafe-eval'" : ''};
    style-src 'self' 'unsafe-inline';
    img-src 'self' blob: data:;
    font-src 'self';
    object-src 'none';
    base-uri 'self';
    form-action 'self';
    frame-ancestors 'none';
    upgrade-insecure-requests;
`

module.exports = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: cspHeader.replace(/\n/g, ''),
          },
        ],
      },
    ]
  },
}
```

## Subresource Integrity (Experimental)

Next.js offers experimental support for [Subresource Integrity (SRI)](https://developer.mozilla.org/docs/Web/Security/Subresource_Integrity), which protects your script files from being modified in transit.

SRI covers script files, not inline scripts. It is not a hash-based CSP: no hashes are added to your `Content-Security-Policy` header, and `script-src` still needs a nonce or `'unsafe-inline'` to allow the inline scripts Next.js emits while rendering.

> **Good to know**: This feature is experimental and available in App Router applications.

### How SRI works

SRI generates cryptographic hashes of your JavaScript files at build time. These hashes are added as `integrity` attributes to the `<script src>` tags that load them, allowing browsers to verify that files haven't been modified during transit.

### Enabling SRI

Add the experimental SRI configuration to your `next.config.js`:

```js filename="next.config.js"
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    sri: {
      algorithm: 'sha256', // or 'sha384' or 'sha512'
    },
  },
}

module.exports = nextConfig
```

### CSP configuration with SRI

When SRI is enabled, you can continue using your existing CSP policies. SRI works independently by adding `integrity` attributes to your assets:

> **Good to know**: `'unsafe-inline'` is what allows the inline hydration scripts to run on a statically rendered page. You can combine `integrity` attributes with a [nonce](#nonces) on dynamically rendered routes, but browsers ignore `'unsafe-inline'` in a policy that also contains a nonce.

```js filename="next.config.js"
const isDev = process.env.NODE_ENV === 'development'

const cspHeader = `
    default-src 'self';
    script-src 'self' 'unsafe-inline'${isDev ? " 'unsafe-eval'" : ''};
    style-src 'self' 'unsafe-inline';
    img-src 'self' blob: data:;
    font-src 'self';
    object-src 'none';
    base-uri 'self';
    form-action 'self';
    frame-ancestors 'none';
    upgrade-insecure-requests;
`

module.exports = {
  experimental: {
    sri: {
      algorithm: 'sha256',
    },
  },
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: cspHeader.replace(/\n/g, ''),
          },
        ],
      },
    ]
  },
}
```

### SRI compared to nonces

- **Static generation**: Hashes are computed at build time, so pages can stay statically generated and cached by a CDN
- **File integrity**: Browsers reject a script file that doesn't match the hash your build produced
- **Inline scripts**: Still allowed by `'unsafe-inline'` or a nonce, and a nonce requires dynamic rendering

### Limitations of SRI

- **Experimental**: Feature may change or be removed
- **App Router only**: Not supported in Pages Router
- **Script files only**: The inline scripts Next.js emits while rendering, such as the RSC payload (`self.__next_f.push(...)`), do not receive an `integrity` attribute
- **Client component chunks**: Chunks the RSC runtime requests during rendering are served without an `integrity` attribute

</AppOnly>

## Development vs Production Considerations

CSP implementation differs between development and production environments:

### Development Environment

In development, you will need to enable `'unsafe-eval'` because React uses `eval` to provide enhanced debugging information, such as reconstructing server-side error stacks in the browser to show you where errors originated on the server. Development also needs `'unsafe-inline'` in `style-src` in place of the nonce, because Next.js injects inline styles for the dev overlay that don't carry one:

### Production Deployment

Common issues in production:

- **Nonce not applied**: Ensure your proxy runs on all necessary routes
- **Static assets blocked**: `'self'` already covers `/_next/static`, so check for a missing origin in `img-src`, `font-src`, or `connect-src` before widening `script-src`
- **Third-party scripts**: Add necessary domains to your CSP policy

### Common CSP Violations

1. **Inline styles**: `style` attributes are covered by `style-src-attr`, which a nonce cannot satisfy. Add `style-src-attr 'unsafe-inline'`, or move the styles into a stylesheet
2. **Inline scripts you add yourself**: scripts injected with `dangerouslySetInnerHTML`, such as the ones that [prevent a flash before hydration](/docs/app/guides/preventing-flash-before-hydration), need the nonce passed to them explicitly
3. **WebAssembly**: Add `'wasm-unsafe-eval'` if using WebAssembly
4. **Service workers**: Add `worker-src` for the origins your service worker scripts are served from
