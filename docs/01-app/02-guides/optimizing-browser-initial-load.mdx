Browser initial-load performance depends on both how much code a route ships and
_when_ the browser needs it. A large editor loaded after a click has a different
cost than the same editor in the route's initial JavaScript.

Use the experimental bundle analyzer to inspect client contributions and module
reachability. For automated analysis, default to `--output`:

```bash filename="Terminal"
pnpm exec next experimental-analyze --output --baseline-name initial-load-before
pnpm exec next experimental-analyze query --help
```

Output mode performs the production analysis, writes queryable artifacts, and
exits cleanly. Run `pnpm exec next experimental-analyze` without `--output` only
for optional interactive browser exploration; server mode stays open by design.

Start with sources that are reachable synchronously in the client graph:

```bash filename="Terminal"
pnpm exec next experimental-analyze \
  query get_route_modules \
  --input '{
    "route":"/dashboard",
    "environment":"client",
    "loadScopes":["initial"],
    "groupBy":"package",
    "metric":"compressed",
    "limit":500
  }'
```

`loadScopes` use exact route entries in current analyzer artifacts, with a
labeled heuristic fallback for older artifacts. They are graph evidence, not
network measurements. An `initial` source is reachable from the route through
synchronous edges. An `async` source is behind at least one asynchronous edge.
Use source inspection to determine whether the feature is actually needed before
interaction.

Common opportunities include:

- editors, maps, charts, dialogs, and viewers rendered only after interaction;
- multiple browser copies of the same package, especially React or versions in
  the same semver major;
- display-only Markdown/MDX parsing, highlighting, sanitization, or other pure
  rendering inside a Client Component;
- broad icon, locale, language, chart, or editor registries;
- route-level Client Component boundaries that can move to an interactive leaf;
- large initial CSS, fonts, images, static data, polyfills, and shims.

Inspect reverse import edges before changing an entry. They can reveal that an
application re-export, rather than the attributed package itself, is responsible
for pulling a module into the route:

```bash filename="Terminal"
pnpm exec next experimental-analyze \
  query explain_route_module \
  --input '{
    "route":"/dashboard",
    "environment":"client",
    "sourcePath":"<sourcePath from get_route_modules>",
    "maxDepth":25
  }'
```

For a complete account of every synchronous path retaining a candidate, query
`get_initial_import_graph`. Its SCC-collapsed graph reports edge counterfactuals
without enumerating exponentially many path arrays. Before changing an edge,
use `analyze_import_edge` to list the sources/packages and estimated attribution
that would leave initial scope. Use `get_route_outputs` and `get_css_assets` for
emitted CSS/media evidence; those queries do not claim the browser requested the
files.

After each change, regenerate and compare analyzer data. Source cleanup or a
type-only import change can have zero bundle impact when the bundler already
removes it, so do not infer a win from the source diff. Removal, narrower imports,
server migration, and package deduplication should reduce client attribution.
Lazy loading can leave eventual route bytes unchanged; verify that the affected
source moved from `initial` to `async`, then test the interaction itself.

The analyzer already performs production analysis. Prefer targeted behavior
tests and the narrowest relevant type-check before attempting another expensive
full production build.

## Use the optimizer Skill

The [`next-browser-initial-load-optimizer`](https://www.skills.sh/vercel/next.js/next-browser-initial-load-optimizer)
Skill runs this workflow one measured candidate at a time, including source
inspection, behavior safeguards, before/after verification, and reverting
changes that do not improve the intended signal.

Install it from the Next.js repository:

```bash filename="Terminal"
npx skills add vercel/next.js --skill next-browser-initial-load-optimizer
```

Then ask your coding agent:

```prompt
Optimize browser initial-load performance for /dashboard using the next-browser-initial-load-optimizer Skill. Preserve the existing UI and interactions.
```

The analyzer's compressed source values are attribution estimates because each
source part is compressed independently. Use a cold-browser network trace when
you need observed transfer bytes or exact request timing.
