Many apps can provide responsive interactions without a client data-fetching library. See [Building interactive apps](/docs/app/guides/interactive-apps) for patterns using Server Functions, transitions, optimistic UI, and pending feedback.

Use a client data-fetching library such as [SWR](https://swr.vercel.app), [TanStack Query](https://tanstack.com/query), or [Apollo Client](https://www.apollographql.com/docs/react) when a Client Component needs features such as focus revalidation, interval polling, mutations, or request deduplication.

## Choose a client fetching pattern

Client data-fetching libraries support three common patterns:

| Pattern                 | SWR                            | TanStack Query        | Initial data                                   |
| ----------------------- | ------------------------------ | --------------------- | ---------------------------------------------- |
| Inline loading states   | `useSWR`                       | `useQuery`            | Fetched in the browser after hydration         |
| Suspense loading states | `useSWR` with `suspense: true` | `useSuspenseQuery`    | Fetched in the browser after hydration         |
| Seeded from the server  | `<SWRConfig fallback>`         | `<HydrationBoundary>` | Included in the React Server Component payload |

Use inline loading states when the component should stay rendered while it fetches, or when several independent queries in one component should start together. Use [Suspense](/docs/app/getting-started/fetching-data#streaming) when the surrounding UI has a suitable fallback and [error boundary](/docs/app/getting-started/error-handling#nested-error-boundaries).

For browser-driven interactions such as autocomplete, you can use either client-only pattern. The initial result waits for hydration and a browser request, which is often the right tradeoff for data that is not needed until an interaction.

Seed the client cache from a [Server Component](/docs/app/getting-started/server-and-client-components) when the server knows what the initial render needs. The library receives that value in the React Server Component payload and can continue managing it in the browser.

Choose a pattern based on whether the Client Component needs server-rendered data, streaming, or client-side cache features:

| Capability            | Client library      | Server Component    | Server seed + client library |
| --------------------- | ------------------- | ------------------- | ---------------------------- |
| Server-rendered data  | <Cross size={18} /> | <Check size={18} /> | <Check size={18} />          |
| Streaming             | <Cross size={18} /> | <Check size={18} /> | <Check size={18} />          |
| Request deduplication | <Check size={18} /> | <Check size={18} /> | <Check size={18} />          |
| Client cache features | <Check size={18} /> | <Cross size={18} /> | <Check size={18} />          |

If a Client Component only needs to read server data once, pass it a Promise and unwrap it with React's [`use()`](https://react.dev/reference/react/use). This avoids adding a data-fetching library for data that never revalidates on the client.

## Cache server data with Cache Components (optional)

You can also cache the server data used for the initial seed. Server seeding and server caching are independent choices. Add Cache Components when the server read or rendered view should be reused. When both are enabled, three cache layers can hold related data:

| Layer                        | What it stores                                                    | Freshness control                                                                               |
| ---------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Next.js server cache         | Cached data and Server Component output                           | `cacheLife` [`revalidate`](/docs/app/api-reference/functions/cacheLife#revalidate) and `expire` |
| Next.js client cache         | React Server Component payloads for visited and prefetched routes | `cacheLife` [`stale`](/docs/app/api-reference/functions/cacheLife#stale)                        |
| Client data-fetching library | Browser data stored under an SWR key or TanStack query key        | The library's revalidation options and mutations                                                |

Next.js [prefetching](/docs/app/guides/prefetching) can place the next route's server-rendered view in the client cache before navigation.

The cache layers keep independent freshness policies and do not need matching durations. Cache identities and mutation invalidation must stay coordinated across layers.

## Coordinate mutations

Server Components, data-fetching libraries, and mutations manage different parts of the data flow:

- **Server Components** provide the initial data, scoped to the segment that owns it.
- **The data-fetching library** stores the browser value under a shared cache identity.
- **Mutations** can update the browser cache immediately and refresh cached server data for the next render.

An optimistic update should restore the previous browser value if the write fails. If the server read is not cached, there is no server tag to invalidate.

After a mutation, invalidate any cached server read that produced the seed:

| Method                                                                                 | Use when                                          | Next server read                     |
| -------------------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------ |
| [`updateTag(tag)`](/docs/app/api-reference/functions/updateTag)                        | A Server Action must read its own write           | Waits for fresh data                 |
| [`revalidateTag(tag, 'max')`](/docs/app/api-reference/functions/revalidateTag)         | The update is passive or stale data is acceptable | Serves stale data while revalidating |
| [`revalidateTag(tag, { expire: 0 })`](/docs/app/api-reference/functions/revalidateTag) | The next read must reflect the update             | Waits for fresh data                 |
