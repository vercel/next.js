Request Insights shows where time is spent as your Next.js app handles requests in development. It records a timeline for each completed App Router request, including compilation, module loading, data fetching, and rendering.

This guide walks through a typical performance audit workflow that you can apply in your own app.

## Example

Suppose a request to `/reports` takes several seconds. We'll find it in the development overlay and inspect its timeline.

### Step 1: Reproduce the slow request

Enable Request Insights in `next.config.ts`, then start the development server:

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    requestInsights: true,
  },
}

export default nextConfig
```

```js filename="next.config.js" switcher
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    requestInsights: true,
  },
}

module.exports = nextConfig
```

This option enables both the **Request Insights** panel in the development overlay and the `next experimental-request-insights` CLI. If the development server is already running, restart it before continuing.

Open `http://localhost:3000/reports` and reproduce the slowdown. The development server keeps up to 500 completed requests in memory, including the latest RSC and HTML page requests, until it restarts.

### Step 2: Find the request in the overlay

Open the Next.js development tools in the browser and select **Request Insights**. The panel lists completed requests with their route, duration, type, and status.

Select the `/reports` request that took several seconds. Use the route, duration, type, and status to distinguish it from other requests made while loading the page.

### Step 3: Inspect the request timeline

Selecting a request opens its overview, trace, and recorded fetches. The trace places each operation on the request timeline and shows its duration. Spans can overlap or contain other spans, so use their position and nesting to tell nested work apart from separate delays. Each fetch also shows its URL, cache status, and duration.

In this example, `ResolveMetadata.generateMetadata` contains a 3.53-second `/metadata` fetch and spans 3.54 seconds of the 3.65-second request. Compilation and rendering complete in milliseconds, so they do not explain the slowdown. The next step is to inspect `generateMetadata` and the data it awaits.

The `request` kind is browser or server request work. The `instant-insights` kind is a development validation render started for a parent request. Validation renders execute in the same development server and can overlap with, and add contention to, page or API requests. The CLI's `get` output lists overlapping work and the amount of shared time.

### Step 4: Inspect requests from the command line

Request Insights also provides a CLI for terminal workflows and automation. List requests for a route:

```bash
next experimental-request-insights list --route /reports
```

To inspect concurrency in chronological order, include relative start and end times:

```bash
next experimental-request-insights list --sort start
```

Then inspect the matching request using its full ID or an unambiguous prefix:

```bash
next experimental-request-insights get 4f83d912
```

Add `--json` to `get` for the complete request with span attributes, or to `list` for machine-readable summaries. If automatic server discovery fails, pass the active origin with `--url http://localhost:3000`.
