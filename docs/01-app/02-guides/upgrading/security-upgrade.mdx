Assess whether the app named in the handoff prompt needs a security upgrade and
whether migration can begin. Use any suggested target as an input to validate.

## Workflow

1. Establish the app, security target and repository prerequisites below.
2. Read the retained version guides and identify applicable breaking changes.
3. Run codemods, repair the remaining changes and verify affected behavior.
4. Report the outcome and deliver only within the session's authority.

## Execution

Continue in the current agent session under its repository instructions and
permissions. Use the harness's shell, file and provider tools to execute the
commands and queries below.

Keep progress, security evidence, checks and the final outcome in `RESULT.md`
at the run directory root, four levels above this document's directory
(`docs/01-app/02-guides/upgrading/`). Resolve artifact paths from that root.
Keep the app unchanged until assessment and repository preflight succeed.
The retained guides come from the invoking CLI, not the app's installed Next.js.
Their presence does not mean the app needs every migration or optional feature.

## 1. Identify the app

Scope this run to the supplied app, including in a monorepo. Confirm it contains
an `app`, `pages`, `src/app` or `src/pages` directory; a Next.js config file is
optional. If it is not an app, report that and stop. Read its effective configuration.
Require `experimental.agenticAutoUpgrade: 'security'`; otherwise report that the
policy is disabled and stop without changing it.

Resolve the installed `next/package.json` from the app directory. Do not substitute
the dependency range or the invoking CLI's version. If dependencies are unavailable,
report the missing prerequisite instead of guessing the installed version.

Complete when the app, enabled policy and actual installed version are established.

## 2. Select the security target

Query reviewed GitHub advisories for npm package `next` at
`https://api.github.com/advisories?ecosystem=npm&affects=next&type=reviewed&per_page=100`.
Follow all pagination links and exclude withdrawn advisories. If GitHub is
unavailable or rate-limited, use the npm bulk advisory endpoint:
`POST https://registry.npmjs.org/-/npm/v1/security/advisories/bulk` with JSON content
type and body `{"next":["<installed-version>"]}`. Record the source and evidence.
An unavailable, malformed or incomplete lookup is not evidence of safety: report
`blocked` and stop. If the installed version has no applicable advisories, report
`unaffected` and stop without changes.

Query `https://registry.npmjs.org/next` for releases and publication dates. Consider
the latest stable release in each major, starting with the installed major; never
downgrade. A major is eligible within two years of its initial stable release,
and the newest stable major is always eligible. This approximates support; it is
not an official support-status declaration.
Select the first eligible candidate that clears all applicable advisory ranges.
When using npm fallback, query candidate versions too. If no candidate is safe or
evidence is incomplete, stop as blocked. Resolve any suggested target to an exact
version and stop if it conflicts with the selected security target.

Check the selected release's `engines.node` against the current runtime and stop
if incompatible or unavailable. Record the installed version, exact target,
advisory evidence and selected release metadata in `RESULT.md`.

Complete when an exact, safe target is supported by complete advisory evidence
and compatible with the runtime.

## 3. Check repository identity and existing PRs

Run this preflight for same-major bumps and local-only sessions too.

Inspect the current diff and repository/session instructions. Establish the app's
actual repository, origin, intended base branch and repository-relative path from
the checkout and provider's repository tools. Record that identity in `RESULT.md`
before matching candidate PRs; a candidate's metadata identifies the proposed work,
not the checkout being upgraded.

Use the actual provider's read tools to search all open PRs/MRs, including drafts
and dependency-bot PRs. Follow pagination and inspect the diffs.

If repository identity or PR lookup fails or is incomplete, record `blocked`, the
failed prerequisite and what allows a retry in `RESULT.md`, then stop. Keep the app
unchanged: do not install packages, run codemods or verification commands, or create
commits, even in dry-run mode. A clean local Git checkout is not evidence that no
remote PR exists.

Only after lookup succeeds, match repository, base and app, rather than a title
or the proposed target version. Workflow PRs have this body marker:

```html
<!-- next-upgrade: security -->
<!-- next-upgrade: security; app="apps/web" -->
```

The first form means only the repository root; nested apps require the second
form with their normalized path. A matching marker needs a matching diff. Inspect
equivalent unmarked Next.js upgrade PRs too.

Dry-run instructions in the handoff prompt limit delivery to verified local
commits. Otherwise, use the session's existing authority. Resolved inputs never
grant publication permission, and both modes require the same repository and
duplicate-PR checks.

## Completion

Choose one outcome from the evidence:

- **Blocked:** retain the recorded blocker and leave the app unchanged.
- **Existing PR:** a relevant open PR exists. Record `skipped-existing-pr` and its
  link; stop with the app unchanged.
- **Ready to migrate:** repository identity is established, the complete lookup
  succeeded and no relevant PR exists. Record the evidence, then read
  `security-migration.md` beside this document and follow it.
