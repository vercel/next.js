## 1. Reproduce the problem

Start the app with its development script, such as `npm run dev`, or use the server that's already running. Give your agent the URL, the action, and what you expected to see. For example: “Open Home and click Settings. I expect the Settings heading to appear immediately, but it only appears after the data loads.” Opening Settings directly would miss the click you're investigating.

## 2. Observe what happens

Choose the observation that answers your question:

- **What appeared during the click?** Check whether the Settings heading is visible while navigation is paused. Use the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools) or follow the [Playwright example for testing a link with `instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests). Checking the heading only after the page finishes loading won't tell you when it appeared.
- **Why does the route have an Insight?** Read the [DevTools Insight](/docs/app/guides/devtools#issues-and-insights) or ask the dev server about the destination. [Call `check_route`](/docs/app/guides/mcp#calling-the-dev-server-directly) with the concrete path, for example `{"path":"/settings"}`. Include the query string if it changes the page. With Cache Components enabled, `validation.errors` reports findings and their source locations when available. The request doesn't use browser cookies.
- **What happened after an interaction?** If clicking **Save** leaves the old value on screen, reproduce it in the same browser session. Use [Agent Browser](https://github.com/vercel-labs/agent-browser) to inspect the response to the save request and the value displayed afterward. If the click threw an exception, `get_errors` reads the connected browser's error state and `get_logs` returns the dev log path. If a fallback stays visible after the response, [`next-dev-loop`](/docs/app/guides/ai-agents#next-dev-loop) can show which React boundary is still pending.
- **Does it only fail in production?** Run `next build`. If prerendering fails, [`--debug-prerender`](/docs/app/guides/building#debug-prerender-errors) gives you a readable stack trace; [`--debug-build-paths`](/docs/app/api-reference/cli/next#building-specific-routes) limits it to the affected routes. If the build succeeds, reproduce the problem with `next start`.

## 3. Verify the fix

After editing, repeat the reproduction. For the Settings example, click from Home again and check that the heading appears before the data arrives, then that the finished page shows the data. For a production failure, repeat the normal production build and the interaction that failed.

If you're fixing a route Insight, call `check_route` again with the same path and query. Confirm that `validation.status` is `"validated"` and the original finding is gone. If the status is `"not-run"`, read `validation.reason`. An HTTP 200 alone doesn't tell you whether validation ran or what the reader saw during the click.
