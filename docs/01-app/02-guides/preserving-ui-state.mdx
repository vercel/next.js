> **Good to know:** This guide assumes [Cache Components](/docs/app/getting-started/caching) is enabled. Enable it by setting [`cacheComponents: true`](/docs/app/api-reference/config/next-config-js/cacheComponents) in your Next config file.

Before Cache Components, preserving page-level state across navigations required workarounds like hoisting state to a [shared layout](/docs/app/getting-started/layouts-and-pages#nesting-layouts) or using an external store. With Cache Components, Next.js preserves recently visited routes and their UI state.

Instead of unmounting a page when you navigate away, Next.js hides it using React's [`<Activity>`](https://react.dev/reference/react/Activity) component. This changes the route lifecycle:

- React state and DOM state are preserved, including form values, expanded `<details>` elements, and media playback positions.
- The hidden DOM remains in the document with `display: none`.
- Effect cleanup functions run when the route is hidden. React runs the Effects again when the route becomes visible.
- Hidden components can continue to render at a lower priority when their props or state change.

Next.js preserves up to 3 routes. Beyond that, the oldest route is evicted and renders with fresh state when you visit it again.

> **Good to know:** An Effect cleanup indicates that React disconnected the Effect. It is not a navigation event. In development, [Strict Mode runs an extra setup and cleanup cycle](https://react.dev/reference/react/StrictMode#fixing-bugs-found-by-re-running-effects-in-development). Keep cleanup functions idempotent, and don't rely on an exact number of setup or cleanup calls.

## Choosing what to preserve

Activity preserves all component state and DOM state by default. For each piece of state, you decide whether that's the right behavior for your UI. The patterns below show common scenarios and how to handle both sides.

### Expandable UI (dropdowns, accordions, panels)

When a user navigates away and returns, Activity preserves the open/closed state of expandable elements.

**When to keep it:** A sidebar with expanded sections, a FAQ accordion, or a filters panel. The user set up their view intentionally, and restoring it avoids re-doing that work.

**When to reset it:** A dropdown menu or popover triggered by a button click. These are transient interactions, not persistent view state. Returning to a page with a dropdown already open is not user friendly.

For browser-managed UI such as a [popover](https://developer.mozilla.org/docs/Web/API/Popover_API), close it in a `useLayoutEffect` cleanup function. Calling `hidePopover()` more than once is safe, so the cleanup remains correct when React runs an extra setup and cleanup cycle in development:

```tsx highlight={9-13}
'use client'

import { useLayoutEffect, useRef } from 'react'

function SettingsDropdown() {
  const menuRef = useRef<HTMLDivElement>(null)

  useLayoutEffect(() => {
    return () => {
      menuRef.current?.hidePopover()
    }
  }, [])

  return (
    <>
      <button onClick={() => menuRef.current?.togglePopover()}>Options</button>
      <div ref={menuRef} popover="auto">
        <button>Edit Profile</button>
        <button>Change Password</button>
      </div>
    </>
  )
}
```

When Activity hides this component, the cleanup closes the popover before the route is hidden. You can also use `Link`'s [`onNavigate`](/docs/app/api-reference/components/link#onnavigate) callback to close UI immediately when a navigation link is clicked.

Avoid calling a React state setter from cleanup to detect navigation. In development, the extra Effect cycle can also run when Activity shows a route, which could reset state after the route becomes visible. Reset React state in the event that completes the interaction, or key a state-owning boundary when its identity changes.

### Dialogs and other top-layer UI

Activity preserves dialog open/closed state. A modal dialog, popover, or overlay can also stay in the browser's top layer after its route is hidden, where it may intercept interactions with the visible page.

Derive whether the dialog is open from the URL or other current data instead of using mount-time state. Close the dialog in the layout Effect cleanup so it leaves the top layer before the route is hidden:

```tsx filename="app/products/product-dialog.tsx" highlight={10,24-34}
'use client'

import { usePathname, useRouter, useSearchParams } from 'next/navigation'
import { useLayoutEffect, useRef } from 'react'

export function ProductDialog() {
  const pathname = usePathname()
  const searchParams = useSearchParams()
  const router = useRouter()
  const isDialogOpen = searchParams.get('edit') === 'true'
  const dialogRef = useRef<HTMLDialogElement>(null)

  function setDialogOpen(open: boolean) {
    const params = new URLSearchParams(searchParams.toString())
    if (open) {
      params.set('edit', 'true')
    } else {
      params.delete('edit')
    }
    const query = params.toString()
    router.replace(query ? `${pathname}?${query}` : pathname, { scroll: false })
  }

  useLayoutEffect(() => {
    const dialog = dialogRef.current
    if (!dialog) return

    if (isDialogOpen && !dialog.open) dialog.showModal()
    if (!isDialogOpen && dialog.open) dialog.close()

    return () => {
      if (dialog.open) dialog.close()
    }
  }, [isDialogOpen])

  return (
    <div>
      <button onClick={() => setDialogOpen(true)}>Edit Product</button>
      <dialog
        ref={dialogRef}
        onCancel={(event) => {
          event.preventDefault()
          setDialogOpen(false)
        }}
      >
        <label>
          Product name
          <input name="name" />
        </label>
        <button onClick={() => setDialogOpen(false)}>Close</button>
      </dialog>
    </div>
  )
}
```

When Activity shows the route again, the Effect reads the current `isDialogOpen` value and restores the dialog only when the URL calls for it. The cleanup also handles navigation through browser controls or links outside this component.

### Forms, inputs, and state

Activity preserves form input values (text fields, selected options, checkbox states), submission results, and status messages across navigations.

**When to keep it:** A search page with filters, a draft the user was composing, or a settings form with unsaved changes. Preserving input state is one of the biggest UX wins because the user doesn't lose work.

**When to reset it:** A "new transaction" flow where each visit should start fresh, or a form where stale success/error messages would be confusing in a new context.

#### Resetting form state on submit

Consider a page where the user creates a new item. After submitting, `router.push` navigates to the new record. Since Activity preserves the page, navigating back shows the previous name still in the form. Reset state in the event handler to keep the form fresh:

```tsx filename="app/new/page.tsx" highlight={13}
'use client'

import { useState } from 'react'
import { useRouter } from 'next/navigation'

export default function NewItemPage() {
  const [name, setName] = useState('')
  const router = useRouter()

  async function handleSubmit(e: React.SubmitEvent<HTMLFormElement>) {
    e.preventDefault()
    const item = await createItem({ name })
    setName('')
    router.push(`/items/${item.id}`)
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <button type="submit">Create</button>
    </form>
  )
}
```

Reset status messages in the same event that completes the interaction. When state belongs to a particular record, search, or user, key the component that owns the state by that identity. Avoid resetting React state from Effect or ref cleanup: cleanup can run more than once in development, including while Activity shows a route.

If you use [`useActionState`](https://react.dev/reference/react/useActionState), see [Reset state](https://react.dev/reference/react/useActionState#reset-state) in the React docs for how to add a `RESET` action to your reducer. For more on building responsive interactions with these hooks, see the [Building interactive apps](/docs/app/guides/interactive-apps) guide.

#### Syncing an uncontrolled input with the URL

An uncontrolled search input keeps its DOM value while its route is hidden. If the URL changes before the route becomes visible again, synchronize the input from the current URL in a layout Effect.

Pass the initial query from the page's [`searchParams` prop](/docs/app/api-reference/file-conventions/page#searchparams) so the server-rendered input has the right value. Keep the input uncontrolled so typing doesn't wait for the navigation Transition:

```tsx filename="app/search/search-input.tsx"
'use client'

import { useRouter } from 'next/navigation'
import { useLayoutEffect, useRef } from 'react'

export function SearchInput({ initialQuery }: { initialQuery: string }) {
  const router = useRouter()
  const inputRef = useRef<HTMLInputElement>(null)

  useLayoutEffect(() => {
    const input = inputRef.current
    if (!input) return
    input.value = new URL(window.location.href).searchParams.get('q') ?? ''
  }, [])

  return (
    <label>
      Search
      <input
        ref={inputRef}
        type="search"
        defaultValue={initialQuery}
        onChange={(event) => {
          const url = new URL(window.location.href)
          const query = event.currentTarget.value

          if (query) {
            url.searchParams.set('q', query)
          } else {
            url.searchParams.delete('q')
          }

          router.replace(`${url.pathname}${url.search}${url.hash}`, {
            scroll: false,
          })
        }}
      />
    </label>
  )
}
```

React re-runs the layout Effect when Activity shows the route, so the DOM value matches the current URL before the revealed route paints. Updating the existing `URL` preserves unrelated search parameters and the hash.

## State and authentication

Activity can preserve local component state and DOM input values across authentication changes. Receiving a different user as a prop doesn't reset existing state. Without an explicit boundary, a form draft created by one user can appear in another user's session.

Key the boundary that owns user-specific client state by the authenticated user's stable ID. React remounts the boundary when the user changes, which resets React state and uncontrolled DOM state together:

```tsx filename="app/account/page.tsx"
import { UserScopedForm } from './user-scoped-form'

export default async function AccountPage() {
  const user = await getCurrentUser()

  return <UserScopedForm key={user.id} />
}
```

Place the key above every component that stores state for that user. Continue to authorize all mutations on the server. Resetting client state prevents stale UI from appearing, but it is not an authorization boundary.

## Effects while a route is hidden

React cleans up a route's Effects when Activity hides it and sets them up again when the route becomes visible. An Effect with an empty dependency array therefore runs more than once during the route's lifetime.

This behavior prevents hidden routes from keeping subscriptions, timers, and event listeners active. It also means:

- A `beforeunload` listener inside a page stops protecting that page's draft while the route is hidden. If the warning must cover drafts across routes, store the dirty state in a shared layout and install the listener there.
- Setup logic runs again when the route becomes visible. Make it safe to repeat, and don't assume it only runs after the first mount.
- CSS entry animations can play again when the preserved DOM becomes visible. Track whether an animation has completed when it should only run once.

Use Effect cleanup to stop or undo external behavior. Prefer event handlers, URL state, or data-derived keys when you need to reset React state.

## Global styles

Page-level styles (CSS variables, z-index, global classes) can affect visible pages when the originating component is hidden by Activity. You likely want to disable them when hidden: a hidden page's accent color or z-index overrides shouldn't leak into the visible page.

Use a callback ref to toggle the stylesheet's `media` attribute:

```tsx
<style
  ref={(style) => {
    if (style) style.media = '' // Enable when visible
    return () => {
      if (style) style.media = 'not all' // Disable when hidden
    }
  }}
>
  {`:root { --page-accent: blue; }`}
</style>
```

Or use `useLayoutEffect` when managing multiple style elements or more complex cleanup:

```tsx
'use client'

import { useLayoutEffect, useRef } from 'react'

function PageWithStyles() {
  const styleRef = useRef<HTMLStyleElement>(null)

  useLayoutEffect(() => {
    if (styleRef.current) styleRef.current.media = ''
    return () => {
      if (styleRef.current) styleRef.current.media = 'not all'
    }
  }, [])

  return <style ref={styleRef}>{`:root { --page-accent: blue; }`}</style>
}
```

When Activity hides the component, the cleanup sets `media="not all"`, which disables the stylesheet. When visible again, the effect re-runs and resets `media` to enable it.

### The `:has` selector

A [`:root:has(...)`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has) rule applies styles based on its selector. Neither the selected element nor the matched element knows about the relationship. It's valid CSS, but it bypasses React's data flow and couples unrelated components.

For global state, prefer a `data-*` attribute that React owns:

```tsx
<html data-modal-open={modalOpen ? "true" : undefined}>
```

```css
html[data-modal-open='true'] {
  overflow: hidden;
}
```

Reserve `:has()` for local parent/child styling within a component:

```css
.card:has(img) {
  padding-top: 0;
}
```

This isn't only a React data-flow or Next.js concern. Broad `:has()` selectors are a real performance bottleneck. See [Performance considerations](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has#performance_considerations) on MDN.

> **Good to know:** If the hidden component itself defines the global `:has` rule, the toggle from the section above disables it along with the component's other styles.

## Scroll position

Hiding an element with `display: none` can reset the scroll position of a nested scroll container. Track the container's `scrollTop` as it scrolls, then restore it when the route becomes visible:

```tsx filename="app/components/scrollable-panel.tsx"
'use client'

import { useLayoutEffect, useRef, type ReactNode } from 'react'

export function ScrollablePanel({ children }: { children: ReactNode }) {
  const panelRef = useRef<HTMLDivElement>(null)
  const savedScrollTop = useRef(0)

  useLayoutEffect(() => {
    const panel = panelRef.current
    if (!panel) return

    panel.scrollTop = savedScrollTop.current
  }, [])

  return (
    <div
      ref={panelRef}
      className="scrollable-panel"
      onScroll={(event) => {
        savedScrollTop.current = event.currentTarget.scrollTop
      }}
    >
      {children}
    </div>
  )
}
```

The ref survives Activity hide and show cycles. If the route is evicted from the 3-route retention window, the component unmounts and the ref is lost. Store the position in a shared layout, URL, or another persistent store when it must survive eviction.

## Testing

Hidden Activity content has `display: none` but remains in the document. This applies both to routes preserved by Cache Components and to content you hide with `<Activity>` directly. It affects end-to-end testing with tools like Playwright, Cypress, or Puppeteer:

- **DOM queries can find hidden elements.** Selectors may match elements regardless of visibility.
- **Interactions with hidden elements fail or timeout.** Most tools wait for elements to become visible before interacting.
- **Assertions may match hidden content.** Be explicit about visibility when asserting element presence.

### Use visibility-aware selectors

In Playwright, `getByRole` excludes hidden elements by default:

```ts
// Good - getByRole filters by visibility automatically
await page.getByRole('button', { name: 'Submit' }).click()
await page.getByRole('textbox', { name: 'Email' }).fill('test@example.com')
```

Other locators, including `getByLabel` and `getByPlaceholder`, can match both the visible page and a hidden route. Use [visibility filtering](https://playwright.dev/docs/api/class-locator#locator-filter-option-visible) when `getByRole` isn't suitable:

```ts
// Fallback - filter by visibility explicitly
await page
  .getByLabel('Email')
  .filter({ visible: true })
  .fill('test@example.com')
await page.locator('.product-card').filter({ visible: true }).first().click()
await page
  .locator('[data-testid="timer"]')
  .filter({ visible: true })
  .textContent()

// Avoid - may match hidden elements in Activity boundaries
await page.locator('.product-card').first().click()
```

`getByRole` is robust to Activity, tabbed navigation, accordions, and other patterns that keep hidden content in the DOM. For other testing tools, check their documentation for visibility-aware selectors.

## Examples

For direct use of `<Activity>` in your components, see the [React Activity reference](https://react.dev/reference/react/Activity). The [Activity Patterns Demo](https://react-activity-patterns.labs.vercel.dev) ([source](https://github.com/nextjs/react-activity-patterns)) combines direct Activity examples with three Next.js routes preserved by Cache Components:

- **Data** — sortable table and selectable list that keep their state across navigations, plus a reviews section that prerenders in the background
- **Forms** — filter panel with DOM state (`<details>`, checkboxes, text inputs) that persists, and a newsletter submission flow
- **Side Effects** — a live timer that pauses when you navigate away and resumes when you return, and a video player that auto-pauses with playback position preserved
