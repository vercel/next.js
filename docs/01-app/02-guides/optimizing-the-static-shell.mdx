[Cache Components](/docs/app/getting-started/caching) can prerender a static shell while request-time content streams in. The shell can keep the route's layout, navigation, headings, and focused loading states visible instead of replacing the page with one broad fallback.

Apps written before Cache Components often await request data near the top of a layout or page. That structure is valid, but adopting a static shell can require a larger refactor than adding one boundary. Working through the route one change at a time lets you check the completed page as more content moves into the shell.

Read [Instant Navigation](/docs/app/guides/instant-navigation) for the rendering model and the Next.js DevTools workflow used to inspect each step.


## Patterns for building a useful static shell

Most static-shell refactors use the same patterns:

- **Pass request promises down.** Start `cookies()`, `headers()`, or another asynchronous read where it is convenient, but await the promise inside the component that needs the result.
- **Stream request-time work.** Put `params`, `searchParams`, and uncached data behind a focused `<Suspense>` boundary so static siblings can prerender.
- **Cache reusable work.** Add a cache directive only when the result can be reused. Choose its lifetime from the data's freshness requirements and invalidate it when a write changes the result.
- **Keep stable UI above the boundary.** Reuse existing loading states for the part that changes instead of replacing the route with one broad fallback.

The example applies these patterns to one route. You can make and verify each change separately, which may be more practical for an existing application than restructuring the route at once.

## Example

Consider a team settings route written in a blocking style. The layout resolves request data before it renders the settings frame:

```tsx filename="app/[team]/settings/layout.tsx"
import type { ReactNode } from 'react'
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'
import { getCurrentUser } from '@/lib/auth'
import { SettingsShell } from './settings-shell'

export default async function SettingsLayout({
  children,
}: {
  children: ReactNode
}) {
  const cookieStore = await cookies()
  const requestHeaders = await headers()
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) {
    redirect('/login')
  }

  return <SettingsShell>{children}</SettingsShell>
}
```

The page also resolves `params`, `searchParams`, and uncached settings before it renders the heading, filters, or form:

```tsx filename="app/[team]/settings/page.tsx"
import { getTeamSettings } from '@/lib/settings'
import { SettingsForm } from './settings-form'
import { SettingsSectionNav } from './settings-section-nav'

export default async function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  const { team } = await params
  const { section = 'profile' } = await searchParams
  const settings = await getTeamSettings(team, section)

  return (
    <main>
      <h1>Settings</h1>
      <SettingsSectionNav activeSection={section} />
      <SettingsForm settings={settings} />
    </main>
  )
}
```

These awaits happen before their surrounding components return, so the static shell cannot include the settings frame or page. This may be a natural structure in an existing App Router app. Moving each request-time read closer to the component that needs it preserves the completed route while more content becomes available in the shell.

### Step 1: Choose what belongs in the static shell

Start with the completed page and separate content by when its data is available. The settings route has five requirements:

| Content                    | Behavior                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------- |
| Settings frame and heading | Render without request data, so keep them in the static shell.                                    |
| Authentication redirect    | Check at request time. The check renders nothing for an authorized user.                          |
| Team settings form         | Read protected, team-specific data at request time and stream it behind the form's loading state. |
| Active settings section    | Read `searchParams` inside the part of the page that changes with the URL.                        |
| Plan descriptions          | Cache them because the same values can be reused across requests.                                 |

These decisions determine where the route needs `<Suspense>` and where caching is valid. They also keep authorization separate from presentation. Protected data must still authorize access inside the function that reads it.

Keep the primary heading or other [Largest Contentful Paint candidate](/docs/app/guides/streaming#lcp-largest-contentful-paint) in the static shell when possible. If its data can be reused, cache the data instead of moving the whole primary region behind a loading state.

### Step 2: Move request-time work behind focused boundaries

Start with the layout, then apply the same pattern to the page.

#### Keep the layout visible while authentication resolves

Start the `cookies()` and `headers()` reads in the layout, but pass their promises to the component that needs them. Moving the awaits and redirect into a component behind `<Suspense>` lets the layout return `SettingsShell` and `children` first.

```tsx filename="app/[team]/settings/layout.tsx" highlight={13-15,20-27}
import type { ReactNode } from 'react'
import { Suspense } from 'react'
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'
import { getCurrentUser } from '@/lib/auth'
import { SettingsShell } from './settings-shell'

export default function SettingsLayout({ children }: { children: ReactNode }) {
  const cookieStore = cookies()
  const requestHeaders = headers()

  return (
    <SettingsShell>
      <Suspense fallback={null}>
        <AuthGate cookieStore={cookieStore} requestHeaders={requestHeaders} />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate({
  cookieStore,
  requestHeaders,
}: {
  cookieStore: ReturnType<typeof cookies>
  requestHeaders: ReturnType<typeof headers>
}) {
  const user = await getCurrentUser({
    cookieStore: await cookieStore,
    requestHeaders: await requestHeaders,
  })

  if (!user) {
    redirect('/login')
  }

  return null
}
```

Calling `cookies()` or `headers()` starts the work without blocking the layout. `AuthGate` suspends when it awaits those promises, so the settings frame can stay in the static shell. The empty fallback is appropriate because an authorized `AuthGate` also returns `null`.

The shell must contain only content that is safe to send before authentication completes. Keep authorization checks in the data access functions used by the page. A layout redirect does not protect a database query or Server Action by itself. See [Authentication with Cache Components](/docs/app/guides/authentication-with-cache-components) for the complete authentication pattern.

#### Move page data into focused boundaries

Next, the page can return its heading before it resolves `params`, `searchParams`, or team settings. Pass each promise to the component that needs it and place that component behind a focused boundary.

```tsx filename="app/[team]/settings/page.tsx" highlight={7,10-12,17-26}
import { Suspense } from 'react'
import { getTeamSettings } from '@/lib/settings'
import { SettingsForm, SettingsFormSkeleton } from './settings-form'
import { SettingsTabs, SettingsTabsSkeleton } from './settings-tabs'

export default function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  return (
    <main>
      <h1>Settings</h1>
      <Suspense fallback={<SettingsTabsSkeleton />}>
        <SettingsTabs />
      </Suspense>
      <Suspense fallback={<SettingsFormSkeleton />}>
        <TeamSettings params={params} searchParams={searchParams} />
      </Suspense>
    </main>
  )
}

async function TeamSettings({
  params,
  searchParams,
}: Pick<PageProps<'/[team]/settings'>, 'params' | 'searchParams'>) {
  const { team } = await params
  const { section = 'profile' } = await searchParams
  const settings = await getTeamSettings(team, section)

  return <SettingsForm settings={settings} />
}
```

The heading and focused skeletons now render in the static shell. The protected settings read stays at request time and replaces only the form skeleton when it resolves.

`SettingsTabs` can be a Server Component that awaits `searchParams`, following the same pattern as `TeamSettings`. If it needs client-side interaction, pass the promise to a Client Component and unwrap it with React's [`use()`](https://react.dev/reference/react/use), or read the URL with [`useSearchParams()`](/docs/app/api-reference/functions/use-search-params):

```tsx filename="app/[team]/settings/settings-tabs.tsx"
'use client'

import { useSearchParams } from 'next/navigation'

export function SettingsTabs() {
  const section = useSearchParams().get('section') ?? 'profile'

  return (
    <nav aria-label="Settings sections">
      <a
        aria-current={section === 'profile' ? 'page' : undefined}
        href="?section=profile"
      >
        Profile
      </a>
      <a
        aria-current={section === 'billing' ? 'page' : undefined}
        href="?section=billing"
      >
        Billing
      </a>
    </nav>
  )
}

export function SettingsTabsSkeleton() {
  return <nav aria-label="Settings sections">Loading sections...</nav>
}
```

During a client navigation, `useSearchParams()` can resolve synchronously because the router already has the URL. The `<Suspense>` boundary is still needed for a page load, where the static shell does not know the query string.

The same focused-boundary placement applies to `cookies()`, `headers()`, `params`, `searchParams`, and uncached data. Start a promise higher in the tree when that avoids a request waterfall, but await it only inside the boundary for the content that needs the result.

An uncached database or network read already waits for the request and does not need `connection()`. Call [`connection()`](/docs/app/api-reference/functions/connection) before synchronous values such as `Date.now()`, `Math.random()`, or `crypto.randomUUID()` when they must be generated for each request. Cache the value instead when it should be shared across requests.

When a finite set of route parameters is known ahead of time, [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params) can prerender those routes. Keep parameter values that are not known at build time inside a focused boundary, as shown above. With Cache Components, [`next/root-params`](/docs/app/api-reference/functions/next-root-params#root-parameters-and-generatestaticparams) also requires at least one generated value for each root parameter.

#### Handle metadata and viewport

Metadata and viewport are resolved outside the page's component tree, so a boundary around page content does not cover them. Cache reusable values in `generateMetadata` or `generateViewport`. If metadata must use request data, it can stream alongside a static shell using a dynamic marker. A request-specific viewport cannot stream and makes the route blocking. See [`generateMetadata` and `generateViewport`](/docs/app/guides/migrating-to-cache-components#generatemetadata-and-generateviewport) for the complete patterns.

### Step 3: Cache data that can be reused

Streaming keeps request-time data from blocking the static shell. Caching includes reusable data in the shell after it resolves.

The settings page can cache plan descriptions because they are shared across teams and change on a known schedule. Keep team settings uncached because the page needs current, authorized values.

```tsx filename="app/[team]/settings/plan-options.tsx" highlight={7-8}
import { cacheLife } from 'next/cache'
import { db } from '@/lib/db'

export async function PlanOptions() {
  'use cache'
  cacheLife('hours')

  const plans = await db.plan.findMany({
    orderBy: { monthlyPrice: 'asc' },
  })

  return (
    <ul>
      {plans.map((plan) => (
        <li key={plan.id}>{plan.description}</li>
      ))}
    </ul>
  )
}
```

Render `PlanOptions` outside the team settings boundary:

```tsx filename="app/[team]/settings/page.tsx" highlight={3}
<main>
  <h1>Settings</h1>
  <PlanOptions />
  <Suspense fallback={<SettingsFormSkeleton />}>
    <TeamSettings params={params} />
  </Suspense>
</main>
```

Choose the cache lifetime from the data's freshness requirements. Keep data uncached when it must be recomputed for the request, even if caching would put more content in the shell. See [Caching](/docs/app/getting-started/caching) for cache keys, lifetimes, tags, and revalidation.

The default `use cache` handler stores entries in memory as a best effort. Use [`use cache: remote`](/docs/app/api-reference/directives/use-cache-remote) when cached data must persist across instances and requests.

React [`cache()`](https://react.dev/reference/react/cache) deduplicates work during a render, but it does not make request data available during prerendering. A `cache()` wrapper around `cookies()` or `headers()` still needs a `<Suspense>` boundary. Use a cache directive when the result itself can be reused.

## Reuse and place loading states

The static shell should reuse the loading states that already describe the completed page. It also needs a boundary in each server-rendered segment that can suspend.

### Reuse existing loading states

Before writing a loading state, check the route for an existing one:

1. Reuse the route's `loading.tsx` when the whole segment shares one loading state.
2. Reuse an exported `*Skeleton` colocated with the deferred component.
3. Reuse the fallback from an existing `<Suspense>` boundary inside the component.

If the component has no reusable loading state, extract its loading markup into a colocated skeleton. Avoid building a second skeleton that mirrors the whole page because the duplicate structure can drift from the completed layout.

If the same layout markup appears in the fallback and the completed component, move that markup above the boundary. React can then keep the stable layout mounted while the data streams. A `fallback={null}` is appropriate only when the deferred component also renders nothing, such as the authentication gate above.

> **Good to know:** Validation checks that request-time work is behind a boundary, not that the boundary renders useful content. A high-level `fallback={null}` can pass validation and still produce a blank shell. Use an empty fallback only when the resolved component also renders nothing. Otherwise, keep stable layout outside the boundary and provide a loading state for the deferred content.

See [Push dynamic access down](/docs/app/guides/streaming#push-dynamic-access-down) for the general Suspense pattern and [Iterate on loading states](/docs/app/guides/instant-navigation#iterate-on-loading-states) for inspecting the result.

### Place boundaries in the segments that change

Production routes often split the settings frame into [parallel route slots](/docs/app/api-reference/file-conventions/parallel-routes#slots):

```text
app/[team]/settings/
├── @sidebar/
│   └── page.tsx
├── page.tsx
└── layout.tsx
```

Each server-rendered slot has its own dynamic reads. A boundary around `children` does not cover a session or database read in `@sidebar`, so place a boundary in each slot that can suspend.

A slot that statically renders `null`, such as an empty `default.tsx`, does not suspend and does not need a boundary.

The example reuses a loading state exported by the sidebar:

```tsx filename="app/[team]/settings/@sidebar/sidebar.tsx"
export function SettingsSidebarSkeleton() {
  return <nav aria-label="Settings">Loading navigation...</nav>
}
```

```tsx filename="app/[team]/settings/layout.tsx" highlight={16-22}
import type { ReactNode } from 'react'
import { Suspense } from 'react'
import { redirect } from 'next/navigation'
import { getCurrentUser } from '@/lib/auth'
import { SettingsShell } from './settings-shell'
import { SettingsSidebarSkeleton } from './@sidebar/sidebar'

export default function SettingsLayout({
  children,
  sidebar,
}: {
  children: ReactNode
  sidebar: ReactNode
}) {
  return (
    <SettingsShell
      sidebar={
        <Suspense fallback={<SettingsSidebarSkeleton />}>{sidebar}</Suspense>
      }
    >
      <Suspense fallback={null}>
        <AuthGate />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate() {
  const user = await getCurrentUser()

  if (!user) {
    redirect('/login')
  }

  return null
}
```

Client navigation rerenders the server segments below the layout shared by the source and destination. Place a boundary inside that changing subtree. A boundary above the shared layout can help an initial page load without covering the client navigation.

The lowest layout shared by the source and destination is the divergence point. An initial page load renders every layout from the document root, while a client navigation renders only the segments below this point. A `loading.tsx` above the divergence point can provide the initial-load shell without covering that client navigation. A `loading.tsx` at the destination segment is inside both render paths and can cover both.

When an Insight still reports an uncovered read, see [Choosing where to place the boundary](/docs/messages/blocking-prerender-dynamic#choosing-where-to-place-the-boundary).

A Client Component in the shared layout can update when `usePathname()` changes, but it is outside the server render for the navigation. Focus the server boundaries on the slots and segments that Next.js renders for the destination.

### Keep loading states responsive

The static shell and completed page should use the same responsive layout. A separate desktop-shaped fallback can drift from a sidebar that becomes a drawer or select menu on smaller screens.

Keep the breakpoint logic in `SettingsShell`, then let the sidebar slot supply either its skeleton or resolved content. The shell changes layout once at each breakpoint, and both states use that same decision.

## Verify the static shell

Use the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools) to pause the route before request-time content resolves. Inspect both a direct visit and a client navigation because the direct visit renders from the root while the client navigation reuses shared layouts. Check that the settings frame, heading, cached plan descriptions, and focused skeletons appear in the expected layout on desktop and mobile.

Keep important shell content as regression coverage with [`instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests). Test initial loads and client navigations separately because they render different parts of the route tree:

```ts filename="e2e/settings-navigation.test.ts" highlight={12-18,25-32}
import { expect, test, type Page } from '@playwright/test'
import { instant } from '@next/playwright'

async function expectSettingsShell(page: Page) {
  await expect(page.getByRole('heading', { name: 'Settings' })).toBeVisible()
  await expect(page.getByTestId('plan-options')).toBeVisible()
  await expect(page.getByTestId('team-settings-form')).toHaveCount(0)
}

test('serves the settings shell on an initial load', async ({
  page,
  baseURL,
}) => {
  await instant(
    page,
    async () => {
      await page.goto('/acme/settings')
      await expectSettingsShell(page)
    },
    { baseURL }
  )

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})

test('prefetches the settings shell for a client navigation', async ({
  page,
}) => {
  await page.goto('/acme')

  await instant(page, async () => {
    await page.getByRole('link', { name: 'Settings' }).click()
    await page.waitForURL((url) => url.pathname === '/acme/settings')
    await expectSettingsShell(page)
  })

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})
```

Inside each callback, the settings heading and cached plan options must be visible while the request-time form remains paused. The final assertion confirms that the form renders after the pause is released. Use stable selectors from your application for the shell and deferred regions.

The completed route should have the same settings data, redirects, error states, and interactions as the original route.
