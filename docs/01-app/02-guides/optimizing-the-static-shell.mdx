[Cache Components](/docs/app/getting-started/caching) can prerender a static shell while request-time content streams in. The shell can keep the route's layout, navigation, headings, and focused loading states visible instead of replacing the page with one broad fallback.

Apps written before Cache Components often await request data near the top of a layout or page. With Cache Components enabled, those routes may already have a small static shell, sometimes made up of one broad loading state.

This guide shows how to expand that shell by tracing each data read to the UI that needs it, caching reusable work, and moving request-time work behind focused `<Suspense>` boundaries. It also covers how to keep important content available early and reserve space as the rest of the page streams in.

```ts filename="next.config.ts" highlight={4}
}

export default nextConfig
```

## Patterns

How much of a route can render in the static shell depends on the data each region needs and how fresh that data must be. Not every read should be cached, and not every loading state should be removed. When a layout or page awaits data near the top, trace each result to the UI that uses it, then choose the matching pattern:

| Pattern                                                     | Use it when                                        | Result                                                    |
| ----------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| [Keep static UI in the shell](#keep-static-ui-in-the-shell) | A region does not need request data                | Its completed UI can render in the static shell           |
| [Cache reusable work](#cache-reusable-work)                 | A result can be reused across requests             | The cached result can render in the static shell          |
| [Stream request-time work](#stream-request-time-work)       | A region needs request data or other uncached data | Its nearest `<Suspense>` fallback can render in the shell |

### Keep static UI in the shell

A `<Suspense>` boundary controls which part of the UI its fallback replaces when a child suspends. Static UI can sit inside a boundary without a problem. However, if the same boundary also contains slow or request-time work, that fallback temporarily replaces the static UI too.

To keep headings, navigation, cached content, and other stable UI visible, place the boundary around the smaller region that can suspend:

```tsx filename="app/products/page.tsx" highlight={2-4}
<main>
  <h1>Products</h1>
  <CategoryNav />
  <ProductList />
  <Suspense fallback={<InventorySkeleton />}>
    <Inventory />
  </Suspense>
</main>
```

When possible, avoid placing the primary heading or other [Largest Contentful Paint candidate](/docs/app/guides/streaming#lcp-largest-contentful-paint) in the same fallback region as slower work. If that content needs reusable data, cache the data so the completed content can render in the shell.

### Cache reusable work

Uncached data must be computed during the request and can leave the region showing a fallback. When the result can be reused, cache the function or component so its completed UI can render in the static shell. Give the result a lifetime based on how fresh the data needs to be:

```tsx filename="app/products/product-list.tsx" highlight={4-6}
import { cacheLife, cacheTag } from 'next/cache'

export async function ProductList() {
  'use cache'
  cacheLife('hours')
  cacheTag('products')

  const products = await db.products.findMany()
  return <List products={products} />
}
```

If the application can change a cached result, use [`cacheTag()`](/docs/app/getting-started/revalidating#cachetag) to connect the cached read to its writes. Follow [Revalidating](/docs/app/getting-started/revalidating) to invalidate the tag from the corresponding mutation, then verify that the next read returns the updated value. Use [`use cache: remote`](/docs/app/api-reference/directives/use-cache-remote) when an entry must persist across instances and requests. Keep data uncached when it must be recomputed for each request.

React [`cache()`](https://react.dev/reference/react/cache) can instead deduplicate matching calls during one server request. It does not persist the result across requests or make request-time data part of the static shell. See [Reusing data with `React.cache`](/docs/app/getting-started/fetching-data#reusing-data-with-reactcache) for that pattern.

To prerender known dynamic routes and generate others on demand, see [ISR with Cache Components](/docs/app/guides/incremental-static-regeneration-cache-components).

Learn more about cache scopes and lifetimes in [Caching](/docs/app/getting-started/caching#usage).

### Stream request-time work

Some data cannot be known until a request arrives. If a layout or page awaits that work before returning its UI, stable content in the same component waits too. Let the region that needs the data suspend so the rest of the route can render first.

#### Resolve data in the Server Component that uses it

Move `params`, `searchParams`, or an uncached data read into the smallest Server Component that needs it. Place that component behind `<Suspense>` so its stable siblings stay visible while the work resolves:

```tsx filename="app/products/[slug]/page.tsx" highlight={7-9,17-18}
import { Suspense } from 'react'

export default function ProductPage({ params }: PageProps<'/products/[slug]'>) {
  return (
    <main>
      <h1>Product</h1>
      <Suspense fallback={<ProductSkeleton />}>
        <Product params={params} />
      </Suspense>
    </main>
  )
}

async function Product({
  params,
}: Pick<PageProps<'/products/[slug]'>, 'params'>) {
  const { slug } = await params
  const product = await db.products.findBySlug(slug)
  return <ProductDetails product={product} />
}
```

The heading and product fallback can render before the uncached product query finishes. Request APIs such as `cookies()` and `headers()` follow the same pattern:

```tsx filename="app/dashboard/layout.tsx" highlight={7-9,16}
import { Suspense } from 'react'
import { cookies } from 'next/headers'

export default function DashboardLayout({ children }) {
  return (
    <DashboardShell>
      <Suspense fallback={<UserMenuSkeleton />}>
        <UserMenu />
      </Suspense>
      {children}
    </DashboardShell>
  )
}

async function UserMenu() {
  const cookieStore = await cookies()
  const menuStyle = cookieStore.get('menu-style')?.value ?? 'compact'

  return <DashboardMenu menuStyle={menuStyle} />
}
```

The layout can return `DashboardShell` before `UserMenu` reads the incoming request.

For a small region, you do not need to create another component only to await a promise. Resolve `params`, `searchParams`, or another promise inline with `.then()` inside the boundary:

```tsx filename="app/products/page.tsx" highlight={2}
<Suspense fallback={<ProductTabsSkeleton />}>
  {searchParams.then(({ tab = 'details' }) => (
    <ProductTabs activeTab={tab} />
  ))}
</Suspense>
```

See [Push dynamic access down](/docs/app/guides/streaming#push-dynamic-access-down) for more examples of resolving request-time work closer to the UI that uses it.

#### Pass promises to Client Components

An interactive Client Component may need data fetched on the server. Awaiting that data in its parent would also hold back the parent's stable UI. Instead, start the request without awaiting it and pass the promise to the Client Component behind `<Suspense>`:

```tsx filename="app/dashboard/page.tsx" highlight={6,9-10}
import { Suspense } from 'react'
import { getActivity } from '@/app/lib/data'
import { ActivityChart } from './activity-chart'

export default function DashboardPage() {
  const activityPromise = getActivity()

  return (
    <Suspense fallback={<ActivityChartSkeleton />}>
      <ActivityChart dataPromise={activityPromise} />
    </Suspense>
  )
}
```

The Client Component unwraps the promise with React's [`use()`](https://react.dev/reference/react/use):

```tsx filename="app/dashboard/activity-chart.tsx" highlight={12}
'use client'

import { use } from 'react'

type Activity = { date: string; value: number }

export function ActivityChart({
  dataPromise,
}: {
  dataPromise: Promise<Activity[]>
}) {
  const activity = use(dataPromise)

  return <Chart data={activity} />
}
```

For URL state, a Client Component can usually call [`useSearchParams()`](/docs/app/api-reference/functions/use-search-params) directly instead of receiving the `searchParams` promise. The hook resolves synchronously during a client navigation because the router already has the URL. On a page load, it needs a boundary because the static shell does not know the query string.

#### Avoid data waterfalls

Moving request-time work into smaller components also gives independent work a chance to start sooner. When the results belong to separate UI regions, use sibling async components so React can render them in parallel and stream each one when it is ready:

```tsx filename="app/dashboard/page.tsx"
<Suspense fallback={<SalesSkeleton />}>
  <Sales />
</Suspense>
<Suspense fallback={<ActivitySkeleton />}>
  <Activity />
</Suspense>
```

If one UI region needs multiple independent results, start the requests together before awaiting them:

```tsx filename="app/dashboard/comparison-chart.tsx" highlight={2-3,5}
export async function ComparisonChart({ teamId }: { teamId: string }) {
  const revenuePromise = getRevenue(teamId)
  const targetPromise = getRevenueTarget(teamId)

  const [revenue, target] = await Promise.all([revenuePromise, targetPromise])

  return <Chart actual={revenue} target={target} />
}
```

Keep requests sequential when the second needs a result from the first:

```tsx filename="app/[team]/projects/page.tsx" highlight={2-3}
export async function Projects({ slug }: { slug: string }) {
  const team = await getTeam(slug)
  const projects = await getProjects(team.id)

  return <ProjectList projects={projects} />
}
```

If React reaches a component only after other blocking work, but the request inputs are already available, [preload the data](/docs/app/getting-started/fetching-data#preloading-data) to start that work earlier.

Learn more about [sequential and parallel data fetching](/docs/app/getting-started/fetching-data#sequential-data-fetching).

#### Design loading states

When a child suspends, its nearest boundary shows the fallback until the child is ready. This is the UI people see while the region streams, so its size and placement affect both the loading experience and [Cumulative Layout Shift](/docs/app/guides/streaming#cls-cumulative-layout-shift).

Use separate boundaries when regions can reveal independently. Nest them when a group should first appear together, followed by progressively more detail:

```tsx filename="app/account/page.tsx"
<Suspense fallback={<AccountSkeleton />}>
  <AccountHeader />
  <Suspense fallback={<ActivitySkeleton />}>
    <Activity />
  </Suspense>
</Suspense>
```

Keep shared layout outside the boundary so the fallback and completed content follow the same responsive rules:

```tsx filename="app/products/page.tsx"
<ProductGridFrame>
  <Suspense fallback={<ProductGridSkeleton />}>
    <Products />
  </Suspense>
</ProductGridFrame>
```

> **Good to know:** As the completed UI changes, its skeleton might no longer match its size or responsive layout. Keeping the skeleton next to the component, or exporting it from the same file, makes it easier to update and reuse wherever the component suspends. For variable-length content, a collapsed Show more/Show less state can reserve predictable space for the content below.

An empty fallback works when the resolved component has no visual footprint, such as an authorization gate that returns `null`.

When a route uses parallel slots, each slot can stream with its own loading state. See [Loading and Error UI with Parallel Routes](/docs/app/api-reference/file-conventions/parallel-routes#loading-and-error-ui).

Learn more about choosing sibling and nested boundaries in [Streaming](/docs/app/guides/streaming#granular-streaming-with-suspense).

## Example

Consider a team settings route that awaits request data near the top of both its layout and page. This structure may feel natural in an App Router application written before Cache Components. It can also carry over from the [Pages Router](/docs/app/guides/migrating/app-router-migration#step-6-migrating-data-fetching-methods), where a route-level function such as `getServerSideProps` loads data before rendering the page. In the App Router, the same structure leaves none of the settings UI in the static shell.

The example starts with one layout and one page:

```text filename="Folder structure"
app/[team]/settings/
├── layout.tsx
└── page.tsx
```

The layout waits for authentication before it returns the settings frame:

```tsx filename="app/[team]/settings/layout.tsx"
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default async function SettingsLayout({ children }) {
  const cookieStore = await cookies()
  const requestHeaders = await headers()
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) redirect('/login')

  return <SettingsShell>{children}</SettingsShell>
}
```

The page then waits for its URL data, team settings, and reusable plan descriptions before it returns the heading:

```tsx filename="app/[team]/settings/page.tsx"
export default async function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  const { team } = await params
  const { section = 'profile' } = await searchParams
  const [settings, plans] = await Promise.all([
    getTeamSettings(team, section),
    db.plan.findMany(),
  ])

  return (
    <main>
      <h1>Settings</h1>
      <SettingsTabs activeSection={section} />
      <PlanList plans={plans} />
      <SettingsForm settings={settings} />
    </main>
  )
}
```

The following steps keep the completed page and its authorization behavior while making more of it available in the static shell.

If you want to compare the route visually as it changes, the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools) can pause a direct visit or client navigation before request-time data resolves.

### Step 1: Move URL-dependent work behind Suspense

The settings tabs are interactive, so they can read the URL directly with `useSearchParams()`. The server-rendered form receives the `params` and `searchParams` promises and resolves them where their values are needed.

First, put both regions behind a focused boundary:

```tsx filename="app/[team]/settings/page.tsx" highlight={10-15}
import { Suspense } from 'react'

export default function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  return (
    <main>
      <h1>Settings</h1>
      <Suspense fallback={<SettingsContentSkeleton />}>
        <SettingsTabs />
        <Suspense fallback={<SettingsFormSkeleton />}>
          <TeamSettings params={params} searchParams={searchParams} />
        </Suspense>
      </Suspense>
    </main>
  )
}
```

The tabs read the active section from the URL:

```tsx filename="app/[team]/settings/settings-tabs.tsx" highlight={3,6}
'use client'

import { useSearchParams } from 'next/navigation'

export function SettingsTabs() {
  const section = useSearchParams().get('section') ?? 'profile'

  return <Tabs activeSection={section} />
}
```

The form awaits both URL promises before starting the query that depends on their values:

```tsx filename="app/[team]/settings/team-settings.tsx" highlight={5-9}
export async function TeamSettings({
  params,
  searchParams,
}: Pick<PageProps<'/[team]/settings'>, 'params' | 'searchParams'>) {
  const [{ team }, { section = 'profile' }] = await Promise.all([
    params,
    searchParams,
  ])
  const settings = await getTeamSettings(team, section)

  return <SettingsForm settings={settings} />
}
```

On a page load, the tabs appear once the URL is available while the form continues to show its nested loading state. During a client navigation, `useSearchParams()` can resolve synchronously. The settings query starts after the server resolves the team and section it depends on.

The plan query does not depend on either URL value. Move it into a sibling component so React can start it while the URL-dependent branch is pending. It remains uncached at this point, so keep a temporary boundary:

```tsx filename="app/[team]/settings/page.tsx" highlight={3-5}
<main>
  <h1>Settings</h1>
  <Suspense fallback={<PlanOptionsSkeleton />}>
    <PlanOptions />
  </Suspense>
  <Suspense fallback={<SettingsContentSkeleton />}>
    <SettingsTabs />
    <Suspense fallback={<SettingsFormSkeleton />}>
      <TeamSettings params={params} searchParams={searchParams} />
    </Suspense>
  </Suspense>
</main>
```

```tsx filename="app/[team]/settings/plan-options.tsx"
export async function PlanOptions() {
  const plans = await db.plan.findMany()
  return <PlanList plans={plans} />
}
```

The heading renders directly. `PlanOptions` and the URL-dependent settings branch can begin independently.

### Step 2: Move authentication behind Suspense

Move the `cookies()` and `headers()` reads into an authentication gate behind `<Suspense>`. The layout can return the settings frame without waiting for authentication:

```tsx filename="app/[team]/settings/layout.tsx" highlight={8-10,17-19}
import { Suspense } from 'react'
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default function SettingsLayout({ children }) {
  return (
    <SettingsShell>
      <Suspense fallback={null}>
        <AuthGate />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate() {
  const [cookieStore, requestHeaders] = await Promise.all([
    cookies(),
    headers(),
  ])
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) redirect('/login')

  return null
}
```

`AuthGate` is the only component that needs the request values, so it owns those reads. Its boundary lets the settings frame and page stay in the shell. An empty fallback fits this boundary because an authorized gate also returns `null`.

> **Good to know:** Because `AuthGate` runs after the shell starts streaming, its redirect is handled on the client. If the gate calls [`unauthorized()`](/docs/app/api-reference/functions/unauthorized) or [`forbidden()`](/docs/app/api-reference/functions/forbidden), the corresponding UI can render, but the HTTP response remains `200`. If the response must return `401` or `403`, perform the route-level check in [`proxy`](/docs/app/api-reference/file-conventions/proxy) before rendering. See [Status codes](/docs/app/api-reference/file-conventions/loading#status-codes).

A layout redirect does not protect a database query or Server Action by itself. Keep authorization checks in the data access functions used by the page, and include only safe UI in the shell before authentication completes. See [Authentication with Cache Components](/docs/app/guides/authentication-with-cache-components) for the complete pattern.

### Step 3: Cache the reusable plan data

The team settings must stay current and authorized for each request, so they stay uncached behind `<Suspense>`. Plan descriptions are shared across teams and change on a known schedule, so `PlanOptions` can cache them:

```tsx filename="app/[team]/settings/plan-options.tsx" highlight={4-5}
import { cacheLife } from 'next/cache'

export async function PlanOptions() {
  'use cache'
  cacheLife('hours')

  const plans = await db.plan.findMany()
  return <PlanList plans={plans} />
}
```

`PlanOptions` has no request-time dependency, so Next.js can resolve it while generating the static shell. Its existing `<Suspense>` boundary does not prevent that, but the fallback is no longer needed for this route. You can remove the boundary so the code reflects that the completed plan list is part of the shell. If a cached component is only reached after request-time data resolves, keep a boundary around that branch so it can show a loading state while the cache fills.

If a write changes the plan descriptions, revalidate this cache from the corresponding mutation.

```tsx filename="app/[team]/settings/page.tsx" highlight={3}
<main>
  <h1>Settings</h1>
  <PlanOptions />
  <Suspense fallback={<SettingsContentSkeleton />}>
    <SettingsTabs />
    <Suspense fallback={<SettingsFormSkeleton />}>
      <TeamSettings params={params} searchParams={searchParams} />
    </Suspense>
  </Suspense>
</main>
```

The finished route now reveals in stages:

```text
1. In the static shell             2. After the URL resolves          3. After the settings load
┌──────────────────────────────┐   ┌──────────────────────────────┐   ┌──────────────────────────────┐
│ <h1>Settings</h1>            │   │ <h1>Settings</h1>            │   │ <h1>Settings</h1>            │
│ <PlanOptions />              │   │ <PlanOptions />              │   │ <PlanOptions />              │
│ <SettingsContentSkeleton />  │   │ <SettingsTabs />             │   │ <SettingsTabs />             │
│                              │   │ <SettingsFormSkeleton />     │   │ <TeamSettings />             │
└──────────────────────────────┘   └──────────────────────────────┘   └──────────────────────────────┘
```

### Step 4: Verify the instant UI

Suppose you want to ensure that future changes keep this loading state in the static shell. Use [`instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests) around a direct page load, without warming or prefetching the route:

```ts filename="e2e/settings-navigation.test.ts" highlight={14,17-18}
import { expect, test, type Page } from '@playwright/test'
import { instant } from '@next/playwright'

async function expectSettingsShell(page: Page) {
  await expect(page.getByRole('heading', { name: 'Settings' })).toBeVisible()
  await expect(page.getByTestId('plan-options')).toBeVisible()
  await expect(page.getByTestId('team-settings-form')).toHaveCount(0)
}

test('serves the settings shell on an initial load', async ({
  page,
  baseURL,
}) => {
  await instant(
    page,
    async () => {
      await page.goto('/acme/settings')
      await expectSettingsShell(page)
    },
    { baseURL }
  )

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})
```

Inside the callback, the settings heading and cached plan options must be visible while the request-time form is paused. The final assertion confirms that the form renders after the pause is released.

The completed route should have the same settings data, redirects, error states, and interactions as the original route.

### Step 5: Continue with prefetching

The test above captures the shared static shell for a direct visit. It still shows `SettingsContentSkeleton` because the route does not know `searchParams` during prerendering.

During a client navigation, `SettingsTabs` can read the URL synchronously. Other server content that depends on the destination's `params` or `searchParams` is not part of the shared shell. If that work is cacheable, a per-link prefetch can resolve it before the click instead of streaming it afterward.

Continue with [Optimizing prefetching](/docs/app/guides/optimizing-prefetching) when that URL-specific content should be part of an individual link's prefetched UI. The guide also covers how to choose a prefetch policy based on the cost of the work.
