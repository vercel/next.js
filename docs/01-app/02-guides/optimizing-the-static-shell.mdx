[Cache Components](/docs/app/getting-started/caching) can prerender a static shell while request-time content streams in. The shell can keep the route's layout, navigation, headings, and focused loading states visible instead of replacing the page with one broad fallback.

Apps written before Cache Components often await request data near the top of a layout or page. With Cache Components enabled, those routes may already have a small static shell made up of a broad loading state. Expanding it can require a larger refactor: moving data reads closer to the UI that needs them, caching reusable work, and deciding how content should stream through `<Suspense>`.

The goal is not to make the shell larger for its own sake. Keep the [Largest Contentful Paint](/docs/app/guides/streaming#lcp-largest-contentful-paint) candidate available early, reserve space to reduce [Cumulative Layout Shift](/docs/app/guides/streaming#cls-cumulative-layout-shift), and design a loading experience that reveals the page in useful, coherent stages.

Read [Instant Navigation](/docs/app/guides/instant-navigation) for the rendering model and the Next.js DevTools workflow used to inspect each step.

## Prerequisites

Enable [`cacheComponents`](/docs/app/api-reference/config/next-config-js/cacheComponents) and resolve the route's blocking validation errors first. For the migration workflow, see [Migrating to Cache Components](/docs/app/guides/migrating-to-cache-components).

```ts filename="next.config.ts" highlight={4}
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig
```

## Patterns

When a layout or page awaits data near the top, trace each result to the UI that actually uses it. Then apply the matching pattern:

| Data needed by the region | Pattern                                                                                     | Static shell                               |
| ------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------ |
| No request data           | Render the region directly                                                                  | Includes the completed UI                  |
| Reusable data             | Cache the function or component, with a lifetime and on-demand revalidation when it changes | Includes the cached result                 |
| Request-time data         | Await the data in a focused component behind `<Suspense>`                                   | Includes the boundary's focused loading UI |

### Keep static UI in the shell

A boundary should wrap only the region that waits for request-time data. Render headings, navigation, cached content, and other stable UI directly:

```tsx filename="app/products/page.tsx" highlight={2-4}
<main>
  <h1>Products</h1>
  <CategoryNav />
  <ProductList />
  <Suspense fallback={<InventorySkeleton />}>
    <Inventory />
  </Suspense>
</main>
```

Keep the primary heading or other [Largest Contentful Paint candidate](/docs/app/guides/streaming#lcp-largest-contentful-paint) outside the boundary when possible. If its data can be reused, cache the data instead of moving the whole primary region behind a loading state.

Learn how to choose what reveals together and avoid layout shifts in [Design the loading UI](#design-the-loading-ui).

### Cache reusable work

Cache a function or component when its result can be reused. Give the result a lifetime based on how fresh the data needs to be:

```tsx filename="app/products/product-list.tsx" highlight={4-5}
import { cacheLife } from 'next/cache'

export async function ProductList() {
  'use cache'
  cacheLife('hours')

  const products = await db.products.findMany()
  return <List products={products} />
}
```

If the application can change a cached result, add on-demand revalidation to the corresponding write and verify the read after the mutation. Use [`use cache: remote`](/docs/app/api-reference/directives/use-cache-remote) when an entry must persist across instances and requests. Keep data uncached when it must be recomputed for each request.

Learn more about cache keys, lifetimes, tags, and on-demand revalidation in [Caching](/docs/app/getting-started/caching).

### Stream request-time work

A top-level `await` prevents the component from returning its stable UI. Pass `params`, `searchParams`, or another promise to a smaller component and await it behind `<Suspense>`:

```tsx filename="app/products/[slug]/page.tsx" highlight={7-9,17-18}
import { Suspense } from 'react'

export default function ProductPage({ params }: PageProps<'/products/[slug]'>) {
  return (
    <main>
      <h1>Product</h1>
      <Suspense fallback={<ProductSkeleton />}>
        <Product params={params} />
      </Suspense>
    </main>
  )
}

async function Product({
  params,
}: Pick<PageProps<'/products/[slug]'>, 'params'>) {
  const { slug } = await params
  const product = await db.products.findBySlug(slug)
  return <ProductDetails product={product} />
}
```

The heading and fallback can render in the static shell while the uncached product query waits for the request. The same pattern applies to `searchParams`, `cookies()`, and `headers()`.

Independent async components behind sibling boundaries can render and stream in parallel. Keep data fetching sequential when one request needs the result of another. When independent requests must stay in the same component, start them together before awaiting them with `Promise.all`.

Learn more about passing promises through the tree and placing focused boundaries in [Streaming](/docs/app/guides/streaming#push-dynamic-access-down), and about [sequential and parallel data fetching](/docs/app/getting-started/fetching-data#sequential-data-fetching).

## Example

Consider a team settings route that awaits request data near the top of both its layout and page. This structure may be natural in an App Router application written before Cache Components, but it leaves no useful static shell.

The layout waits for authentication before it returns the settings frame:

```tsx filename="app/[team]/settings/layout.tsx"
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default async function SettingsLayout({ children }) {
  const cookieStore = await cookies()
  const requestHeaders = await headers()
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) redirect('/login')

  return <SettingsShell>{children}</SettingsShell>
}
```

The page then waits for its URL data, team settings, and reusable plan descriptions before it returns the heading:

```tsx filename="app/[team]/settings/page.tsx"
export default async function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  const { team } = await params
  const { section = 'profile' } = await searchParams
  const [settings, plans] = await Promise.all([
    getTeamSettings(team, section),
    db.plan.findMany(),
  ])

  return (
    <main>
      <h1>Settings</h1>
      <SettingsTabs activeSection={section} />
      <PlanList plans={plans} />
      <SettingsForm settings={settings} />
    </main>
  )
}
```

The following steps keep the completed page and its authorization behavior while making more of it available in the static shell.

### Step 1: Find what each await blocks

Read the layout and page from the top down. The layout waits for authentication before returning `SettingsShell`, even though the frame does not use the authenticated user. The page waits for its URL data before returning the heading. Its plan query also starts only after the URL data resolves, even though the plans do not depend on the URL.

For each region, keep only the data dependency it needs:

| Region                     | Data                                       | Rendering choice                                           |
| -------------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| Settings frame and heading | No request data                            | Render directly in the static shell                        |
| Plan descriptions          | Reusable data                              | Cache and render in the static shell                       |
| Active settings tab        | `searchParams`                             | Stream as part of the settings content                     |
| Team settings form         | `params`, `searchParams`, and current data | Stream behind a nested form loading state                  |
| Authentication redirect    | `cookies()` and `headers()`                | Stream through a gate that renders nothing when authorized |

Protected data must still authorize access inside the function that reads it. The static shell should contain only UI that is safe to send before authentication completes.

### Step 2: Return the page before request-time data resolves

Move the URL-dependent work into a focused `SettingsContent` component. The page can now return its heading and loading states without awaiting `params` or `searchParams` itself.

The plan query is independent of the URL, so move it into a sibling component where React can start rendering it without waiting for `SettingsContent`. It is still uncached at this point and needs its own boundary. These boundaries also determine [how the loading UI reveals](#design-the-loading-ui):

```tsx filename="app/[team]/settings/page.tsx" highlight={10,13,34}
import { Suspense } from 'react'

export default function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  return (
    <main>
      <h1>Settings</h1>
      <Suspense fallback={<PlanOptionsSkeleton />}>
        <PlanOptions />
      </Suspense>
      <Suspense fallback={<SettingsContentSkeleton />}>
        <SettingsContent params={params} searchParams={searchParams} />
      </Suspense>
    </main>
  )
}

async function PlanOptions() {
  const plans = await db.plan.findMany()
  return <PlanList plans={plans} />
}

async function SettingsContent({
  params,
  searchParams,
}: Pick<PageProps<'/[team]/settings'>, 'params' | 'searchParams'>) {
  const { section = 'profile' } = await searchParams

  return (
    <>
      <SettingsTabs activeSection={section} />
      <Suspense fallback={<SettingsFormSkeleton />}>
        <TeamSettings params={params} section={section} />
      </Suspense>
    </>
  )
}

async function TeamSettings({
  params,
  section,
}: Pick<PageProps<'/[team]/settings'>, 'params'> & { section: string }) {
  const { team } = await params
  const settings = await getTeamSettings(team, section)

  return <SettingsForm settings={settings} />
}
```

React can begin rendering `PlanOptions` and `SettingsContent` in parallel. Inside `SettingsContent`, the settings query is sequential because it needs both the team and selected section. After `searchParams` resolves, the tabs can render while the nested boundary continues to show the form skeleton. This avoids revealing three related regions independently.

`SettingsContent` can pass the resolved section to an interactive Client Component. You can instead pass the `searchParams` promise to a Client Component and unwrap it with React's [`use()`](https://react.dev/reference/react/use), or read the URL with [`useSearchParams()`](/docs/app/api-reference/functions/use-search-params). Keep the Client Component behind the same outer boundary for the page-load shell.

During a client navigation, `useSearchParams()` can resolve synchronously because the router already has the URL. On a page load, the static shell does not know the query string, so it renders the tab loading state.

When a finite set of parameter values is known ahead of time, [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params) can prerender those routes. Values that are not generated are resolved at request time and follow the boundary pattern above. With Cache Components, [`next/root-params`](/docs/app/api-reference/functions/next-root-params#root-parameters-and-generatestaticparams) also requires at least one generated value for each root parameter.

### Step 3: Return the layout before authentication resolves

Start the `cookies()` and `headers()` reads in the layout without awaiting them. Pass the promises to an authentication gate behind `<Suspense>`:

```tsx filename="app/[team]/settings/layout.tsx" highlight={6-7,11,21-22}
import { Suspense } from 'react'
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default function SettingsLayout({ children }) {
  const cookieStore = cookies()
  const requestHeaders = headers()

  return (
    <SettingsShell>
      <Suspense fallback={null}>
        <AuthGate cookieStore={cookieStore} requestHeaders={requestHeaders} />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate({ cookieStore, requestHeaders }) {
  const user = await getCurrentUser({
    cookieStore: await cookieStore,
    requestHeaders: await requestHeaders,
  })

  if (!user) redirect('/login')

  return null
}
```

`AuthGate` suspends when it awaits the promises, so the settings frame and page can stay in the shell. An empty fallback fits this boundary because an authorized gate also returns `null`.

A layout redirect does not protect a database query or Server Action by itself. Keep authorization checks in the data access functions used by the page. See [Authentication with Cache Components](/docs/app/guides/authentication-with-cache-components) for the complete pattern.

React [`cache()`](https://react.dev/reference/react/cache) can deduplicate a request read during a render, but it does not make that read available during prerendering. A `cache()` wrapper around `cookies()` or `headers()` still needs a boundary.

### Step 4: Cache the reusable data

The team settings must stay current and authorized for each request, so they stay uncached behind `<Suspense>`. Plan descriptions are shared across teams and change on a known schedule, so `PlanOptions` can cache them:

```tsx filename="app/[team]/settings/plan-options.tsx" highlight={4-5}
import { cacheLife } from 'next/cache'

export async function PlanOptions() {
  'use cache'
  cacheLife('hours')

  const plans = await db.plan.findMany()
  return <PlanList plans={plans} />
}
```

Once `PlanOptions` is cacheable, remove its `<Suspense>` boundary so the cached result renders directly:

```tsx filename="app/[team]/settings/page.tsx" highlight={3}
<main>
  <h1>Settings</h1>
  <PlanOptions />
  <Suspense fallback={<SettingsContentSkeleton />}>
    <SettingsContent params={params} searchParams={searchParams} />
  </Suspense>
</main>
```

The finished static shell contains the settings frame, heading, cached plan descriptions, and focused loading states for the active tab and form. Authentication and team settings still resolve for the request. If a write changes the plan descriptions, revalidate this cache from the corresponding mutation.

## Design the loading UI

As you move request-time work behind `<Suspense>` to avoid blocking the page, its fallback becomes part of the static shell. Loading UI that does not reserve the same space as the completed content can cause [Cumulative Layout Shift](/docs/app/guides/streaming#cls-cumulative-layout-shift) when React replaces it.

A boundary also controls which content reveals together. A broad boundary can pass validation while replacing most of the page with one fallback. Keep stable layout outside the boundary, then choose whether the other regions should stream independently or as a group.

Separate boundaries work well when each region has a predictable size and can appear without moving the content around it. Group related regions when separate fallbacks would make the page jump or appear in fragments. Nested boundaries can reveal a stable part of the group first while slower content continues to show its own fallback, as the settings example does with its tabs and form.

Each fallback should use the same layout and reserve the same space as the content it replaces. A `fallback={null}` is appropriate only when the resolved component also renders nothing, such as the authentication gate above.

Validation checks that request-time work is behind a boundary, not whether the loading UI is useful. Use the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools) to pause the route, compare the fallback with the completed page, and adjust the reveal groups. See [Streaming](/docs/app/guides/streaming#push-dynamic-access-down) for the general Suspense pattern.

### Place boundaries in the segments that change

Production routes often split the settings frame into [parallel route slots](/docs/app/api-reference/file-conventions/parallel-routes#slots):

```text
app/[team]/settings/
├── @sidebar/
│   └── page.tsx
├── page.tsx
└── layout.tsx
```

Each server-rendered slot has its own dynamic reads. A boundary around `children` does not cover a session or database read in `@sidebar`, so place a boundary in each slot that can suspend.

A slot that statically renders `null`, such as an empty `default.tsx`, does not suspend and does not need a boundary.

The example reuses a loading state exported by the sidebar:

```tsx filename="app/[team]/settings/@sidebar/sidebar.tsx"
export function SettingsSidebarSkeleton() {
  return <nav aria-label="Settings">Loading navigation...</nav>
}
```

```tsx filename="app/[team]/settings/layout.tsx" highlight={18}
import type { ReactNode } from 'react'
import { Suspense } from 'react'
import { redirect } from 'next/navigation'
import { getCurrentUser } from '@/lib/auth'
import { SettingsShell } from './settings-shell'
import { SettingsSidebarSkeleton } from './@sidebar/sidebar'

export default function SettingsLayout({
  children,
  sidebar,
}: {
  children: ReactNode
  sidebar: ReactNode
}) {
  return (
    <SettingsShell
      sidebar={
        <Suspense fallback={<SettingsSidebarSkeleton />}>{sidebar}</Suspense>
      }
    >
      <Suspense fallback={null}>
        <AuthGate />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate() {
  const user = await getCurrentUser()

  if (!user) {
    redirect('/login')
  }

  return null
}
```

Client navigation rerenders the server segments below the layout shared by the source and destination. Place a boundary inside that changing subtree. A boundary above the shared layout can help an initial page load without covering the client navigation.

The lowest layout shared by the source and destination is the divergence point. An initial page load renders every layout from the document root, while a client navigation renders only the segments below this point. A `loading.tsx` above the divergence point can provide the initial-load shell without covering that client navigation. A `loading.tsx` at the destination segment is inside both render paths and can cover both.

When an Insight still reports an uncovered read, see [Choosing where to place the boundary](/docs/messages/blocking-prerender-dynamic#choosing-where-to-place-the-boundary).

A Client Component in the shared layout can update when `usePathname()` changes, but it is outside the server render for the navigation. Focus the server boundaries on the slots and segments that Next.js renders for the destination.

### Match the completed layout

The static shell and completed page should use the same dimensions and responsive layout. A separate desktop-shaped fallback can drift from a sidebar that becomes a drawer or select menu on smaller screens.

Keep the breakpoint logic in `SettingsShell`, then let the sidebar slot supply either its skeleton or resolved content. The shell changes layout once at each breakpoint, and both states use that same decision.

## Handle metadata and viewport

Metadata and viewport are resolved outside the page's component tree, so a boundary around page content does not cover them. Cache reusable values in `generateMetadata` or `generateViewport`. If metadata must use request data, it can stream alongside a static shell using a dynamic marker. A request-specific viewport cannot stream and makes the route blocking. See [`generateMetadata` and `generateViewport`](/docs/app/guides/migrating-to-cache-components#generatemetadata-and-generateviewport) for the complete patterns.

## Verify the static shell

Use the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools) to pause the route before request-time content resolves. Inspect both a direct visit and a client navigation because the direct visit renders from the root while the client navigation reuses shared layouts. Check that the settings frame, heading, cached plan descriptions, and focused skeletons appear in the expected layout on desktop and mobile.

Keep important shell content as regression coverage with [`instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests). Test initial loads and client navigations separately because they render different parts of the route tree:

```ts filename="e2e/settings-navigation.test.ts" highlight={14,31}
import { expect, test, type Page } from '@playwright/test'
import { instant } from '@next/playwright'

async function expectSettingsShell(page: Page) {
  await expect(page.getByRole('heading', { name: 'Settings' })).toBeVisible()
  await expect(page.getByTestId('plan-options')).toBeVisible()
  await expect(page.getByTestId('team-settings-form')).toHaveCount(0)
}

test('serves the settings shell on an initial load', async ({
  page,
  baseURL,
}) => {
  await instant(
    page,
    async () => {
      await page.goto('/acme/settings')
      await expectSettingsShell(page)
    },
    { baseURL }
  )

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})

test('prefetches the settings shell for a client navigation', async ({
  page,
}) => {
  await page.goto('/acme')

  await instant(page, async () => {
    await page.getByRole('link', { name: 'Settings' }).click()
    await page.waitForURL((url) => url.pathname === '/acme/settings')
    await expectSettingsShell(page)
  })

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})
```

Inside each callback, the settings heading and cached plan options must be visible while the request-time form is paused. The final assertion confirms that the form renders after the pause is released. Use stable selectors from your application for the shell and deferred regions.

The completed route should have the same settings data, redirects, error states, and interactions as the original route.

## Continue with prefetching

The static shell is shared across links to the route. It can show a focused loading state for content that depends on a destination's `params` or `searchParams`, but it does not contain the result for each URL.

If the shell is already instant and you want that URL-specific content ready before the click, continue with [Optimizing prefetching](/docs/app/guides/optimizing-prefetching). It covers how to prefetch cacheable content for an individual link and choose a prefetch policy based on its cost.
