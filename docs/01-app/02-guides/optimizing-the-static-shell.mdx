[Cache Components](/docs/app/getting-started/caching) can prerender a static shell while request-time content streams in. The shell can keep the route's layout, navigation, headings, and focused loading states visible instead of replacing the page with one broad fallback.

Apps written before Cache Components often await request data near the top of a layout or page. With Cache Components enabled, those routes may already have a small static shell, sometimes made up of one broad loading state.

In this guide, you'll expand that shell by tracing each data read to the UI that needs it, caching reusable work, and moving request-time work behind focused `<Suspense>` boundaries. You'll also keep important content available early and reserve space as the rest of the page streams in.

## Patterns

When a layout or page awaits data near the top, trace each result to the UI that actually uses it. Then apply the matching pattern:

| Data needed by the region | Pattern                                                                                     | Static shell                                     |
| ------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| No request data           | Render the region directly                                                                  | Includes the completed UI when it is reachable   |
| Reusable data             | Cache the function or component, with a lifetime and on-demand revalidation when it changes | Can include the cached result                    |
| Request-time data         | Await the data in a focused component behind `<Suspense>`                                   | Can include the nearest boundary's loading state |

### Keep static UI in the shell

A boundary should wrap only the region that waits for request-time data. Render headings, navigation, cached content, and other stable UI directly:

```tsx filename="app/products/page.tsx" highlight={2-4}
<main>
  <h1>Products</h1>
  <CategoryNav />
  <ProductList />
  <Suspense fallback={<InventorySkeleton />}>
    <Inventory />
  </Suspense>
</main>
```

Keep the primary heading or other [Largest Contentful Paint candidate](/docs/app/guides/streaming#lcp-largest-contentful-paint) outside the boundary when possible. If its data can be reused, cache the data instead of moving the whole primary region behind a loading state.

### Cache reusable work

Cache a function or component when its result can be reused. Give the result a lifetime based on how fresh the data needs to be:

```tsx filename="app/products/product-list.tsx" highlight={4-5}
import { cacheLife } from 'next/cache'

export async function ProductList() {
  'use cache'
  cacheLife('hours')

  const products = await db.products.findMany()
  return <List products={products} />
}
```

If the application can change a cached result, add on-demand revalidation to the corresponding write and verify the read after the mutation. Use [`use cache: remote`](/docs/app/api-reference/directives/use-cache-remote) when an entry must persist across instances and requests. Keep data uncached when it must be recomputed for each request.

Learn more about cache scopes and lifetimes in [Caching](/docs/app/getting-started/caching#usage), and about updating cached data after a mutation in [Revalidating](/docs/app/getting-started/revalidating).

### Reuse work within a request

React [`cache()`](https://react.dev/reference/react/cache) can deduplicate matching calls during one server request. This is useful when several components need the same uncached data:

```tsx filename="app/lib/user.ts" highlight={3}
import { cache } from 'react'

export const getUser = cache(async (id: string) => {
  return db.user.findUnique({ where: { id } })
})
```

Unlike `use cache`, React `cache()` does not persist the result across requests or make request-time data available during prerendering. Wrapping a `cookies()`, `headers()`, or uncached data read with React `cache()` does not make it part of the static shell. The component that reads it still needs a boundary. See [Reusing data with `React.cache`](/docs/app/getting-started/fetching-data#reusing-data-with-reactcache) for the complete request memoization pattern.

### Stream request-time work

#### Resolve promises in Server Components

A top-level `await` prevents the component from returning its stable UI. Pass `params`, `searchParams`, or another promise to the region that needs it, then resolve it behind `<Suspense>`:

```tsx filename="app/products/[slug]/page.tsx" highlight={7-9,17-18}
import { Suspense } from 'react'

export default function ProductPage({ params }: PageProps<'/products/[slug]'>) {
  return (
    <main>
      <h1>Product</h1>
      <Suspense fallback={<ProductSkeleton />}>
        <Product params={params} />
      </Suspense>
    </main>
  )
}

async function Product({
  params,
}: Pick<PageProps<'/products/[slug]'>, 'params'>) {
  const { slug } = await params
  const product = await db.products.findBySlug(slug)
  return <ProductDetails product={product} />
}
```

The heading and fallback can render in the static shell while the uncached product query waits for the request. For `cookies()` or `headers()` reads that only one Server Component needs, move the read into that component and place it behind the boundary.

If a layout already starts a request read that a child needs, pass the promise without awaiting it in the layout:

```tsx filename="app/dashboard/layout.tsx" highlight={2,6}
export default function DashboardLayout({ children }) {
  const cookieStore = cookies()

  return (
    <DashboardShell>
      <Suspense fallback={<UserMenuSkeleton />}>
        <UserMenu cookieStore={cookieStore} />
      </Suspense>
      {children}
    </DashboardShell>
  )
}
```

The child resolves the promise inside the boundary. The layout does not wait before returning the dashboard shell.

A Server Component can resolve `searchParams` inline with `.then()` without making the page itself async:

```tsx filename="app/products/page.tsx" highlight={2}
<Suspense fallback={<ProductTabsSkeleton />}>
  {searchParams.then(({ tab = 'details' }) => (
    <ProductTabs activeTab={tab} />
  ))}
</Suspense>
```

When a finite set of parameter values is known ahead of time, [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params) can prerender those routes. Values that are not generated resolve at request time and follow the boundary pattern above. With Cache Components, [`next/root-params`](/docs/app/api-reference/functions/next-root-params#root-parameters-and-generatestaticparams) also requires at least one generated value for each root parameter.

#### Unwrap promises in Client Components

Pass a promise from a Server Component to a Client Component when the interactive UI needs the value. The Client Component can unwrap it with React's [`use()`](https://react.dev/reference/react/use). Keep the Client Component behind `<Suspense>`:

```tsx filename="app/products/page.tsx"
<Suspense fallback={<ProductTabsSkeleton />}>
  <ProductTabsClient searchParams={searchParams} />
</Suspense>
```

```tsx filename="app/products/product-tabs-client.tsx" highlight={10}
'use client'

import { use } from 'react'

export function ProductTabsClient({
  searchParams,
}: {
  searchParams: Promise<{ tab?: string }>
}) {
  const { tab = 'details' } = use(searchParams)

  return <nav>{/* Render the active tab. */}</nav>
}
```

A Client Component can also read the URL with [`useSearchParams()`](/docs/app/api-reference/functions/use-search-params). It can resolve synchronously during a client navigation because the router already has the URL. On a page load, it needs a boundary because the static shell does not know the query string.

Learn more about passing promises through the tree and placing focused boundaries in [Streaming](/docs/app/guides/streaming#push-dynamic-access-down).

#### Design loading states

When a child suspends, its nearest boundary shows the fallback until the child is ready. A fallback encountered during prerendering can become part of the static shell. A boundary reached after request-time data resolves can show its fallback later while the remaining work streams.

Choose boundaries based on which parts of the page should reveal together. Sibling boundaries let independent regions complete in any order:

```tsx filename="app/dashboard/page.tsx"
<Suspense fallback={<SalesSkeleton />}>
  <Sales />
</Suspense>
<Suspense fallback={<ActivitySkeleton />}>
  <Activity />
</Suspense>
```

Nest boundaries when a group should first appear together, followed by progressively more detail:

```tsx filename="app/account/page.tsx"
<Suspense fallback={<AccountSkeleton />}>
  <AccountHeader />
  <Suspense fallback={<ActivitySkeleton />}>
    <Activity />
  </Suspense>
</Suspense>
```

A fallback should reserve space for the content it replaces to reduce [Cumulative Layout Shift](/docs/app/guides/streaming#cls-cumulative-layout-shift). Share the responsive frame between the fallback and completed content so both states follow the same layout rules:

```tsx filename="app/products/page.tsx"
<Suspense
  fallback={
    <ProductGridFrame>
      <ProductGridSkeleton />
    </ProductGridFrame>
  }
>
  <ProductGridFrame>
    <Products />
  </ProductGridFrame>
</Suspense>
```

An empty fallback works when the resolved component has no visual footprint, such as an authorization gate that returns `null`.

When a route uses parallel slots, each slot can stream with its own loading state. See [Loading and Error UI with Parallel Routes](/docs/app/api-reference/file-conventions/parallel-routes#loading-and-error-ui).

#### Avoid data waterfalls

Suspense controls when content is revealed. It does not make already-reachable data requests sequential. Independent async components behind sibling boundaries can render and stream in parallel.

When independent requests stay in the same component, start both before awaiting them:

```tsx filename="app/dashboard/overview.tsx" highlight={2-3,5}
export async function Overview({ userId }: { userId: string }) {
  const profilePromise = getProfile(userId)
  const activityPromise = getActivity(userId)

  const [profile, activity] = await Promise.all([
    profilePromise,
    activityPromise,
  ])

  return <Dashboard profile={profile} activity={activity} />
}
```

Keep the requests sequential when the second needs a result from the first:

```tsx filename="app/[team]/projects/page.tsx" highlight={2-3}
export async function Projects({ slug }: { slug: string }) {
  const team = await getTeam(slug)
  const projects = await getProjects(team.id)

  return <ProjectList projects={projects} />
}
```

If React reaches a component only after other blocking work, but the request inputs are already available, [preload the data](/docs/app/getting-started/fetching-data#preloading-data) to start that work earlier.

Learn more about [sequential and parallel data fetching](/docs/app/getting-started/fetching-data#sequential-data-fetching).

## Example

Consider a team settings route that awaits request data near the top of both its layout and page. This structure may feel natural in an App Router application written before Cache Components. It can also carry over from the [Pages Router](/docs/app/guides/migrating/app-router-migration#step-6-migrating-data-fetching-methods), where a route-level function such as `getServerSideProps` loads data before rendering the page. In the App Router, the same structure leaves none of the settings UI in the static shell.

The example starts with one layout and one page:

```text filename="Folder structure"
app/[team]/settings/
├── layout.tsx
└── page.tsx
```

The layout waits for authentication before it returns the settings frame:

```tsx filename="app/[team]/settings/layout.tsx"
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default async function SettingsLayout({ children }) {
  const cookieStore = await cookies()
  const requestHeaders = await headers()
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) redirect('/login')

  return <SettingsShell>{children}</SettingsShell>
}
```

The page then waits for its URL data, team settings, and reusable plan descriptions before it returns the heading:

```tsx filename="app/[team]/settings/page.tsx"
export default async function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  const { team } = await params
  const { section = 'profile' } = await searchParams
  const [settings, plans] = await Promise.all([
    getTeamSettings(team, section),
    db.plan.findMany(),
  ])

  return (
    <main>
      <h1>Settings</h1>
      <SettingsTabs activeSection={section} />
      <PlanList plans={plans} />
      <SettingsForm settings={settings} />
    </main>
  )
}
```

The following steps keep the completed page and its authorization behavior while making more of it available in the static shell.

If you want to compare the route visually as it changes, the [Navigation Inspector](/docs/app/guides/instant-navigation#visualize-loading-states-with-the-nextjs-devtools) can pause a direct visit or client navigation before request-time data resolves.

### Step 1: Move URL-dependent work behind Suspense

The settings tabs are interactive, so pass `searchParams` to the Client Component and unwrap it with `use()`. The server-rendered form receives the same promise and resolves it where the section is needed.

First, put both regions behind a focused boundary:

```tsx filename="app/[team]/settings/page.tsx" highlight={9-16}
import { Suspense } from 'react'

export default function SettingsPage({
  params,
  searchParams,
}: PageProps<'/[team]/settings'>) {
  return (
    <main>
      <h1>Settings</h1>
      <Suspense fallback={<SettingsContentSkeleton />}>
        <SettingsTabs searchParams={searchParams} />
        <Suspense fallback={<SettingsFormSkeleton />}>
          <TeamSettings params={params} searchParams={searchParams} />
        </Suspense>
      </Suspense>
    </main>
  )
}
```

The tabs unwrap the promise in a Client Component:

```tsx filename="app/[team]/settings/settings-tabs.tsx" highlight={10}
'use client'

import { use } from 'react'

export function SettingsTabs({
  searchParams,
}: Pick<PageProps<'/[team]/settings'>, 'searchParams'>) {
  const { section = 'profile' } = use(searchParams)

  return <Tabs activeSection={section} />
}
```

The form awaits both URL promises before starting the query that depends on their values:

```tsx filename="app/[team]/settings/team-settings.tsx" highlight={7-10}
export async function TeamSettings({
  params,
  searchParams,
}: Pick<PageProps<'/[team]/settings'>, 'params' | 'searchParams'>) {
  const [{ team }, { section = 'profile' }] = await Promise.all([
    params,
    searchParams,
  ])
  const settings = await getTeamSettings(team, section)

  return <SettingsForm settings={settings} />
}
```

The tabs can appear once `searchParams` resolves while the form continues to show its nested loading state. The settings query starts afterward because it depends on the resolved team and section.

The plan query does not depend on either URL value. Move it into a sibling component so React can start it while the URL-dependent branch is pending. It remains uncached at this point, so keep a temporary boundary:

```tsx filename="app/[team]/settings/page.tsx" highlight={3-5}
<main>
  <h1>Settings</h1>
  <Suspense fallback={<PlanOptionsSkeleton />}>
    <PlanOptions />
  </Suspense>
  <Suspense fallback={<SettingsContentSkeleton />}>
    <SettingsTabs searchParams={searchParams} />
    <Suspense fallback={<SettingsFormSkeleton />}>
      <TeamSettings params={params} searchParams={searchParams} />
    </Suspense>
  </Suspense>
</main>
```

```tsx filename="app/[team]/settings/plan-options.tsx"
export async function PlanOptions() {
  const plans = await db.plan.findMany()
  return <PlanList plans={plans} />
}
```

The heading renders directly. `PlanOptions` and the URL-dependent settings branch can begin independently.

### Step 2: Move authentication behind Suspense

Move the `cookies()` and `headers()` reads into an authentication gate behind `<Suspense>`. The layout can return the settings frame without waiting for authentication:

```tsx filename="app/[team]/settings/layout.tsx" highlight={8,16,20}
import { Suspense } from 'react'
import { cookies, headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default function SettingsLayout({ children }) {
  return (
    <SettingsShell>
      <Suspense fallback={null}>
        <AuthGate />
      </Suspense>
      {children}
    </SettingsShell>
  )
}

async function AuthGate() {
  const [cookieStore, requestHeaders] = await Promise.all([
    cookies(),
    headers(),
  ])
  const user = await getCurrentUser({ cookieStore, requestHeaders })

  if (!user) redirect('/login')

  return null
}
```

`AuthGate` is the only component that needs the request values, so it owns those reads. Its boundary lets the settings frame and page stay in the shell. An empty fallback fits this boundary because an authorized gate also returns `null`.

A layout redirect does not protect a database query or Server Action by itself. Keep authorization checks in the data access functions used by the page, and include only safe UI in the shell before authentication completes. See [Authentication with Cache Components](/docs/app/guides/authentication-with-cache-components) for the complete pattern.

### Step 3: Cache the reusable plan data

The team settings must stay current and authorized for each request, so they stay uncached behind `<Suspense>`. Plan descriptions are shared across teams and change on a known schedule, so `PlanOptions` can cache them:

```tsx filename="app/[team]/settings/plan-options.tsx" highlight={4-5}
import { cacheLife } from 'next/cache'

export async function PlanOptions() {
  'use cache'
  cacheLife('hours')

  const plans = await db.plan.findMany()
  return <PlanList plans={plans} />
}
```

`PlanOptions` has no request-time dependency, so Next.js can resolve it while generating the static shell. Its existing `<Suspense>` boundary does not prevent that, but the fallback is no longer needed for this route. You can remove the boundary so the code reflects that the completed plan list is part of the shell. If a cached component is only reached after request-time data resolves, keep a boundary around that branch so it can show a loading state while the cache fills.

If a write changes the plan descriptions, revalidate this cache from the corresponding mutation.

```tsx filename="app/[team]/settings/page.tsx" highlight={3}
<main>
  <h1>Settings</h1>
  <PlanOptions />
  <Suspense fallback={<SettingsContentSkeleton />}>
    <SettingsTabs searchParams={searchParams} />
    <Suspense fallback={<SettingsFormSkeleton />}>
      <TeamSettings params={params} searchParams={searchParams} />
    </Suspense>
  </Suspense>
</main>
```

The finished route now reveals in stages:

| When                    | New content available                            | Loading state             |
| ----------------------- | ------------------------------------------------ | ------------------------- |
| In the static shell     | Settings frame, heading, and cached plan options | Settings content skeleton |
| After the URL resolves  | Active settings tab                              | Settings form skeleton    |
| After the settings load | Settings form                                    | None                      |

## Follow validation as you refactor

When you load or navigate to a route in `next dev`, [instant navigation validation](/docs/app/guides/instant-navigation#validate-instant-navigation) reports request-time or uncached work that prevents some UI from rendering instantly. A new insight after a refactor can mean that a data read moved outside its boundary or that new uncached work was introduced.

The insight identifies the affected code and links to the available fixes. For reads in the page or layout tree, see [runtime data during prerendering or a navigation](/docs/messages/blocking-prerender-runtime) and [uncached data during prerendering or a navigation](/docs/messages/blocking-prerender-dynamic).

### Metadata and viewport

Metadata and viewport are resolved outside the page's component tree, so a boundary around page content does not cover them. Their insights separate request data from uncached data:

- For metadata, see [runtime data in `generateMetadata()`](/docs/messages/blocking-prerender-metadata-runtime) or [uncached data in `generateMetadata()`](/docs/messages/blocking-prerender-metadata-dynamic). Metadata can stream alongside a static shell when the page includes an intentional dynamic marker.
- For viewport, see [runtime data in `generateViewport()`](/docs/messages/blocking-prerender-viewport-runtime) or [uncached data in `generateViewport()`](/docs/messages/blocking-prerender-viewport-dynamic). Viewport cannot stream, so request-time viewport data makes the route blocking.

For the complete API behavior, see [`generateMetadata`](/docs/app/api-reference/functions/generate-metadata#with-cache-components), [`generateViewport`](/docs/app/api-reference/functions/generate-viewport#with-cache-components), and the [Cache Components migration guide](/docs/app/guides/migrating-to-cache-components#generatemetadata-and-generateviewport).

## Verify the instant UI

The Navigation Inspector can pause the route before request-time content resolves. Repeat the inspection for a direct visit and a client navigation because the direct visit renders from the root while the client navigation reuses shared layouts. Check that the settings frame, heading, cached plan descriptions, and focused skeletons appear in the expected layout on desktop and mobile.

Keep important shell content as regression coverage with [`instant()`](/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests). Test initial loads and client navigations separately because they render different parts of the route tree:

```ts filename="e2e/settings-navigation.test.ts" highlight={14,31}
import { expect, test, type Page } from '@playwright/test'
import { instant } from '@next/playwright'

async function expectSettingsShell(page: Page) {
  await expect(page.getByRole('heading', { name: 'Settings' })).toBeVisible()
  await expect(page.getByTestId('plan-options')).toBeVisible()
  await expect(page.getByTestId('team-settings-form')).toHaveCount(0)
}

test('serves the settings shell on an initial load', async ({
  page,
  baseURL,
}) => {
  await instant(
    page,
    async () => {
      await page.goto('/acme/settings')
      await expectSettingsShell(page)
    },
    { baseURL }
  )

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})

test('prefetches the settings shell for a client navigation', async ({
  page,
}) => {
  await page.goto('/acme')

  await instant(page, async () => {
    await page.getByRole('link', { name: 'Settings' }).click()
    await page.waitForURL((url) => url.pathname === '/acme/settings')
    await expectSettingsShell(page)
  })

  await expect(page.getByTestId('team-settings-form')).toBeVisible()
})
```

Inside each callback, the settings heading and cached plan options must be visible while the request-time form is paused. The final assertion confirms that the form renders after the pause is released. Use stable selectors from your application for the shell and deferred regions.

The completed route should have the same settings data, redirects, error states, and interactions as the original route.

## Continue with prefetching

The static shell is shared across links to the route. It can show a focused loading state for content that depends on a destination's `params` or `searchParams`, but it does not contain the result for each URL.

If the shell is already instant and you want that URL-specific content ready before the click, continue with [Optimizing prefetching](/docs/app/guides/optimizing-prefetching). It covers how to prefetch cacheable content for an individual link and choose a prefetch policy based on its cost.
