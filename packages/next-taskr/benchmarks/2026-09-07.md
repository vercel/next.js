# Taskr versus Rust runner — 2026-09-07

The current Rust runner is slower for this release-build workload, including with
a populated transform cache. Paired geometric-mean time ratios show **76% more
time cold** and **24% more time warm**. The local machine was busy, so the magnitude
is indicative rather than an isolated-machine performance claim.

| Runner                          | Median full release | Observed range | Paired time increase |
| ------------------------------- | ------------------: | -------------: | -------------------: |
| Taskr                           |             32.75 s |  32.28–84.49 s |             baseline |
| Rust, empty transform cache     |             78.88 s | 50.77–103.61 s |                 +76% |
| Rust, populated transform cache |             47.34 s |  37.02–82.00 s |                 +24% |

Relative increases compare each Rust run with the Taskr run in the same block,
then take the geometric mean. They are not ratios of the marginal medians.
Exploratory paired bootstrap intervals (10,000 block resamples, six blocks)
correspond to approximately **47–120% more time cold** and **9–41% more time
warm**. These intervals do not remove the effects of host contention.

## Workload and environment

- Apple M3 Max, 16 logical CPUs, 48 GiB RAM, macOS arm64.
- Node 20.20.0, pnpm 10.33.0, Taskr 1.1.0, SWC 1.11.24, Rspack 1.6.7,
  NCC 0.38.4, TypeScript 6.0.2.
- Checkout revision: `416bf20921cc3ffeab61a181927ae0c4051088f8`, plus the current
  uncommitted Rust runner changes. Input and binary hashes are saved in the
  adjacent JSON report.
- Rust used `cargo build -p next-taskr --release`: optimized code, thin LTO, no
  debug assertions. Native runner compilation was excluded from timings.
- Before: `pnpm --filter=next build`. After: `pnpm --filter=next build:rust --stats`,
  with `NEXT_TASKR_BINARY` pointing to the optimized binary.
- Each release clears `dist` and runs the complete package build, including
  runtime bundling and declaration generation. Package-manager and launcher
  startup are included; output comparison and cache preparation are outside the
  timer. Turborepo does not bypass these commands.
- Six repetitions per variant, all six order permutations. Warm-ups excluded.
  Cold means an empty Rust persistent transform cache; operating-system page
  caches and other build-tool caches were not flushed.
- Every measured cold Rust run executed 2,669 transforms; every warm run executed
  zero.

## Phase observations

Median phase durations, taken from timestamped progress events except for the
recovered Taskr sample described below:

| Runner                          | File compilation (`next_compile`) | TypeScript declarations |
| ------------------------------- | --------------------------------: | ----------------------: |
| Taskr                           |                            3.16 s |                 19.80 s |
| Rust, empty transform cache     |                           21.77 s |                 35.44 s |
| Rust, populated transform cache |                            9.84 s |                 23.87 s |

File compilation shows the clearest regression. The current protocol includes
the entire 253,425-byte error-code table in every transform cache request. Across
2,669 requests, that is 676,391,325 bytes (about 645 MiB) before JSON escaping,
even on a warm build. This is a concrete source of avoidable overhead, although
these timings alone do not assign a precise fraction of the regression to it.
Sharing that input once per session is the first optimization to investigate.

## Correctness and run notes

All 18 measured builds exited successfully and their 8,453 output files passed
comparison. Five runs needed the agreed Rspack exception; the other thirteen
matched byte for byte. The exception verifies equality after only the tracer
module-ID spelling change and its corresponding generated-column shifts in
source maps. Other output contents, paths, entry types and executable bits remain
checked.

An initial Node 20 warm-up exposed an IPC `writev`/ENOBUFS failure. The worker now
waits for each protocol write to complete. That fix was present for every measured
Rust run. Failed setup attempts are not included in the measured series.

The checker initially recognized only the Turbo runtime variants. It paused
after block 5 when the same ID race appeared in the non-Turbo variants. That
difference was verified and accepted. The successful block 5 Taskr timing was
recovered from its progress log at 1 ms precision; its phase durations use Taskr's
own timings. No measured successful run was discarded. The series resumed for
the final block with the same runner binary and Node version. The cache backup
was moved outside the repository for the resumed block; original cache contents
were restored afterward.

Other git, vitest, filesystem-event, and system activity was observed during the
series. In particular, TypeScript declaration time varied from roughly 18 to 62
seconds across the Taskr runs. This explains why raw ranges are broad and why
paired comparisons and phase timings are also shown.

## Reproduce

Run in a bootstrapped checkout without another build or watch process writing its
outputs:

```sh
cargo build -p next-taskr --release
node scripts/benchmark-taskr.js /tmp/taskr-benchmark-new-run
```

The results directory must be new. The harness saves logs, phase events, artifact
comparison results, and all timings. `--resume` continues an interrupted series
with the same binary and Node version.

The adjacent `2026-09-07.json` preserves the summary, measured timings, source
hashes, and accepted-difference paths. Complete original logs and timestamped
events are in `/tmp/next-taskr-benchmark-2026-09-07-v3/`.
